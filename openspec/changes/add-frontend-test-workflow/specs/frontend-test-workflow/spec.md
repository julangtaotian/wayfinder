## Purpose

为前端仓库提供可独立调用、可审查和可验证的测试用例工作流，使已确认需求能够稳定形成测试方案、项目原生测试与真实验证证据，同时保护业务源码、依赖和既有测试所有权。

## ADDED Requirements

### Requirement: 测试入口必须按用户意图区分阶段和写入权限

系统 MUST 提供唯一公共测试入口，并 MUST 区分只读分析、持久化测试方案、测试代码实现和验证复验。只读分析 MUST 默认零写入；持久化方案和测试实现 MUST 分别要求用户明确请求，且无活动变更时 MUST NOT 持久化方案或修改测试代码。（D-01、D-03；A-01）

#### Scenario: 用户只要求分析覆盖

- **WHEN** 用户要求盘点需求或模块的测试覆盖且没有请求写入
- **THEN** 系统只读取需求、变更、源码、测试设施和 Git 基线并报告缺口，不创建或修改文件

#### Scenario: 无活动变更时要求写测试

- **WHEN** 用户在没有适用活动变更的情况下要求持久化方案或实现测试
- **THEN** 系统保持只读并说明需要先建立受管变更，不把当前实现推断为已确认产品行为

### Requirement: 测试方案必须以 TC 用例建立完整追踪

活动变更的测试方案 MUST 位于该变更的 `test-plan.md`，并 MUST 记录需求路径、完整变更名、最新需求修订基线、测试上下文和一个或多个唯一 `TC-*`。每条用例 MUST 记录优先级、验证类型与层级、适用 D-*、A-*、规格场景和状态矩阵、前置条件、测试数据、动作、可观察断言、目标测试定位、聚焦命令、结果、V-* 和证据；不适用字段 MUST 使用合同允许的显式值而不得留空。（D-02、D-04、D-05；A-02）

#### Scenario: 已确认需求形成测试方案

- **WHEN** 用户为已确认需求和已关联活动变更生成测试方案
- **THEN** 每条 TC 都能追溯到该变更适用范围内的决策与验收，并包含可实施或明确人工验证所需的信息

#### Scenario: 用例引入新的业务事实

- **WHEN** TC 的前置、动作或断言依赖需求台账没有确认的行为
- **THEN** 方案保持草稿或阻断并要求先修订需求，不得把该行为直接写入测试

### Requirement: 测试方案必须按阶段确定性校验

系统 MUST 提供 `plan`、`implement` 和 `complete` 三阶段校验，使用稳定英文机器字段、中文诊断和非零失败状态。所有阶段 MUST 拒绝重复或非法 TC、未知或不可执行的 D/A/V 引用、占位字段、越界路径、错误变更、生成测试默认目标及晚于方案基线的需求修订；后续阶段 MUST 在前序结构基础上逐步要求可用测试设施、测试实现、通过结果和持久证据。（D-06、D-10；A-03、A-08）

#### Scenario: 规划方案包含非法输入

- **WHEN** plan 校验发现重复 TC、未知引用、占位值、路径越界或 `.generated.spec.*` 默认目标
- **THEN** 命令返回非零并定位具体用例和字段，且不修改方案、需求或测试文件

#### Scenario: 需求修订晚于方案基线

- **WHEN** implement 或 complete 校验发现需求存在晚于测试方案基线的 R-* 记录
- **THEN** 系统报告方案过期并阻止继续，直到用例重新核对并更新基线

#### Scenario: 完成时仍有未验证用例

- **WHEN** complete 校验发现任一适用 TC 没有通过结果、V-* 或要求的持久证据
- **THEN** 系统阻止完成且不得把未执行、失败或阻断结果改写为通过

### Requirement: 测试实现必须遵循项目原生设施和文件所有权

用户明确要求实现且 implement 校验通过后，系统 MUST 只使用项目已有并有文件证据的测试框架、命令、目录、fixture、mock 与断言模式。系统 MUST 优先扩展同功能手写专用测试，否则创建命名清晰的专用测试；MUST NOT 安装或升级业务依赖、修改业务源码、覆盖未受管测试、弱化已确认断言或默认修改 `.generated.spec.*`。（D-07、D-08、D-13；A-04、A-07）

#### Scenario: 项目已有同功能专用测试

- **WHEN** TC 指向已受 Git 跟踪且覆盖同功能的手写专用测试
- **THEN** 系统在该文件追加对应场景并复用既有测试工具，重复执行不得重复增加同一用例

#### Scenario: 项目没有同功能专用测试

- **WHEN** 项目存在真实测试目录和可用 runner，但没有同功能手写专用测试
- **THEN** 系统创建职责明确的专用测试文件并记录稳定测试定位

#### Scenario: 项目没有可用测试设施

- **WHEN** 上下文检查没有发现可用测试命令、配置或目录证据
- **THEN** 系统只形成明确人工验证方案并阻止自动测试实现与通过结论，不安装依赖或虚构命令

#### Scenario: 测试暴露产品缺陷

- **WHEN** 实现或运行用例发现业务行为不满足已确认断言
- **THEN** 测试入口记录产品缺陷并交回业务变更流程，不自行修改业务源码或降低断言

### Requirement: 聚焦验证必须记录真实结果并保持失败分类

系统 MUST 默认执行测试方案记录的聚焦命令，并 MUST 将结果区分为通过、产品实现缺陷、测试设计错误、测试代码错误、需求歧义、环境或依赖阻塞和历史无关失败。只有真实执行成功且发现计划测试的用例才能关联通过 V-*；零测试发现、非零退出或未执行 MUST NOT 成为通过证据。（D-09；A-05、A-06）

#### Scenario: 聚焦测试真实通过

- **WHEN** 记录的聚焦命令以零状态完成并发现计划用例
- **THEN** 系统记录实际命令、日期、用例定位和结果，并允许把对应 V-* 更新为通过

#### Scenario: 命令没有发现测试

- **WHEN** 聚焦命令成功退出但没有发现计划用例，或 runner 明确报告零测试
- **THEN** 系统将结果记为阻断或测试设施错误，不得生成通过证据

#### Scenario: 全量测试出现无关失败

- **WHEN** 有发布级理由执行全量验证且出现与当前 TC 无关的历史失败
- **THEN** 系统将无关失败与聚焦结果分别报告，不得吞掉失败或用其否定已证明的聚焦断言

### Requirement: 视觉和人工用例必须复用既有证据合同

视觉用例 MUST 引用现有 UI Review 的页面、视口、场景和持久证据；其他无法自动化的人工用例 MUST 记录设备或环境、操作、可观察检查项和证据位置。测试能力 MUST NOT 复制浏览器运行时、视觉比较、自动修复或复验状态机。（D-11；A-09）

#### Scenario: 测试方案包含视觉场景

- **WHEN** TC 的可观察结果依赖布局、颜色、像素或复杂交互视觉状态
- **THEN** 用例引用既有 UI Review 场景与 V-* 证据，而不是生成第二套浏览器配置或截图比较流程

#### Scenario: 场景只能人工验证

- **WHEN** 项目没有可执行自动化入口且人工验证仍能观察确认行为
- **THEN** TC 明确记录环境、操作、检查项和证据位置，未取得证据前保持未通过

### Requirement: 首版兼容声明必须由真实 fixture 证明

首版 MUST 在 Vue 3 + Vite + Vitest fixture 上证明上下文识别、方案校验、专用测试定位、真实聚焦执行、零测试失败和重复执行稳定性。其他 runner MAY 按项目已有模式使用，但系统 MUST NOT 在没有对应 fixture 或外部证据时声明完整兼容；开发验证依赖、锁文件和缓存 MUST 只按需位于 `outputs/frontend-test-runtime/`，不得进入项目根目录、插件运行时或业务项目，并在验证结束后清理。（D-12、D-14；A-05、A-10）

#### Scenario: Vue Vitest fixture 完成闭环

- **WHEN** 仓库执行测试用例工作流专用验证
- **THEN** fixture 的 Vitest 命令真实发现并通过计划 TC，重复执行保持方案和测试定位稳定

#### Scenario: 遇到未认证 runner

- **WHEN** 项目使用首版没有完整兼容证据的测试 runner
- **THEN** 系统只依据项目现有文件提供有限支持并披露未认证边界，不安装替代框架或声称完整支持
