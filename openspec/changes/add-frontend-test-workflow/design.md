## Context

参见 `proposal.md`。当前仓库已有需求 D/A/V 校验、测试文件 Git 基线、项目命令识别、OpenSpec 变更状态和完成硬门禁，但没有逐用例测试方案或独立测试入口。实现必须保持历史需求与既有变更兼容、默认只读、目标路径安全、生产脚本零第三方依赖，并避免与 UI Review 的浏览器与证据状态机重复。（D-02、D-06、D-08、D-11、D-14）

## Goals / Non-Goals

**Goals:**

- 用一个公共 Skill 覆盖分析、方案、实现和验证意图，同时复用现有需求与变更生命周期。（D-01～D-03）
- 用人类可审查、机器可确定解析的 Markdown 合同承载 `TC-*`，并能在三个阶段逐步收紧门禁。（D-04～D-06、D-10）
- 将测试文件所有权、项目原生设施、结果分类、视觉交接和完成证据接入现有工作流。（D-07～D-11）
- 用 `outputs/frontend-test-runtime/` 中按需准备的真实 Vitest 取得 Vue 3 + Vite fixture 证据，同时不把该依赖带入项目根目录、插件运行时或业务项目。（D-12、D-14）

**Non-Goals:**

- 不构建框架模板生成器、测试管理服务、覆盖率或 Mutation 平台。
- 不让确定性脚本生成任意业务测试代码；测试代码仍由 AI 按 Skill 和项目事实实现。
- 不在测试入口内修改业务源码、安装业务依赖或复制 UI Review 运行时。（D-07、D-08、D-11、D-13）

## Decisions

### 1. 使用严格 Markdown 字段而不是 JSON 或自由表格

`test-plan.md` 使用固定二级区块和 `### TC-01：名称` 用例块。基本信息记录状态、需求、变更、需求修订基线和默认聚焦命令；每个 TC 使用单行字段记录状态、优先级、验证类型、层级、D/A/规格/矩阵来源、前置、数据、替身、动作、可观察断言、目标测试、测试定位、聚焦命令、V-*、结果分类和证据。

选择逐用例字段是因为命令、路径和断言经常包含标点，Markdown 表格容易被竖线或长文本破坏；JSON 虽易解析，但不利于产品、开发和测试共同审查。解析器只接受模板声明的简单格式，不尝试成为通用 Markdown 解析器。（D-04、D-05；A-02）

备选方案是在需求文档中直接扩展 TC 表格，但会让业务事实源混入大量技术测试定位，并使活动变更归档后难以保留当时的实现选择，因此不采用。

### 2. 用变更元数据显式启用测试方案门禁

`.openspec.yaml` 增加可选稳定字段 `test_plan: required`。只有该字段存在时，实施检查和完成入口才要求 `<change-root>/test-plan.md` 并运行相应阶段校验；缺少字段的历史变更保持原行为。`$frontend-test` 持久化方案时写入该字段，但不得覆盖其他元数据。（D-02、D-04、D-06；A-02、A-03、A-08）

备选方案是只根据文件是否存在启用门禁，但误删文件会让门禁静默消失；对所有活动变更强制要求则会误伤历史与纯文档变更。

### 3. 将确定性上下文与 AI 测试实现分离

`inspect-test-context.mjs` 只读复用项目识别结果，并在有界范围内补充测试配置、目录、测试文件、生成基线、Git 跟踪和可用命令证据。它输出稳定 JSON，不执行测试、不安装依赖、不推断产品行为。`frontend-test/SKILL.md` 负责读取需求、源码和既有测试后形成用例，并在明确授权时按项目模式编辑测试代码。（D-03、D-07、D-08；A-01、A-04、A-07）

备选方案是让脚本按 runner 模板直接生成测试代码，但跨框架差异会使首版产生脆弱或虚假测试，因此不采用。

### 4. 三阶段校验共享一个解析结果

`validate-test-plan.mjs` 先规范化需求、变更和计划路径，确认它们属于同一项目与活动变更，再解析需求中的可执行 D/A、最新 R-*、V-* 和变更范围。公共结构错误在所有阶段失败：TC 唯一、必需字段、引用、路径与生成测试保护。

- `plan`：要求方案事实完整、来源有效、目标安全，允许测试尚未实现和结果为计划。
- `implement`：额外要求方案就绪、自动 TC 有可用测试上下文、目标与聚焦命令，需求状态为已确认或实施中且修订基线最新。
- `complete`：额外要求方案已验证，全部适用 TC 为通过或人工通过，目标测试、V-* 和可识别持久证据存在。

机器输出包含 `ok`、`stage`、`planStatus`、`stale`、`caseCount`、`automaticCases`、`manualCases`、`errors` 和 `warnings`；CLI 错误使用中文。（D-05、D-06、D-09、D-10；A-03、A-06、A-08）

### 5. 需求修订采用保守的最新 R 基线

方案记录生成时需求中的最新 `R-*`。后续出现更大编号的修订时，implement 与 complete 全方案阻断；AI 必须重新检查所有适用 TC 后更新基线。首版不尝试从修订文本自动判断某个 TC 是否受影响，避免错误保留旧断言。（D-10；A-08）

备选方案是为每个 TC 计算 D/A 内容哈希，但会引入规范化和历史格式兼容复杂度，留待后续评估。

### 6. 聚焦执行由 Skill 使用项目现有命令

首版不新增通用测试子进程包装器。Skill 根据测试上下文和方案执行已记录命令，要求实际退出状态与用例发现证据，并把失败分类写回计划和需求 V-*。默认聚焦与全量升级继续沿用现有需求规则；完成门禁只消费已经持久化的结果，不重新运行外部命令。（D-08、D-09；A-05、A-06）

该选择避免脚本解释任意包管理器 shell 语义或扩大命令执行权限。零测试发现通过 fixture 和 Skill 规则作为明确阻断。

### 7. 视觉用例只保存交接引用

TC 的验证类型为视觉时，方案记录现有 UI Review 场景、视口和 V-* 证据位置；校验器不启动浏览器、不比较图片、不修复源码。人工用例使用相同的环境、检查项和持久证据要求。（D-11；A-09）

### 8. Vitest 仅作为 outputs 内的按需验证运行时

根 `package.json` 不声明 Vitest，也不生成根锁文件。`npm run prepare:test-runtime` 使用 Node.js 标准库包装 npm，把固定版本 Vitest、锁文件与下载缓存全部限制在被定向忽略的 `outputs/frontend-test-runtime/`；专用 Node 测试只从该目录调用 Vitest，对 fixture 中带 `TC-*` 标题的专用测试执行真实聚焦验证，并断言根 `node_modules` 不存在验证专用 Vitest。`npm run verify` 将跨平台临时目录定向到 `outputs/verify-runtime/tmp` 并按最外层所有权自动回收，验证结束后由 `npm run cleanup:test-runtime` 删除 Vitest 输出子目录；插件发布结构、业务 fixture 和业务项目不执行或携带该安装。（D-12、D-14；A-05、A-10）

## Risks / Trade-offs

- [Markdown 解析规则过严，人工编辑容易失败] → 模板、中文字段级错误和 `--json` 同时提供，解析器只约束作为机器合同的字段。（D-05、D-06）
- [完整 R-* 基线会让无关修订也使方案过期] → 首版选择安全优先并输出当前/计划基线，后续再评估逐用例哈希。（D-10）
- [AI 可能生成实现细节或弱断言] → Skill 要求可观察断言、D/A 来源和产品缺陷交接；校验器不把文件存在视为通过。（D-05、D-07、D-09）
- [新增完成门禁误伤历史变更] → 只在 `test_plan: required` 时启用，缺少声明保持兼容。（D-02、D-06）
- [Vitest 增加开发安装体积或污染根目录] → 只按需安装在被定向忽略的 `outputs/frontend-test-runtime/`，验证后清理；不进入根依赖、插件成品或业务项目。（D-12、D-14）
- [未认证 runner 的执行输出差异] → 首版只正式声明 Vitest fixture，其他 runner 披露有限支持并依赖项目证据。（D-12）

## Migration Plan

1. 先新增模板、规则、上下文识别、方案解析与专用测试，不修改既有变更完成语义。
2. 新增 `$frontend-test`，并在本变更内建立首份 `test-plan.md` 自举验证。
3. 以可选元数据接入 `$frontend-change`、检查和完成入口；验证没有声明的历史 fixture 保持兼容。
4. 同步 0.15.0 版本、README、manifest、结构门禁和公开 Skill 清单，执行专用与全量验证。
5. 回滚时移除新 Skill、脚本、模板和可选门禁；已有历史变更与业务项目测试不需要迁移。
