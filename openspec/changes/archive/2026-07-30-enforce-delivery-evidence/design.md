## Context

当前项目检查器按脚本名称选择第一个匹配项，`build` 优先于 `build:prod`，并将任何名为 `lint` 的脚本视为 lint。需求决策校验器只校验 D/A 引用结构；需求模板没有可解析的实际验证记录，变更完成规则也没有在同步和归档前运行交付门槛校验。

四个真实项目证明这些机制需要保持兼容地扩展：旧版 BRM 仍应得到迁移提醒，KAM 的完整新版资料不应被误报，体检项目要区分默认与生产构建，医生工作台要暴露未完成的构建、人工验证和错误的测试复用声明。

## Goals / Non-Goals

**Goals:**

- 让项目检查报告同时表达脚本名称、命令和语义可信度，且保持现有字段可用。
- 让新需求能够结构化记录状态、实际自动验证和人工视觉验证。
- 让完成阶段只在所有可交付条件真实满足时同步规格和归档。
- 在可用 Git 基线下检查“新建 / 复用”测试文件策略，并在没有基线时诚实降级。

**Non-Goals:**

- 不执行用户项目的命令、浏览器或截图，也不判断自定义脚本的真实运行结果。
- 不自动重写旧需求，或要求旧需求在日常状态检查时迁移到新表格。
- 不以自然语言静态分析代替业务评审、代码审查或人工视觉判断。

## Decisions

### 兼容扩展命令语义报告

- **决策**：保留 `inspection.scriptNames.build` 和 `inspection.commands.build` 的现有选择逻辑；新增 `commandSemantics`，其中默认构建优先 `build`，交付构建优先 `build:prod`、`build:production`、`build:release`，没有显式交付脚本时回退默认构建。lint 保留现有命令字段，并以 `verified`、`unverified` 或 `missing` 报告语义状态。
- **依据**：调用方仍可依赖旧字段；新字段可避免把裸 `build` 或 `vite optimize` 夸大为生产构建或 lint。
- **替代方案**：替换 `commands.build` 的选择结果。该方案会破坏既有 AGENTS、检查输出与调用方，不采用。

### 采用保守的 lint 静态识别

- **决策**：只把直接包含已识别 lint 工具或项目已知 lint 子命令的脚本标记为 `verified`；脚本存在但无法识别时标记 `unverified` 并给出中文警告；没有脚本时标记 `missing`。
- **依据**：未知 Node 包装脚本不能被静态证明无效，但也不能被误报为 lint。
- **替代方案**：维护任意 shell 命令的白名单或把所有 `lint` 脚本视为有效。前者不可维护，后者已在医生项目中产生错误结论，均不采用。

### 在单份需求中记录验证状态与证据

- **决策**：新模板增加受控需求状态、`验证记录` 表和验收映射中的 `验证记录` 引用。验证记录包含稳定 `V-*` ID、验证类型、命令或人工环境、日期、结果及证据位置。人工记录必须表达视口或设备环境、检查项和截图或录屏位置。
- **依据**：不创建额外管理文件，仍使一个需求文件同时服务人工评审和确定性校验。
- **替代方案**：将终端输出写入新日志文件。它会增加管理文件并与现有验收映射分离，不采用。

### 为校验器增加阶段化严格度

- **决策**：`validate-requirement-decisions.mjs` 新增 `--stage plan|implement|complete`，默认为 `plan`。计划和实施阶段继续支持旧六列表映射；完成阶段要求新结构、状态为“已验收”、所有 A-* 和任务勾选完成、映射关联的 V-* 均为“通过”。
- **依据**：旧项目可以继续进行非完成阶段的读取和修订；新变更只有真正具备交付证据时才进入不可逆的同步/归档动作。
- **替代方案**：所有阶段都强制迁移旧需求。它会违反插件不覆盖业务项目内容和渐进迁移原则，不采用。

### 用 Git 索引提供测试文件基线

- **决策**：解析新模板的测试文件策略。策略为“复用”时，目标必须存在；若仓库具有 Git 索引，目标必须已受版本控制。策略为“新建”时，规划阶段不得指向已受版本控制的同职责测试。没有可用 Git 基线时保留校验通过并返回中文降级警告；完成阶段仍要求目标文件存在。
- **依据**：这能够识别“新建文件误写为复用”，又不把尚未提交的初始化仓库误判为错误。
- **替代方案**：始终要求 Git 历史。非 Git 项目或首次初始化项目无法使用，不采用。

### 在完成入口先校验，再同步和归档

- **决策**：变更技能的 Complete 阶段先运行 `--stage complete`，只有通过后才读取同步/归档指引并执行后续动作；实施前使用 `--stage implement`。
- **依据**：把交付门槛放在唯一的完成入口，避免文档文本与归档状态脱节。
- **替代方案**：只更新提示词要求人工确认。既有试运行已证明提示词不足以稳定阻断，不采用。

## Risks / Trade-offs

- [自定义 lint 包装器被报告为语义未验证] → 保留命令、说明原因并允许项目规则提供可追溯确认，不将其报为缺失。
- [旧需求无法直接完成] → 默认计划/实施校验保持兼容，完成时给出明确的升级缺项而不自动改写。
- [验证记录被手工伪造] → 插件只能验证结构与完成阶段实际执行的命令；最终证据仍接受人工审查，不夸大为自动真实性证明。
- [Git 工作区没有已提交基线] → 返回降级警告而非阻断；完成阶段仍核验目标文件存在。

## Migration Plan

1. 先扩展检测与校验 JSON，保留所有旧字段与默认入口。
2. 更新模板、规则和技能，让新需求从创建起使用验证记录和五状态模型。
3. 在 Complete 阶段接入严格校验；旧需求只会在请求完成时被报告缺项，不被自动修改。
4. 为多构建、非 lint、旧格式、Git 与无 Git 基线、人工视觉证据以及完成阻断添加 fixture。
5. 如需回滚，移除新阶段调用和新增字段读取；旧 `commands` 与默认需求校验保持不变。

## Open Questions

- 无。任意自定义 lint 包装器的运行真实性仍由项目规则或人工确认，插件只报告静态语义可信度。
