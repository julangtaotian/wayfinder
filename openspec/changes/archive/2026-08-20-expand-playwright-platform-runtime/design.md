## Context

参见 `proposal.md`。共享 Playwright 1.62.1 运行时与五个平台资产已经分离，`playwright-runtime.mjs` 负责平台选择和完整性，`build-playwright-platform.mjs` 负责维护规范源资产，五个平台也已经取得原生真实启动证据。当前问题转为发布边界：本地 marketplace 直接复制整个插件源目录，导致五套平台资产同时进入安装缓存，成品约 1.38 GB；Linux ARM64 的 Chromium headless shell 规范源还是带调试符号的 ELF，单文件约 300 MiB。

约束来自 REQ-2026-020 D-08、D-10、D-13、D-16：目标项目零安装、运行阶段零下载、平台资产独立、固定 Playwright 版本、许可和摘要必须校验，且支持结论必须来自对应原生环境。新发布过程还必须默认预览、拒绝危险路径和覆盖，只修改暂存副本，并在体积预算上保留约 10% 余量。

## Goals / Non-Goals

**Goals:**

- 用一个稳定的平台描述表驱动支持列表与构建主机映射，避免多处平台集合漂移。
- 新增 `darwin-x64`、`linux-arm64`、`win32-x64` 独立运行包，同时保持现有两平台元数据兼容。
- 让结构校验、完整性生成、专用测试和 CI 从同一五平台集合得出结论。
- 在五个平台的原生 GitHub Runner 上执行相同的真实 Chromium 冒烟。
- 用确定性的单平台暂存入口生成可安装成品，完整保留共享插件能力但排除其他四个平台资产。
- 为每个平台成品执行结构、完整性、体积预算和原生浏览器门禁，并让本机 marketplace 可从匹配成品重装。
- 只在 Linux ARM64 原生构建阶段对暂存 Chromium 去除调试符号，规范源资产和其他平台构建保持字节不变。

**Non-Goals:**

- 不支持 Windows ARM64、Linux ARM32、其他浏览器或运行时按需下载。
- 不修改 UI Review 配置、状态、适配器、比较器或自动修复合同。
- 不把多个平台浏览器合并为一个可互相回退的通用目录。
- 不删除 Chromium/FFmpeg 许可、FFmpeg 或完整性清单，不把浏览器改为安装后下载。
- 不把暂存成品或构建日志提交为规范源，不在 macOS、Windows 或 Linux x64 上交叉修改 Linux ARM64 二进制。

## Decisions

### Linux ARM64 授权文件补齐

Playwright 的 Linux ARM64 Chromium headless shell 压缩包不包含授权文本。构建器必须从仓库内同版本的 Linux x64 运行包复制通用 `LICENSE.headless_shell` 到 Linux ARM64 独立目录，再执行完整性校验；缺少来源文件时构建失败并回滚，不允许发布缺少授权文件的平台包。

### 1. 以 Node 平台键作为唯一公共标识

公共索引继续使用 `${process.platform}-${process.arch}`，本轮固定为五个键：`darwin-arm64`、`darwin-x64`、`linux-x64`、`linux-arm64`、`win32-x64`。构建脚本在内部把它们分别映射到 Playwright 1.62.1 的 `mac15-arm64`、`mac15`、`ubuntu24.04-x64`、`ubuntu24.04-arm64`、`win64`。

选择该方案是因为运行时无需理解 Playwright 私有主机命名，也不会把 Windows 的 Node 标识误写成 `win64`。备选方案是在元数据中直接公开 Playwright 主机名，但会让运行时合同依赖上游内部命名。

### 2. 平台元数据与完整性清单继续逐包落盘

每个平台保留 `platforms/<key>.json`、`platform-assets/<key>/.local-browsers/` 和 `integrity/<key>.json` 三部分。新增元数据明确记录 Chromium headless shell 与 FFmpeg 的平台原生相对路径；完整性生成遍历全部五个平台，不把某个平台文件计入共享清单。

选择逐包清单是为了延续缺包、混装和摘要变化的失败关闭语义。备选方案是单一总清单，虽然文件更少，但无法清晰归因平台污染，也不利于后续拆分发布。

### 3. 构建命令保持预览优先并禁止覆盖

`build-playwright-platform.mjs --platform <key>` 继续只输出计划；只有 `--write` 才下载到临时目录，成功后原子移动并重建完整性清单。平台描述表提供主机覆盖值，现有最终目录仍禁止覆盖，失败只清理当前临时目录。

选择延续现有维护入口可保持发布过程可审查。备选方案是 CI 每次动态下载浏览器，但这违反运行阶段零下载和发布物自包含要求。

### 4. CI 使用五项原生 Runner 矩阵

验证矩阵使用 `macos-15`、`macos-15-intel`、`ubuntu-24.04`、`ubuntu-24.04-arm`、`windows-2025`，分别设置期望平台键。每项检出 Git LFS 资产、安装固定 Node 20.19.0，并运行统一验证；平台测试必须断言当前键受支持且 `smoke.skipped === false`。

选择原生 Runner 是因为交叉下载只能证明资产存在，不能证明操作系统装载器、权限和动态库满足真实启动。备选方案是在单一 Mac 上只做完整性检查，不能满足五平台支持证据。

### 5. 专用平台测试由集合驱动

继续复用 `tests/ui-review-platform-runtime.test.mjs`。fixture 为五个平台生成最小独立资产，断言共享清单不包含平台文件、每个平台只能引用自身目录、所有清单都能验证，并保留缺包、混装、摘要变化和未支持平台测试；真实浏览器测试只启动当前原生平台包。

### 6. Windows 原生验证保持文本、路径和测试进程可移植

仓库文本统一以 LF 检出，Playwright 的 LFS 平台资产继续显式使用 `-text`，避免 Windows 自动转换内置运行时文本后触发完整性误报。传给 Git pathspec 和诊断信息的仓库相对路径统一使用正斜杠；需要模拟 FFmpeg 的测试通过 Node 可执行文件加脚本参数启动，不依赖 Windows 不支持的 shebang 执行语义。

这些调整只修正原生验证基础设施，不改变 UI Review 的配置、运行结果或平台支持范围。继续保留字节级完整性校验，不在运行时对已检出的文件进行换行归一化，以免掩盖真实篡改。跨平台测试在比较 OpenSpec 返回的原生路径前统一路径分隔符，但不改写运行时实际输出。

### 7. Windows 运行副作用与规范路径采用精确兼容

Windows Chromium 首次启动会在浏览器可执行文件旁生成 `debug.log`。完整性遍历只排除 `win32-x64` 元数据所指可执行文件同目录下的这一条固定路径；其他日志、缓存或新增文件继续按未登记文件阻塞，避免把宽泛忽略规则变成完整性漏洞。

OpenSpec 1.8 会把规划根规范化为文件系统真实路径。完成门禁比较项目根时同步使用原生真实路径，并仅在 Windows 上折叠大小写，兼容盘符大小写、短路径别名和规范化结果差异；`global_default` 与真实跨目录结果仍然阻塞。

### 8. 区分五平台规范源与单平台可安装成品

仓库中的 `plugins/frontend-ai-workflow` 继续作为五个平台规范源，保留全部 LFS 资产，供维护、完整性重建和跨平台 CI 使用。新增 `package-plugin-platform.mjs` 从规范源生成一个独立 marketplace 暂存根，其中只包含当前平台插件成品和由脚本生成的 marketplace 描述；暂存根不进入 Git 跟踪。

选择生成独立 marketplace 根而不是修改仓库 `.agents/plugins/marketplace.json`，是为了让本地开发入口继续指向规范源，同时允许 Codex 通过命令注册并安装瘦身成品。备选方案是把五个平台发布为五份长期复制的源码目录，会重复共享文件并让版本同步容易漂移；直接修改现有 marketplace 又会破坏开发校验和其他平台检出。

### 9. 发布入口默认预览，并采用允许根、全新目录和原子发布

发布入口接受稳定英文参数 `--platform`、`--output`、`--write`。未提供 `--write` 时只返回计划；写入时目标平台必须等于当前原生 `${process.platform}-${process.arch}`，输出必须位于仓库 `dist/` 或系统临时目录内，且最终目录不得已存在。根目录、用户主目录、仓库根、插件源目录、符号链接逃逸和未知平台全部拒绝。

脚本先写入同一父目录下的进程级临时目录，完成复制、裁剪、摘要、结构、体积和原生冒烟后才原子改名为最终目录；失败时只清理自己创建的临时目录。这样既延续仓库“预览优先、显式写入”合同，也不会覆盖用户已有文件。

### 10. 成品通过分发描述切换结构校验模式

平台成品在 `runtime/playwright/distribution.json` 写入固定 schema、`kind: platform`、目标平台键、排除平台、体积预算和是否去符号。规范源没有该描述，结构校验继续要求五套元数据、清单和资产并执行 `verifyAllPlatforms: true`；成品模式只要求描述的平台元数据、资产和清单，同时显式确认其他四个平台三类文件均不存在。

分发描述位于 Playwright 运行时内，因此生成后必须重建共享清单与目标平台清单，不能把它当作未校验旁路文件。运行时公共支持列表仍保留五个平台键；当前安装包与主机不匹配时，在读取浏览器前就以中文原因阻塞。

### 11. 体积使用逻辑字节计量并保留平台余量

成品体积以插件目录内普通文件大小与符号链接目标字节数之和计量，避免不同文件系统分配块造成 CI 漂移。预算固定为：`darwin-arm64=260 MiB`、`darwin-x64=260 MiB`、`linux-x64=330 MiB`、`linux-arm64=420 MiB`、`win32-x64=340 MiB`。这些门槛均高于当前单平台估算并保留约 10% 余量，同时保证最差平台相对约 1.38 GB 安装副本仍减少约 70%。

发布结果必须同时输出 `sizeBytes`、`budgetBytes` 和 `headroomBytes`；小于等于预算才允许原子发布。许可、FFmpeg、共享 Playwright、OpenSpec、Skills、脚本和目标平台完整性不能作为可裁剪项，后续新增共享能力如果侵占余量会在发布阶段提前失败。

### 12. Linux ARM64 只在原生暂存副本去除调试符号

目标和当前平台均为 `linux-arm64` 时，脚本在复制完成后对元数据指向的 Chromium headless shell 暂存副本执行原生 `strip --strip-debug`，再用 `readelf` 确认不存在 `.debug_*` 段。执行前后记录暂存文件大小，并对规范源文件计算摘要，发布结束后再次确认源摘要未变。

任何命令缺失、非零退出、调试段残留、文件没有缩小、规范源摘要变化、完整性或 Chromium 冒烟失败都会阻止发布。其他平台不运行这一步；不允许通过主机覆盖值在非 ARM64 环境交叉改写二进制。去符号后重新生成成品 SHA-256 清单，因此运行时仍保持字节级验证。

### 13. 五平台 CI 验证成品，本机从生成 marketplace 重装

现有五平台矩阵在规范源全量验证后，各自生成当前平台 marketplace 成品，对成品执行仓库确定性结构校验、体积门禁和真实 Chromium 截图，并上传成品或体积报告作为证据。Linux ARM64 额外断言 `stripped: true` 和调试段检查结果；所有平台都必须证明其他四个平台资产不存在。Codex 官方 Plugin validator 由本地规范源与当前平台真实成品门禁执行，因为公共 GitHub Runner 不携带 Codex 插件开发环境，CI 不为此临时联网安装外部校验依赖。

本地完成后先使用插件开发工具更新规范源 manifest 的单一 cachebuster，再生成 `darwin-arm64` 成品，并对规范源和成品分别运行 Codex 官方 Plugin validator。通过 Codex CLI 注册脚本生成的本地 marketplace 并从该 marketplace 重装，不手改个人或仓库 marketplace；安装缓存再次检查分发描述、逻辑体积、完整性和真实启动。新任务用于加载更新后的 Skill 与工具。

## Risks / Trade-offs

- [仓库检出仍包含五个平台 LFS 资产，开发目录不会随安装包一起降到单平台大小] → 本轮优化安装缓存与发布下载边界，规范源继续保留五平台可复现资产；开发机磁盘另通过 Git LFS 拉取策略处理，不把它与插件运行期合同混在一起。
- [暂存复制过程如果路径或清理范围错误可能覆盖用户文件] → 只允许 `dist/` 或系统临时目录下的全新目标，使用独立临时目录和最终原子改名，任何清理都限定为脚本本次创建的精确路径。
- [双结构模式可能让规范源漏资产或成品混入其他平台文件] → 使用受校验的 `distribution.json` 明确模式；规范源仍验证全部五平台，成品必须验证目标平台存在且其余四平台三类资产全部不存在。
- [Linux ARM64 去符号可能破坏浏览器或因工具差异产生不可复现结果] → 只用固定原生 Runner 工具处理暂存副本，检查调试段、源摘要和文件缩减，随后重建完整性并真实截图；任一步失败不发布。
- [体积预算过紧会随共享功能增长产生误报，过松则失去优化约束] → 以当前单平台估算上浮约 10% 固化预算并报告剩余余量，后续扩大预算必须回到需求决策而不是静默调整。
- [Linux ARM64 GitHub Runner 仍处于公开预览，可能出现容量或镜像波动] → 固定 `ubuntu-24.04-arm` 并把基础设施故障与产品测试失败分开报告，不以跳过替代证据。
- [Windows 路径分隔符与 `.exe` 命名不同] → 元数据统一使用 POSIX 相对路径，运行时现有安全路径函数负责转换；新增 Windows fixture 和原生冒烟共同验证。
- [Windows Chromium 启动后产生诊断日志] → 只按元数据计算并排除可执行文件旁的固定 `debug.log`，专用测试同时证明任意其他新增文件仍被阻止。
- [交叉下载成功但平台资产目录结构发生上游变化] → 构建后立即按元数据检查浏览器、FFmpeg 和许可路径，再生成清单；路径变化会阻塞而不是发布不完整包。
- [五平台全量完整性遍历耗时增加] → 保留共享与平台分片清单；后续若需要拆分发布，可在不改变运行时平台键的前提下按包分发。

## Migration Plan

1. 先扩展专用平台测试，固定预览零写入、安全路径、拒绝覆盖、单平台保留、其他平台排除、体积和失败清理合同。
2. 实现分发描述、双结构校验与平台 marketplace 暂存入口；先在本机预览，再生成 `darwin-arm64` 成品并验证逻辑体积、完整性和真实截图。
3. 在 Linux ARM64 原生路径实现暂存副本去符号、调试段检查、源摘要保护和失败回滚，不改动现有 LFS 规范源二进制。
4. 扩展五平台 CI，使每个 Runner 都在规范源全量门禁后生成并验证自身成品，收集 `platformKey`、成品字节、预算余量、`stripped` 与截图字节数。
5. 使用插件开发工具更新单一 cachebuster，从生成的 `darwin-arm64` 本地 marketplace 重装，复核安装缓存体积、完整性与 Chromium；全部证据写入 V-18 后关闭 A-07、A-10、A-12、A-14。

回滚时移除平台成品暂存入口和分发描述识别，恢复从五平台规范源直接安装；不得删除现有平台源资产、完整性清单或把运行期下载作为回退。已生成的暂存 marketplace 可以精确移除，不影响仓库 marketplace 和历史运行状态。
