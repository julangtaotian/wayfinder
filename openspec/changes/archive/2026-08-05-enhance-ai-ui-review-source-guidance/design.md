## Context

现有生成器将结构化问题标准化后同时驱动截图标注和 Markdown 输出。DOM 选择器足以连接截图与页面，但不能唯一确定仓库内的样式声明；同名 `.el-button` 规则在组件库依赖、全局主题和场景样式中均可能存在。参见 `proposal.md` 与新增规格。

## Goals / Non-Goals

**Goals:**

- 让每条问题形成“DOM → 源码锚点 → 安全修改边界 → 复验”的闭环。
- 在输入标准化阶段阻止危险路径和不完整指导进入交付报告。
- 保持两个固定交付文件以及现有截图编号合同不变。

**Non-Goals:**

- 不根据报告自动修改源码，也不生成可直接应用的补丁文件。
- 不依赖易漂移的源码行号或 Source Map。
- 不修改两套组件库验收项目的真实 UI。

## Decisions

### 使用结构化嵌套字段承载修复上下文

每个 finding 新增 `sourceTarget`、`changeScope`、`forbiddenChanges`、`suggestedPatch` 和 `verification`。`sourceTarget` 包含仓库相对 `file`、稳定 `anchor` 与 `styleSource`；`verification` 包含 `workingDirectory`、非空 `commands`、`page` 和非空 `assertions`。

选择嵌套结构是为了把源码定位与复验职责分开，并让输入校验能逐字段给出中文错误。相比把全部信息拼进原有 `fix` 文本，这种方式更适合 AI 稳定解析，也避免遗漏关键边界。[D-09]

### 路径只允许规范化的仓库相对形式

生成器拒绝绝对路径、空路径、`.`、`..` 路径段和反斜杠，并把合法路径统一为正斜杠形式。生成器不强制目标文件在当前工具进程中存在，因为报告可能在独立采集环境生成；实际文件存在性由本轮人工复核和后续 AI 修复前检查负责。

相比仅做字符串非空校验，该限制能阻止报告把 AI 引导到仓库外部；相比强制本机文件存在，它保留跨工作区生成报告的能力。[D-09]

### 同节点合并必须保持修复目标一致

现有逻辑会合并相同 DOM 选择器的关联差异。若待合并问题的源码文件、稳定锚点、修改作用域、禁止范围或复验上下文不一致，生成器直接拒绝输入，而不是把多个修复目标拼成含糊文本。只有修复目标一致的问题才合并问题描述和值。

### Markdown 使用稳定字段顺序

每条问题先输出页面与视觉证据，再输出“源码修复指导”子段，最后输出“修复后复验”子段。命令和断言逐条列出，使人和 AI 都能直接执行；行号可以出现在说明文字中，但不能替代源码文件与锚点。

## Risks / Trade-offs

- [AI 提供了错误但格式合法的源码映射] → 报告保留 DOM、截图坐标和样式来源供复核；本轮对两套真实报告执行人工文件与锚点检查。
- [同一 DOM 的多个问题实际需要不同源码规则] → 不自动合并不一致的修复目标，要求 AI 拆分选择器或重新整理结论。
- [复验命令依赖本地环境] → 同时记录工作目录、页面和样式断言，命令不可运行时仍可按页面断言人工复核。

## Migration Plan

1. 扩展标准化输入与 Markdown 渲染测试。
2. 更新生成器校验与渲染逻辑。
3. 为两份现有按钮行高报告补充各自真实源码映射和复验步骤，PNG 保持不变。
4. 聚焦测试通过后核对每个项目目录仍只有两个文件；失败时回退新增字段和两份 Markdown，不触碰页面源码。
