## Context

动机见 `proposal.md`，外部行为合同见 `specs/fast-change-routing/spec.md`。旧实现把快速分支直接放进 `frontend-change`，因此简单修改仍要加载完整 Skill，而原本“新请求默认 Plan”的状态规则也被改写。官方 Skill 机制先暴露名称和描述、选择后才加载正文，因此把单一职责拆成独立 Skill 才能真正减少上下文，同时通过互斥描述完成自然语言路由。（D-01、D-06、D-07；A-01、A-04、A-05）

实现不新增运行时分类器或依赖。业务影响是否局部仍需读取当前仓库事实，但快速 Skill 只做最低必要检查；发现实质边界时把已完成工作交给原 `frontend-change`，而不是在两个 Skill 中各走一遍。（D-02～D-05；A-02、A-03）

## Goals / Non-Goals

**Goals:**

- 让明确局部实施请求直接选择短小、独立的快速 Skill，不先加载需求和 OpenSpec 流程。（D-01、D-02；A-01）
- 允许同一局部调用链的必要扩展，用实质风险而非文件路径、数量或行数决定是否交接。（D-03；A-02、A-03）
- 只交接一次并复用调查、修改和验证，保证快速失败不会变成重复工作。（D-04；A-02）
- 恢复并用测试锁定 `frontend-change` 原有完整生命周期。（D-06、D-07；A-04、A-05）

**Non-Goals:**

- 不用文件数、代码行数、目录关键词、置信度分值或脚本风险评分代替仓库事实。（D-02、D-03）
- 不设计“轻量规划”或第二套 OpenSpec 生命周期；需要管理的任务直接交给原完整流程。（D-04、D-06）
- 不修改需求校验器、OpenSpec 运行时、完成门禁、发布流程或外部授权。（D-05、D-06）

## Decisions

### 1. 使用独立 Skill 获得真正的渐进披露

新增 `frontend-fast-change`，用聚焦描述负责隐式选择；`frontend-change` 恢复原描述与正文。只有选中快速能力后才加载短合同，简单任务不再支付完整变更生命周期的上下文成本。（D-01、D-06、D-07；A-01、A-04、A-05）

备选方案是继续在 `frontend-change` 内保留 Fast Path。它只有一个入口，无法在加载前减少完整 Skill 上下文，并会持续耦合两个状态机，因此不采用。

### 2. 准入只检查五个最低事实，升级只看实质影响

最低事实是明确实施意图、已决定结果、局部影响、可行聚焦验证和无匹配活动变更。检查不设置文件数量上限，也不把路由、共享组件等目录名直接等同于风险；只有实际改变共享/公开契约或工程基础设施时交接。（D-02、D-03；A-01～A-03）

备选方案是维护长关键词黑名单。它会误伤安全的小改动，也会漏掉路径普通但语义高风险的变化，不符合快速通道初衷。

### 3. 单次交接复用已经完成的安全工作

轻量检查先解析活动变更，再读取相关源码、必要调用方和邻近测试。出现升级项时停止扩张，保留用户改动与安全工作，并把触发原因、文件、证据和验证一次性交给 `frontend-change`；交接后快速 Skill 不再继续。（D-03、D-04；A-02）

备选方案是交接后让完整流程从头探索。它虽然简单，却把快速通道的前置成本全部浪费并造成重复修改，因此不采用。

### 4. 验证按结果证明而不是流程清单扩张

优先运行覆盖目标行为的单测、邻近测试或项目原生检查；没有自动证据时做明确人工检查。只有聚焦验证不可用、共享链路要求或用户明确要求才扩大范围。完成报告保持短小、真实，不自动执行 Git 或发布动作。（D-04、D-05；A-01、A-03）

备选方案一是所有快速任务跑全量验证，会抵消速度；备选方案二是无验证直接完成，会失去开发者可信度，均不采用。

### 5. 公共资产只放路由，完整合同由独立 Skill 持有

受管 `AGENTS.md` 只说明何时选 `$frontend-fast-change`、何时使用 `$frontend-change`；需求规则与 README 解释职责和示例。专用测试检查关键不变量，不要求逐字复制 Skill。公开 fixture 加入新 Skill，确保打包和初始化相关测试能发现遗漏。（D-07；A-05）

这样减少维护漂移，也避免每个项目的 AGENTS 长期携带完整快速合同。备选方案是在四处复制完整清单，修改成本和语义漂移都更高，因此不采用。

## Risks / Trade-offs

- [两个描述重叠导致误选] → 快速描述只覆盖结果已决定的局部实施，完整描述只覆盖受管变更生命周期；专用测试锁定互斥语义。（D-01、D-06、D-07；A-01、A-04）
- [自然语言仍可能误判影响] → 读取必要调用方和邻近测试；无法界定时交接，并传递事实避免重复。（D-02～D-04；A-02）
- [实质风险列表过长增加快速 Skill 体积] → 只保留风险类别，不复制完整需求规则；目录关键词不作为硬门禁。（D-03；A-02、A-03）
- [聚焦验证可能遗漏远端影响] → 局部调用链是准入事实，验证暴露共享影响时立即交接；完整任务仍使用原门禁。（D-02、D-05、D-06；A-02～A-04）

## Migration Plan

1. 先恢复 `frontend-change` 原 Skill，再新增独立 Skill 和元数据，避免中间状态继续改变完整流程。（D-01、D-06；A-01、A-04）
2. 同步公共路由、公开清单和专用测试，先运行聚焦测试确认两个入口与交接合同。（D-07；A-05）
3. 执行仓库全量、共享离线、官方 Skill/插件 validator 和 Vue 3 + Vite 生命周期验证。（D-05～D-07；A-04、A-05）
4. 已初始化项目不会被静默覆盖；显式升级受管区块后获得简洁路由。回滚时同时移除新 Skill、元数据和公共路由，并保持恢复后的 `frontend-change` 不变。（D-06、D-07；A-04、A-05）
