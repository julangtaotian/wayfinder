## Context

插件当前把“复用既有测试模式”写成原则，但未提供测试文件的选择顺序。实际项目中，通用 `.generated.spec.js` 往往由独立工具生成，文件名覆盖整页且包含大量通用 mock；把新功能追加其中会掩盖功能边界，并可能在再次生成时丢失手写场景。

## Goals / Non-Goals

**Goals:**

- 让需求编写、变更规划和实施采用同一套测试文件决策。
- 保护通用自动生成测试，要求关键新交互拥有可读、可定位的专用测试。
- 允许复用已有的手写专用测试、测试工具和 mock，避免无意义重复。
- 在需求文档中留下可审查的测试文件策略。
- 让页面局部需求默认运行聚焦测试和必要构建，不因最终交付自动升级为全量 coverage。

**Non-Goals:**

- 不移动、拆分或重写既有项目测试文件。
- 不假定所有项目都使用 Vitest、Vue Test Utils 或固定的测试目录。
- 不要求为无法自动化的视觉或外部依赖场景虚构自动测试。

## Decisions

### 测试文件按职责而非路径相近性选择

先查找同一功能的手写专用测试；存在时在该文件追加。不存在时，为新的页面交互、表单状态或关键业务流程新建命名清晰的专用测试，路径遵循项目真实测试目录与邻近测试约定。

备选方案是直接追加最接近页面路径的测试文件。它会把“路径接近”误当成“职责相同”，因此不采用。

### `.generated.spec.*` 是只读基线

文件名含 `.generated.spec.` 的测试只用于理解既有页面覆盖和测试风格，不作为新功能专用测试的落点。若业务项目有明确、可追溯的项目自定义规则允许修改，项目规则优先；否则新功能测试必须独立。

备选方案是要求所有测试完全独立。它会妨碍同一功能已有专用测试的自然扩展，因此不采用。

### 需求与实施双重记录

需求模板增加“测试文件策略”字段；需求编写技能必须填明新建或复用、目标路径和理由。变更技能在实施前复核这一决策，发现现有需求将新功能指向 `.generated.spec.*` 时改为专用测试策略并同步规划材料。

### 验证范围按影响面选择

需求模板增加“验证范围”字段。局部页面、组件或表单改动默认运行专用测试与构建；全量测试或 coverage 只在请求层、鉴权、路由、构建、共享组件或共享状态受影响，缺少聚焦测试，用户明确要求，或需求记录了发布级理由时运行。最终交付只是报告时机，不是全量测试的触发条件。

备选方案是始终在最终交付运行全量测试。它会让无关的生成型测试、外部网络依赖和历史噪声阻塞局部需求验收，因此不采用。

## Risks / Trade-offs

- [项目测试目录不规范] → 以真实测试目录和邻近手写测试为优先证据，无法确定时在需求中标记待确认。
- [历史需求已引用生成测试] → 不自动编辑业务项目；实施前显式修订测试策略。
- [生成文件不是工具产物而是项目命名约定] → 项目自定义规则可明确覆盖默认策略，并要求给出证据。
- [局部测试通过但共享回归未覆盖] → 受影响链触及共享边界时在需求中升级验证范围，并记录对应理由。
