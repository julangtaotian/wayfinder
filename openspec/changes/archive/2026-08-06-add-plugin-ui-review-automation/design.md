## Context

当前 UI 验收样例将 AI 结构化问题转换为标注 PNG 和 Markdown，但生成器位于 `outputs/`，公共插件只发布五个通用工作流 Skill，也没有项目级配置或跨阶段状态合同。插件必须继续满足仅使用 Node.js 标准库、不覆盖项目内容、拒绝危险根目录和不依赖全局运行时的约束。详见 `proposal.md` 与 `specs/plugin-ui-review-automation/spec.md`。

## Goals / Non-Goals

**Goals:**

- 把页面验收、受控源码修复和相同上下文复验变成三个边界清楚的公共 Skill。
- 用一个确定性模块统一配置规范化、场景指纹、运行状态迁移、修复授权和复验结论。
- 将现有标注报告生成器提升为插件正式脚本，同时保留样例路径的兼容入口。
- 让本地 Codex 任务与后续 CI 都能消费同一 JSON 合同，而不引入平台服务。

**Non-Goals:**

- 本轮不实现远程设计平台、代码托管平台或通知连接器。
- 不为目标项目安装 Playwright，也不启动常驻任务调度器。
- 不让确定性脚本自行判断视觉差异或直接修改业务源码；视觉判断与代码修改仍由 Skill 编排当前可用工具完成。

## Decisions

### 使用项目内隐藏目录保存配置与运行产物

默认配置路径为 `.frontend-ui-review/config.json`，默认产物根为 `.frontend-ui-review/runs`。配置使用 JSON 而不是 YAML，原因是插件核心可以直接使用 Node.js 标准库解析和稳定序列化，无需新增 YAML 依赖。Skill 在配置缺失时从插件模板创建草案并要求用户确认场景事实；脚本本身不猜测页面或设计依据。

该选择落实项目内插件形态、本地设计依据和标准库约束。（D-01、D-04、D-08）

备选方案是把 UI 字段加入 `wayfinder/frontend.md`。该文件适合项目导航和稳定画像，不适合保存多个场景、节点与交互数组，因此不采用。

### 一个模块负责配置和状态机，一个模块负责报告渲染

新增 `scripts/ui-review-workflow.mjs`，导出纯函数并提供 CLI，负责：

- 解析并校验配置、设计文件和项目内路径。
- 对规范化场景与设计文件内容计算 SHA-256 指纹。
- 创建验收运行、完成验收、评估修复授权、记录已应用问题、创建复验和计算复验结论。
- 使用原子替换写入 `state.json`，拒绝未知文件和非法状态迁移。

现有生成器迁移为 `scripts/ui-review-report.mjs`，继续负责 AI 问题输入校验、FFmpeg 标注和 Markdown 渲染。样例目录保留薄兼容入口，避免已有测试与使用方式立即失效。工作流模块不导入或执行浏览器实现，Skill 根据环境选择 Codex Browser 或项目现有 Playwright。

该拆分保持既有验收产物合同，并为本地与 CI 使用同一状态合同提供稳定边界。（D-05、D-07、D-08）

备选方案是把全部逻辑放进三个 Skill。路径校验、状态迁移和问题匹配需要低自由度与可重复测试，纯文字指令无法提供相同完整性，因此不采用。

### 运行状态以场景指纹和稳定问题指纹关联

每次运行只处理一个场景。状态包含 `schemaVersion`、`runId`、`stage`、`status`、`scenarioId`、`scenarioFingerprint`、`parentRunId`、问题摘要与产物相对路径。问题指纹由选择器、问题类型、目标值、源码文件和稳定锚点计算；复验使用指纹集合得出 `resolved`、`remaining` 和 `new`。

运行 ID 由调用方提供并限制为安全短标识，方便 CI 使用构建号或提交标识。目录采用 `<artifactsRoot>/<runId>/<scenarioId>`；不同运行不共享可写文件。

场景和问题指纹共同保证修复后的复验仍基于同一验收事实。（D-05、D-06、D-07）

备选方案是按问题编号比较。报告编号会因过滤或合并重新排序，不能稳定表达同一问题，因此不采用。

### 自动修复授权与代码执行分离

确定性模块只返回 `blocked`、`suggest` 或 `apply` 决策并验证修复上下文，不写业务源码。`frontend-ui-fix` Skill 在决策为 `apply` 后仍需检查 Git 状态、当前分支和目标文件，只允许编辑报告列出的仓库相对路径；修改完成后调用状态迁移记录为 `ready-to-verify`。

项目配置 `apply` 等同项目维护者预授权该流程；默认 `suggest` 仍需当前任务明确授权。任何提交、推送或 PR 创建继续要求独立用户请求，不能从自动修复模式推导。

该门禁直接落实默认建议、显式应用和不扩大远程权限的约束。（D-03、D-07、D-08）

### 三个 Skill 共享一份按需参考

三个 `SKILL.md` 保留各自入口、停止条件和命令顺序，共同的数据字段、状态语义和 Browser/Playwright 选择规则放入 `references/ui-review-workflow.md`。每个 Skill 直接链接该参考并在需要执行时读取，避免复制后漂移。

三个 Skill 都生成 `agents/openai.yaml`；验收和复验允许隐式匹配，修复涉及源码写入，配置为仅显式调用，降低误触发风险。

三个入口的职责和调用策略对应用户确认的插件闭环。（D-01、D-02、D-03）

## Risks / Trade-offs

- [FFmpeg 并非所有环境都有] → 报告生成器继续明确探测并失败；Skill 可以保留原始截图与 Markdown 阻塞说明，但不得伪造标注 PNG 或通过结论。
- [Browser 与项目 Playwright 的能力和截图渲染可能不同] → 场景状态记录采集方式，复验必须复用同一方式；跨采集方式视为场景变化并重新验收。
- [自动修复可能碰到用户未提交改动] → Skill 修改前检查 Git 状态与目标文件重叠，存在重叠时停止并请求方向，不自动覆盖。
- [公共 Skill 数量从五个增加到八个] → 更新严格结构白名单、README 与官方 validator；用精确 description 和修复 Skill 显式调用策略减少触发冲突。
- [首版没有远程协作界面] → 使用 Git、CI Artifacts 和 Markdown 作为历史与交付媒介，远程评论和状态回写后续通过连接器扩展。

## Migration Plan

1. 新增配置与运行状态模块、模板和专用测试，不改变既有五个 Skill。
2. 把现有报告生成器迁移到插件脚本并保留样例兼容入口，验证已有样例测试继续通过。
3. 通过 Skill Creator 初始化三个公共 Skill，补齐说明、共享参考和界面元数据。
4. 更新插件结构白名单、发布资产检查、manifest 描述和 README。
5. 运行聚焦测试、仓库全量验证、官方 Skill validator 与 Plugin validator；失败时删除新增入口即可回滚，旧五个 Skill 和样例报告保持可用。
