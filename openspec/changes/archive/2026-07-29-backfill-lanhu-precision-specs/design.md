## Context

两套纯规范目录已经覆盖 26 份组件类文档和 183 条场景，最终双组件库验收也已通过。但验收收口阶段为了贴合蓝湖参考，对 ColorPicker、日期时间选择器、时间选择器以及部分组合组件补充了更精确的面板、间距、文案和初始状态；其中一部分只保留在 Vue/CSS 验收实现和证据中。

本次需要同步两套 Markdown，同时保持规范技术栈无关。最终验收代码可以用于定位差异，但只有能在蓝湖参考或 A-05 三方证据中观察到的值才可写成“画板实测”。

决策来源为 `D-03`、`D-09`、`D-11`、`D-17`，完成判定使用 `A-07`。

## Goals / Non-Goals

**Goals:**

- 找出最终验收实现中尚未进入 Markdown 的可见 UI 精确值。
- 将同一规则同步写入 `lanhu-design-spec` 与 `lanhu-ai-ui-spec` 的对应文档。
- 固化跨目录一致性和关键精确值契约。
- 更新验证记录并给出文档独立还原能力结论。

**Non-Goals:**

- 不把 Element Plus、Element UI 的类名、属性、DOM 或主题变量写进通用规范。
- 不回写证据路由坐标、截图裁切位置、验证页卡片间距和其他验收外壳。
- 不凭组件库默认值新增蓝湖未定义的设计事实。
- 不重新实现或重采已经通过的 183 条验收页面。

## Decisions

### 1. 以“可见事实白名单”决定回写内容

允许回写的内容包括尺寸、间距、色值、文字、面板结构、可见行数、初始选中状态和图标显示尺寸。组件库内部滚动算法、CSS 选择器、弹层挂载方式和证据模式定位不进入规范。这样既能消除实现知识泄漏，又不把技术栈固化成设计契约。

### 2. 两套目录使用相同规范正文

受影响文档在两套目录中保持相同的组件规则、数值和场景说明；`lanhu-design-spec` 可以保留自身验收状态等管理内容，但不能与 AI 输入版产生可见参数差异。聚焦测试对关键片段和相对文档进行双目录检查。

### 3. 优先补齐反向审查已经确认的七类组件

优先检查 Badge、Menu、Select、Cascader、ColorPicker、DateTimePicker 和 TimePicker；同时复核 V-13 至 V-17 涉及的高频组件、分页、进度、穿梭框、上传、表单和 Table，确认精确调整已经回写。只有存在新的实现独占可见事实时才修改对应文档。

### 4. 来源保持为蓝湖标注、画板实测或研发补充

从最终实现反查出的数值只有在参考图和三方证据支持时标记为“画板实测”。蓝湖未定义的异步和恢复规则继续使用“研发补充”；不得把“验收实现使用了某值”本身当作设计来源。

## Risks / Trade-offs

- [风险] 验收代码包含为截图稳定性设置的定位值。→ 只回写组件内部可见值，排除证据模式坐标和验证外壳。
- [风险] 两套组件库的外框盒模型不同。→ 规范记录最终可见外尺寸；必要时同时说明内容尺寸与含边框外尺寸。
- [风险] 文档内容重复增加维护成本。→ 用聚焦测试固化对应文件和关键精确值同步。
- [权衡] 本次不重新执行全新 AI 盲还原。→ 结论只证明已知实现知识已经回写并通过契约检查，不宣称所有模型可一次像素级还原。
