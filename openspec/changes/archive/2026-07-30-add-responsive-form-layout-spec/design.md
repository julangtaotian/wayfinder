## Context

见 [proposal.md](./proposal.md)。本设计落实需求决策 `D-19`。现有设计规范按基础规范、组件、表单和选择器分目录，详细文件都有稳定元数据、来源等级和 Web `@1x` 测量基准。新蓝湖项目包含 12 张画板：1 张总览规则、5 张主分辨率画板，以及 3 张低分辨率空表格状态和 3 张低分辨率有数据状态。

## Goals / Non-Goals

**Goals:**

- 让 AI 只读 Markdown 就能确定 PC 视口下的表单列数、列宽变化、间距和换行边界。
- 保留 12 张画板的名称、ID、原始尺寸和用途，避免只抄总览文字而遗漏状态画板。
- 通过聚焦契约测试验证断点连续、无重叠、无空档，且源冲突处理可追溯。

**Non-Goals:**

- 不修改 Element、Element Plus 或其他组件库验收页。
- 不为 `<1024px` 伪造移动端、单列或双列设计。
- 不把本次基础布局规范计入 183 条组件场景。

## Decisions

### 1. 新建独立基础规范

文件放在 `foundations/responsive-form-layout.md`，而不是分散写入四份 Form 文档。列数是页面壳层与右侧内容区的组合规则，独立文件更容易被不同表单、筛选区和列表页复用。

备选方案是更新每份 Form 文档，但会产生重复断点并增加漂移风险。

### 2. 将 1200 和 2560 作为拉伸验证点

可执行列数只有三档：`1024px～1439px` 三列、`1440px～1919px` 四列、`≥1920px` 六列。`1200px` 与 `2560px` 只证明在同一列数内等宽列会随可用空间拉伸。

备选方案是把五张主画板都写成断点；这会制造没有列数变化的冗余分支，使 AI 更容易写出互相覆盖的媒体查询。

### 3. 以视口断点为设计事实，以内容区守卫为研发补充

蓝湖总览按页面分辨率声明列数，因此规范先使用视口宽度。实现建议同时要求列项 `min-width: 0`、控件 `width: 100%`，并在实际项目壳层占用额外宽度时整体降级一档，保证不横向越界；该守卫必须标为研发补充，不能冒充蓝湖断点。

### 4. 将“1400”归一为“1440”

同一总览的上一条明确写 `1440`，项目存在 `1440`、`1440 copy`、`1440 copy 2` 三张画板，不存在 `1400` 画板。文档保留源文字冲突，但执行值统一为 `1440px`，避免创建无法由画板验证的 1400 分支。

### 5. 验证文档契约而不扩展历史组件验收

聚焦测试检查新文档元数据、12 张画板、精确壳层、三档连续区间、列数、`16px / 8px`、自动拉伸、操作组和 `<1024px` 边界。既有组件数量、场景数量和双组件库视觉证据保持不变。

## Risks / Trade-offs

- [风险] 目标项目的侧栏宽度与蓝湖固定壳层不同，同一视口下右侧内容区可能更窄。→ 规范将固定壳层值标为蓝湖标注，并提供不改变设计事实的容器宽度守卫建议。
- [风险] 把操作按钮当作普通字段列会导致按钮被拉伸或拆分。→ 文档明确列数只统计字段组，操作组不可拆分并整体换位。
- [风险] README 的 45 张画板与历史本地参考图 33 张混淆。→ 索引将来源覆盖更新为 45 张，但不改写历史 `validation-evidence/reference` 的 33 张组件视觉证据清单。

## Migration Plan

1. 新增响应式表单布局文档并更新 README 清单。
2. 更新主规范契约中的文档、详细规范和源画板计数。
3. 更新聚焦测试并运行验证。
4. 验证通过后同步主规范、归档变更；回滚时删除新增文档并恢复 README、契约和测试计数。
