## Why

项目画像已经能识别主要终端形态和小程序框架，但需求与变更上下文仍无法判断项目是否真实配置了对应平台的开发或构建脚本。第三轮需要把已有脚本转成可追溯、不可夸大的候选证据，使实施和验证计划能引用真实入口，同时继续保持插件精简和只读识别边界。

## What Changes

- 从非空 `package.json.scripts` 识别微信小程序、支付宝小程序和 H5 的显式开发/构建候选。
- 为每个候选报告脚本名、当前包管理器命令、稳定来源和 `executed=false`，保留同一目标的全部候选而不自动选择或执行。
- 在已识别平台框架但缺少平台脚本时提供非阻断检查警告；普通 Web 项目保持安静空态。
- 将平台命令状态、目标和证据同步到 AGENTS、Wayfinder、OpenSpec、需求规则和受管变更技能。
- 不增加公共命令、配置文件、依赖、平台适配器、脚本内容解析或自动执行流程。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `project-command-semantics`：增加显式平台命令候选的识别契约，以及需求、变更、初始化、升级和检查对同一证据的消费规则。

## Impact

- 影响项目识别、项目检查、受管模板和受管元数据生成。
- 影响需求整理与变更技能对平台命令证据及验证结果的解释。
- 扩展现有平台画像专项测试，不改变现有公共 CLI、通用命令字段、依赖或未受管文件保护规则。
- 关联需求：`REQ-2026-015` 的 D-01～D-10 与 A-01～A-04。
