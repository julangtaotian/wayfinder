## Context

关联决策：D-01～D-10；关联验收：A-01～A-04。

参见 `proposal.md` 的动机。现有 `inspect-project.mjs` 已统一读取 package scripts、包管理器、通用命令和平台画像，初始化、升级与检查都复用该识别结果；因此平台命令证据应继续沿用这条共享链路，避免出现第二套平台编排系统。

实现还必须遵守只使用 Node.js 标准库、预览只读、不覆盖未受管文件、内置 OpenSpec 运行时以及不输出脚本内容或敏感值等现有约束。

## Goals / Non-Goals

**Goals:**

- 以小型静态映射表达目标、别名和动作，生成稳定、可测试的候选证据。
- 让识别、初始化、升级、检查、需求和变更读取同一事实来源。
- 在数据契约和人类可读上下文中明确“发现候选”与“执行成功”的边界。

**Non-Goals:**

- 不建立平台适配器、命令调度器或发布流水线。
- 不判断脚本内容是否正确，也不选择最佳候选。
- 不扩展第二轮框架清单或替代通用命令语义。

## Decisions

### 1. 在项目识别模块内维护声明式匹配表

目标表只包含 `wechat-mini-program`、`alipay-mini-program`、`h5` 及其已确认别名；动作表只包含开发动作 `dev/serve/start` 和构建动作 `build`，分隔符为 `:`、`-`。候选按动作、别名、分隔符顺序生成，去重后保留所有非空精确匹配。

选择这种方式是因为目标数量很小，且项目识别模块已经负责脚本与包管理器事实。相较于新增适配器目录或解析脚本内容，声明式表更容易审查，不会引入执行和安全边界。

### 2. 新增独立 `platformCommands`，不改写通用 commands

识别结果新增：

- `status`: `detected` 或 `missing`
- `source`: `package-scripts` 或 `unknown`
- `targets`: 只包含至少一个候选的目标；每个目标含 `devCandidates` 与 `buildCandidates`
- `evidence`: 去重排序的 `script:<name>`

候选包含 `scriptName`、由当前包管理器生成的 `command`、`source=explicit-platform-script`、`executed=false`。独立字段可以保持既有 `commands` 和 `commandSemantics` 向后兼容，也避免把多个平台候选误压缩成单一默认命令。

### 3. 缺失警告由平台画像限定

只有 `targetProfile.platform.kind` 已识别且平台命令状态为 `missing` 时，检查才增加非阻断中文警告。普通 Web 或未知平台项目保持空态，避免把可选平台脚本变成所有项目的噪音。

### 4. 受管上下文只写摘要和证据

AGENTS、OpenSpec 上下文写入状态、目标、候选摘要和“发现不代表执行”的提示；Wayfinder 受管元数据写入状态、目标、证据。上下文不复制 package script 内容。升级继续只替换受管区块，因此项目自定义内容不会受影响。

### 5. 技能规则消费证据但不扩大自动化权限

需求规则、`frontend-change` 和 `frontend-workflow-check` 读取 `platformCommands`：存在候选时把它作为待执行入口；缺失时记录人工开发工具或外部 CI 环境；只有实际运行成功后才能更新为通过。技能不因此获得自动安装、启动或发布平台工具的权限。

### 6. 复用平台画像专项测试

在 `tests/project-platform-profile.test.mjs` 增加三类目标、四类包管理器、多候选、空/误导脚本、缺失警告和上下文同步场景。该能力是第二轮平台画像的实施与验证延伸，复用同一手写测试比增加新的测试层级更容易维护。

## Risks / Trade-offs

- [脚本命名不在白名单中会漏报] → 返回 `missing` 并允许需求记录人工工具或外部 CI，不通过解析内容或模糊匹配扩大误报。
- [脚本存在但实际不可用] → 候选固定 `executed=false`，工作流只有在真实执行成功后才记录通过。
- [同一目标候选过多导致选择不明确] → 全部保留，把选择留给具体需求和项目上下文，不在识别层加入隐式优先级。
- [受管模板信息增长] → 只加入一行摘要和少量元数据，不新增独立文档、配置或公共命令。

## Migration Plan

1. 先扩展专项测试，再实现识别与检查契约。
2. 同步受管模板、需求规则和变更/检查技能。
3. 运行专项测试、完整验证和官方插件/技能验证器。
4. 更新插件缓存标识并重装本地副本，核对源码与安装副本。
5. 已初始化项目仅在用户显式升级时刷新受管区块；回滚时删除新增字段与模板摘要即可，无业务数据迁移。
