## Context

当前 UI 验收把 `project-playwright` 的命令和结果路径交给业务项目，插件只校验参数，无法保证项目已经安装正确版本的 Playwright 和对应浏览器。插件已经有一套完整随包发布、固定版本并执行完整性检查的 OpenSpec 运行时，可作为 Playwright 发布方式的结构参考。参见 `proposal.md` 与本变更的 `plugin-ui-review-automation` delta spec。（D-08～D-10，A-06、A-07）

项目约束要求公共逻辑优先使用 Node.js 标准库、保持旧配置兼容、拒绝危险路径，并且运行时不得暗中扩大安装或命令执行权限。Playwright 浏览器是与操作系统和 CPU 绑定的大型二进制，不能把当前平台文件伪装成跨平台资产。

## Goals / Non-Goals

**Goals:**

- 业务项目不修改 `package.json` 或锁文件即可获得固定 Playwright API。
- 插件发布物包含当前目标平台可直接启动的 Chromium headless shell。
- 配置、计划和执行阶段都能解释运行时来源、版本、平台兼容性和失败原因。
- 适配器只在业务项目安全边界内加载，旧项目命令与视觉兜底不改变原语义。

**Non-Goals:**

- 本次不把单个平台构建物声明为 Windows、Linux 与 macOS 通用发布物。
- 本次不把自然语言交互自动猜测成点击或输入动作；项目适配器负责把场景事实转换为 Playwright 操作与结构化结论。
- 本次不新增远程浏览器服务、运行时下载器、自动系统依赖安装或独立管理平台。
- 本次不改变报告问题合同、自动修复权限或复验必须复用实际采集器的规则。

## Decisions

### 1. 运行时采用独立固定目录并内置 Chromium headless shell

在 `runtime/playwright` 保存固定版本的 `playwright`、`playwright-core`、锁文件、许可文件和由 `PLAYWRIGHT_BROWSERS_PATH=0` 安装的 Chromium headless shell。只安装 Chromium 的无头 shell，因为 UI 证据采集不需要 Firefox、WebKit 或有头浏览器，这能控制发布体积。（D-08、D-10，A-07）

备选是只提交 `package.json` 并在首次使用时安装。该方案仍会让用户二次下载、受网络和版本漂移影响，违反需求。另一个备选是调用系统 Chrome；它减少体积但浏览器版本不可固定，视觉复验稳定性较差，因此不作为默认主路径。

### 2. 运行时元数据显式绑定发布平台

运行时元数据记录 Playwright 版本、浏览器名称、操作系统、CPU、可执行文件相对路径和关键文件摘要。结构校验和执行入口都检查元数据与当前平台；不匹配时返回不可移植原因，不尝试下载或寻找未知浏览器。

单仓同时存放所有平台二进制会显著放大插件并且当前环境无法可靠生成其他平台资产。首个发布物绑定实际构建平台；后续如需多平台分发，应由发布矩阵分别生成并验证相同源码的插件包。

### 3. 新配置使用注入式项目适配器

`projectPlaywright.adapter` 指向业务项目内已存在的 ESM 模块，与兼容字段 `command` 互斥。插件运行器先加载并校验自己的 Playwright，再把 `playwright` API、只读场景、运行 ID、项目根和已经校验的绝对产物路径传给适配器。适配器默认导出异步函数并自行完成页面交互、截图和结构化结果写入。（D-08、D-09，A-02、A-06）

相较于通过 `NODE_PATH` 或临时改写业务依赖解析，显式参数注入不依赖 CommonJS 的全局查找规则，也不会污染项目模块图。相较于让插件执行任意配置命令，适配器路径可以按现有仓库相对路径与符号链接规则校验。

### 4. 采集计划生成稳定插件命令但不代替调用方执行

当配置使用适配器时，`capture-plan` 返回当前 Node 可执行文件、插件运行器绝对路径和经过校验的参数数组，并附带 `runtime` 元数据。工作流脚本仍只规划，不直接执行命令；AI 工具或 CI 在已有权限边界内执行计划。适配器执行成功必须生成真实 PNG 和可解析 JSON，否则主路径视为失败。

兼容 `projectPlaywright.command` 继续原样展开占位符并标记为 `project-command` 来源；没有适配器或命令的旧 Playwright 配置继续标记不可移植。视觉兜底只能按现有新运行 ID 规则显式切换。（D-08、D-09，A-06）

### 5. 完整性检查覆盖包、平台元数据和浏览器可执行文件

新增独立 Playwright 完整性清单，摘要覆盖运行时包清单、锁文件、平台元数据和浏览器可执行文件。统一验证先检查静态结构，再真实启动 Chromium 并完成最小页面截图测试。运行期只读检查失败即阻断，不自动修复运行时。

OpenSpec 完整性逻辑保持不变，避免一次依赖引入重构已经稳定的供应链校验。

## Risks / Trade-offs

- [插件体积显著增加] → 只内置 Chromium headless shell，并在文档与验证输出中报告运行时大小。
- [发布物平台不匹配] → 元数据与执行入口双重校验；明确返回不可移植原因，允许场景已声明的视觉兜底。
- [适配器拥有项目进程内代码执行能力] → 只加载配置已声明、项目内真实存在且不经符号链接越界的模块；计划阶段不执行，权限不超过调用方已经授权的项目脚本。
- [旧命令仍可能依赖项目自己的 Playwright] → 保持兼容但标记来源为 `project-command`；新模板与 Skill 只推荐内置适配器。
- [Playwright 与浏览器版本需要同步升级] → 版本固定在运行时常量与包清单中，升级时重新下载、重建完整性清单并执行真实启动测试。

## Migration Plan

1. 新增并验证固定 Playwright 运行时与平台元数据，不修改现有场景配置。
2. 增加适配器配置与执行入口，保留命令式路径并补齐聚焦测试。
3. 将模板和 Skill 默认示例切换到适配器；旧业务项目无需迁移即可继续运行。
4. 完成全量验证后更新插件 cachebuster 并重新安装本地插件。
5. 回滚时恢复旧模板与采集计划逻辑并移除 Playwright 运行时目录；旧命令合同仍可继续使用。
