## Context

动机和范围见 `proposal.md`，行为合同见 `specs/fast-change-routing/spec.md`。现有独立快速 Skill 在发现匹配活动变更时已经会保留调查结果并交接；`frontend-change` 也已有需求状态校验、聚焦验证、工作区证据新鲜度、精确提交 CI 和完成归档门禁。本设计只把这些现有能力组织成一个可恢复的局部纠正步骤，不引入新的执行器或状态机。（D-01～D-06；A-01～A-04）

## Goals / Non-Goals

**Goals:**

- 让唯一活动变更中的既有目标缺陷无需重新 Plan 或 Revise 即可安全修正。（D-01、D-02；A-01）
- 在“待验证”返修时保持需求、任务、验收和证据状态真实，并继续由原硬门禁阻止旧证据。（D-03、D-05；A-02）
- 把修正阶段的读取和验证收缩到直接相关链路，同时保留行为变化立即返回 Revise 的边界。（D-04、D-06；A-02、A-03）

**Non-Goals:**

- 不提供第三个 Skill、公开入口、轻量规划或第二套完成流程。（D-01、D-06）
- 不修改快速 Skill、需求/证据校验器、证据指纹算法、OpenSpec 运行时或归档脚本。（D-05、D-06）
- 不承诺只因文件少、行数少或模型判断有信心就允许局部修正。（D-02、D-06）

## Decisions

### 1. 把修正定义为 Implement 与 Complete 之间的内部回路

在 `frontend-change` 的现有生命周期中增加一个短小的“Correct within an active change”段落，并由 State Rules 把“验证、静态分析、审查或 CI 暴露的既有目标缺陷”路由到该段落。公开描述、阶段标题和独立快速 Skill 保持不变，因此没有匹配活动变更的新请求仍按原规则 Plan 或选择独立快速能力。（D-01、D-02、D-06；A-01、A-04）

备选方案是新增第三个 Skill。它会引入新的隐式选择重叠和交接状态，不符合最小改动目标，因此不采用。

### 2. 使用既有 D/A 和实质边界做准入，不使用规模阈值

修正前只确认唯一活动变更、直接关联的 D/A、任务、源码、必要调用方、邻近测试和聚焦验证。全部事实成立才继续；任何新决策、行为变化或实质工程边界立即返回 Revise，并复用已读取事实。（D-02、D-04、D-06；A-01、A-03）

备选方案是按文件数量、改动行数或目录关键词判定小修复。它既会误放高风险修改，也会误伤同一局部调用链的必要多文件修复，因此不采用。

### 3. 待验证返修先恢复最小真实状态

如果需求仍是“实施中”，不产生状态操作；如果已经“待验证”，先改回“实施中”，并只重新打开直接受影响的任务、A-* 和 V-*。代码变化后，完成阶段继续复算机器证据：工作区指纹不一致的本地证据必须重跑，外部 CI 必须对应新交付提交。（D-03、D-05；A-02）

备选方案是保持“待验证”和已完成记录直接修改代码。这样在中断或恢复时会把旧结果误表示为当前结果，并与实施阶段校验冲突，因此不采用。

### 4. 聚焦命令只执行一次，完成门禁不降级

实现阶段运行能证明缺陷已修复的最窄检查。若严格证据合同要求同一命令形成 V-* 机器证据，就直接通过现有证据采集入口执行；否则执行一次普通聚焦检查。只有进入 Complete 时才根据现有映射和门禁补齐失效验证，不因返修本身自动运行全量测试。（D-04、D-05；A-02、A-04）

备选方案是在修正后立即运行聚焦、全量、证据采集和完成验证。它会重复相同命令，并把交付级成本施加到每次局部编辑，因此不采用。

### 5. 复用同功能专用测试并保持公共文档不变

扩展 `tests/fast-change-routing.test.mjs`，锁定三个互斥去向、状态恢复、最小验证、实质边界退出和原 Complete 门禁。不修改模板、README、需求规则或公开 Skill 清单，因为公共层仍然只有独立快速与完整受管两个入口。（D-01、D-06；A-01～A-04）

备选方案是新建第二个路由测试文件并同步多份公共说明。它会拆散同一合同并增加重复维护，因此不采用。

## Risks / Trade-offs

- [“局部”判断过宽，静默绕过 Revise] → 要求唯一活动变更、既有 D/A、可界定调用链和聚焦验证同时成立；列出的实质变化任一命中即退出。（D-02、D-06；A-03）
- [只重开直接记录但其他证据也因工作区变化失效] → 不人工猜测全部影响，Complete 继续复算所有要求的证据并按实际失效结果补跑。（D-03、D-05；A-02）
- [Skill 文本约束不是新的运行时分类器] → 关键错误仍由现有状态、证据新鲜度、精确提交 CI 和 finalize 门禁阻断，专用测试防止路由语义漂移。（D-05、D-06；A-02、A-04）
- [共享工作流改动的完成验证成本仍较高] → 实施阶段只跑专用测试；全量、结构和官方 validator 只在完成阶段执行一次。（D-04、D-05；A-02、A-04）

## Migration Plan

1. 先更新 `frontend-change` 的内部修正规则，再扩展现有专用测试，保持独立快速 Skill 和公共路由文件不变。（D-01、D-04、D-06；A-01～A-04）
2. 运行专用测试，确认准入、状态恢复、退出条件和原生命周期门禁。（D-02～D-06；A-01～A-04）
3. 完成阶段运行仓库全量、结构和官方 validator；通过原 finalize 流程同步本 delta spec。（D-05、D-06；A-02、A-04）
4. 回滚时移除内部修正段落和对应测试断言；无需迁移需求、证据格式、运行时或项目数据。
