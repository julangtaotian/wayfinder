## Context

需求、规格、设计和任务目前以自然语言相互转述。相同的原始描述在存在关闭语义、输入规则、兼容范围或验证范围等空白时，AI 可以在任一层补入不同默认值；这些值既没有稳定 ID，也没有机械校验，因而无法定位冲突来源。

## Goals / Non-Goals

**Goals:**

- 在既有需求文档内建立唯一、可读、可解析的决策事实源。
- 让验收标准与自动/人工验证一一对应，并能被脚本检查。
- 阻止待确认或暂定的业务决策进入实施任务。
- 让需求、变更和实现技能在同一校验边界工作。

**Non-Goals:**

- 不追求不同模型运行后 Markdown 逐字相同。
- 不自动替既有需求补造或迁移业务决策。
- 不用规则脚本判断自然语言语义是否正确，也不替代用户对业务歧义的确认。

## Decisions

### 在现有需求中使用稳定 ID 的两个表

`REQ-*.md` 新增“决策台账”和“验收—证据映射”两个表。决策 ID 使用 `D-01` 格式，验收 ID 使用 `A-01` 格式；每个决定必须记录状态、取值和来源。状态仅允许“已确认”“项目默认”“暂定”“待确认”。

验收标准以 `[A-01]` 关联映射表，映射表记录关联决策、验证方式、证据位置与预期断言。这样保留一个人可读文件，同时为校验器提供稳定锚点。

### 只让可实施决策进入任务

只有“已确认”或“项目默认”的 `D-*` 可被 `tasks.md` 引用。`暂定` 与“待确认”可在需求中说明，但不得生成实施任务；需要产品决定时必须保留在待确认问题中。

备选方案是允许暂定值进入任务并标记风险。它仍会导致不同运行选择不同默认实现，因此不采用。

### 用确定性校验补足提示词

新增仅依赖 Node.js 标准库的校验器。它检查表头、ID 唯一性、状态和值/来源、验收 ID 与映射一一对应、映射引用的决策存在，以及任务文件没有引用不可实施或未知决策。校验器只验证结构和引用关系；语义是否符合业务仍由需求评审决定。

CLI 采用：

```text
node <plugin-root>/scripts/validate-requirement-decisions.mjs <requirement-path> [--change <change-path>] [--json]
```

### 分层文档只引用事实源，不重新定案

需求编写技能先提炼台账，再写正文、验收与证据映射。变更技能在计划和实施前执行校验；规格、设计和任务必须以 `D-*`、`A-*` 引用已确认事实。OpenSpec 配置作为规划时的持续规则，AGENTS 则让项目内后续 AI 遵守同一边界。

## Risks / Trade-offs

- [用户认为表格增加负担] → 仅增加两个区块，不创建新文件；用紧凑 ID 和模板降低填写成本。
- [业务语言无法被脚本理解] → 脚本只做结构/引用校验，关键业务值仍要求来源和人工确认。
- [旧需求不含新表] → 不自动改写；新版流程明确报告缺失并要求先修订。
- [技术默认值与业务默认值混淆] → “项目默认”必须给出规则或源码来源，用户可见行为、安全和数据语义不可伪装为技术默认值。
