## Context

参见 `proposal.md`。当前兼容入口把纯数据校验、Markdown 生成、文件系统安全操作、FFmpeg 子进程与 CLI 解析放在同一模块。生产调用方只依赖公开导出，且其中部分调用方需要保持同步函数调用；因此不能以异步 `import()` 替换公开 API。

本变更为 UI Review 行为不变的内部重构，依据需求 D-02 声明 `skip_specs: true`。涉及路径、暂存目录、子进程与机器诊断，按 D-05 记录为跨平台高风险；D-09 将测试方案、需求交付和 Markdown 结构校验纳入同一提交前防回归链。

## Goals / Non-Goals

**Goals:**

- 将输入契约、报告文本和标注产物分离为可独立读取的内部模块。
- 保持兼容入口全部公开导出、同步 API、CLI 参数、输出字段、错误语义和退出状态。
- 以专用测试锁定门面规模、单向导入、路径样本与产物失败清理。
- 将“按职责定位、避免机械拆分、保留异常兼容”的后续维护规则写入持久 UI Review 参考资料。

**Non-Goals:**

- 不改变 UI Review 配置、比较结果、报告内容、FFmpeg 渲染算法或输出路径规则。
- 不把公开同步函数转换为异步按需加载，也不修改其他大脚本、CI 或平台运行时。
- 不把维护规则扩大为插件所有脚本的强制目录结构，也不以规则替代需求、兼容性或安全评审。

## Decisions

### 1. 原入口作为薄兼容门面

`ui-review-report.mjs` 保留原路径和 CLI 入口，只重导出既有函数、提供默认输出根并编排 CLI 输入。

选择此方案是为了让 `ui-review-runner.mjs`、`playwright-adapter-runner.mjs` 和现有测试不改导入路径。将消费者迁移到内部模块会扩大重构范围；删除兼容门面会破坏插件脚本的稳定 API。

### 2. 以单向职责模块取代运行时懒加载

- `ui-review-report-contract.mjs`：通用输入、路径与文本校验工具。
- `ui-review-report-input.mjs`：PNG 尺寸读取、审核输入解析与基础校验。
- `ui-review-report-decision.mjs`：问题筛选、合并和结论派生。
- `ui-review-report-markdown.mjs`：普通审核报告与确定性验收报告渲染。
- `ui-review-report-artifacts.mjs`：FFmpeg 发现、绘制滤镜、受控输出暂存、原子替换、失败恢复和报告生成。

兼容门面静态导入并重导出内部能力，内部依赖只能从 contract 向上单向流动。这里的“按需拆分”指职责与读取范围按调用路径分离，而非改变同步公开 API 的运行时加载时机。异步动态导入会迫使 `generateUiReview` 等既有同步函数改变返回类型，因此不采用。

### 3. 保持子进程和路径的现有安全模型

产物模块继续以 `spawnSync(command, args)` 调用 FFmpeg，禁止 shell；输出和暂存目录继续经过 `project-path-safety.mjs`。测试同时覆盖 POSIX 和 Windows 风格输入的规范化，不把绝对路径整段文本当作唯一断言。

该方案复用已验证的安全边界；改用字符串命令、shell 或新的外部依赖会引入无关风险。

### 4. 新建专用模块化测试

创建 `tests/ui-review-report-modularization.test.mjs`，覆盖门面导出、输入/渲染结果、内部模块导入方向、行数上限、受控替换与失败清理。相邻 UI Review 和证据完整性测试继续保护实际消费者。

不把这些断言附加到聚合型 `ui-review-automation.test.mjs`，以避免新的报告脚本职责被隐藏在无关领域用例中。

### 5. 以条件式维护规则保护异常与兼容路径

在 `references/ui-review-workflow.md` 增加仅适用于报告链的维护规则：新功能先归类为数据解析、业务判断或输出报告；只在跨职责或既有模块达到维护边界时拆分。单职责改动保留在所属模块，避免只为目录层级增加跳转。

规则同时明确：输入异常、路径安全、暂存发布与清理、FFmpeg 失败、公开导出、CLI 和中文诊断必须由所属职责继续失败关闭；任何公开 API、报告语义、权限、路径边界或错误语义变更仍需先修订需求台账。将该原则只写在归档规划资料中会随归档淡出日常读取，因此选择项目长期 UI Review 参考资料作为交付物。

### 6. 统一活动文档与跨平台路径的提交前门禁

测试方案和需求交付中的项目相对路径复用 `project-path-safety.mjs`，由同一安全入口拒绝 POSIX 绝对路径、Git 风格 `D:/...` 与 Node 风格 `D:\\...`。测试文件“新建/复用”基线改为读取 `HEAD` 的树，避免 `git add` 后把本轮新建文件误判为既有测试。

结构校验新增只读 Markdown 检查，范围固定为插件模板、根 `requirements/` 的活动需求和 `openspec/changes/` 的活动变更，跳过归档。它仅报告裸 `[D-xx]`、`[A-xx]` 标签，保留反引号代码和有效 Markdown 链接；任务和验收追踪继续使用普通 D/A 编号，因此不改变需求解析器的兼容输入。

## Risks / Trade-offs

- [移动私有辅助函数时遗漏依赖] → 通过门面导出和专用输入/渲染快照回归覆盖；模块只允许单向导入。
- [暂存目录恢复语义变化] → 保持产物模块的原子替换流程，并增加成功、重复写入和失败清理断言。
- [Windows 路径或外部工具差异] → 使用 Node 路径 API、数组参数启动子进程，并在本地确定性测试覆盖 Windows/POSIX 样本；真实五平台 CI 单独复核。
- [规则只停留在文档而重复漏检] → 将跨平台绝对路径与裸 D/A 标签变为验证器错误，分别复用工作流专用测试并在 `npm run validate` 执行；扫描边界排除归档和代码示例，避免误报。
- [额外模块增加跳转次数] → 每个模块按单一职责命名，兼容入口仍为唯一公共入口；局部维护读取量显著下降。
- [维护规则被误用为机械拆分] → 明确单职责改动不拆分，且用专用测试断言参考资料同时包含职责路由和异常兼容边界。

## Migration Plan

1. 创建专用测试和模块边界断言，先覆盖当前兼容合同。
2. 提取 contract、input、decision、markdown 与 artifacts 模块，保留入口重导出与 CLI。
3. 写入长期维护规则并以专用测试锁定其职责与异常兼容边界。
4. 执行聚焦、相邻、体积和仓库级验证；修正任何 API、路径或清理回归。
5. 在同一提交五平台 CI 成功后补充外部复核记录，再完成归档。

回滚仅恢复原入口及删除新增内部模块；生成在业务项目中的既有报告不迁移、不删除。
