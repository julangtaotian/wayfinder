## Context

当前实现由确定性 Node.js 脚本、受管 Markdown 模板、公开技能和插件内置 OpenSpec 组成。范围收集器能稳定枚举文件并计算单文件 SHA-256，但未应用 Git 忽略或敏感文件规则；Wayfinder 没有保存项目快照指纹；需求校验器能验证 D-*、A-*、V-*，但状态与完成前校验顺序倒置，且没有关联变更范围和逐任务追溯；归档参考仍沿用上游可确认绕过的通用语义。（D-01～D-08）

本轮修改跨越扫描、模板、校验、检查和完成归档，必须保持默认只读、显式写入、旧格式兼容以及仅使用 Node.js 标准库。

## Goals / Non-Goals

**Goals:**

- 在读取文件内容前排除 Git 忽略项和敏感路径，生成稳定的范围指纹。（D-01、D-02；A-01）
- 让普通升级保留既有分析快照，只有显式深度刷新才更新扫描时间和指纹。（D-02、D-08；A-02、A-07）
- 将需求修订和完成状态变成可校验状态机，建立关联变更范围与逐任务追溯。（D-03、D-04、D-07；A-03、A-04）
- 提供可组合的变更/交付检查和默认 dry-run 的完成归档入口。（D-05、D-06；A-05、A-06）

**Non-Goals:**

- 不实现多框架或 Monorepo 编排。
- 不自动执行目标业务项目测试，也不伪造命令已执行状态。
- 不自动推断历史需求业务事实，不批量归档当前历史变更。
- 不更改插件内置 OpenSpec 运行时源码。

## Decisions

### 1. 安全过滤先于内容读取

范围收集先使用显式敏感路径规则拒绝 `.env`、凭据、密钥和常见本地配置，再在 Git 仓库中使用 `git ls-files --cached --others --exclude-standard` 限定可读候选。没有 Git 时回退到现有遍历，但仍应用敏感规则。`.env.example`、`.env.sample` 和 `.env.template` 只作为无真实值模板纳入。（D-01；A-01）

选择 Git 自带忽略解析而不是自行实现 `.gitignore` 语法，避免否定规则、嵌套规则和转义行为不一致；没有 Git 时不假装支持 Git 忽略。

### 2. 指纹与扫描时间分离

`collectProjectScope` 继续返回可重复结果，新增由规则版本、纳入文件路径和内容 SHA-256 生成的 `fingerprint`，以及可重复读取的 Git commit/dirty 元数据。`scannedAt` 由显式深度写入流程生成，不放进稳定范围对象。（D-02；A-01、A-02）

普通工作流升级读取并保留 Wayfinder 中已有的快照字段，不重新扫描后覆盖分析基线；只有用户明确深度刷新时才更新快照。健康检查重新计算当前安全范围并比较指纹，不一致只发警告。

### 3. 总量限制采用类别优先而不是纯路径优先

单文件限制后，按 configuration → source → test → documentation → other 的类别优先级和路径稳定排序应用总量上限，避免文档或产物先占满预算导致核心源码被排除。最终输出仍按路径排序，保证消费方稳定。（D-02；A-01）

### 4. 新旧需求使用双轨状态门槛

新增 `precomplete` 阶段：只接受“待验证”，执行与完成相同的验收、任务、V-* 和证据门槛；现有 `complete` 保留对历史“已验收”需求的审计能力。规划只接受“已确认”，实施只接受“已确认/实施中”。完成入口在归档成功后才将单一状态行原子替换为“已验收”。（D-04、D-08；A-04、A-07）

### 5. 关联变更范围采用需求内显式矩阵

新版需求增加“关联变更范围”表，逐个变更列出适用 D-* 与 A-*。校验器在矩阵存在时要求任务全集覆盖该变更声明的范围，并逐行验证任务至少引用一个有效 D-* 或 A-*。旧需求缺少矩阵时保持警告兼容，不自动补写。（D-03、D-07、D-08；A-03、A-07）

### 6. 分层检查复用同一校验核心

`check-project` 继续负责接入结构与分析新鲜度，并报告已完成但未归档的活跃变更。新增变更检查模块组合需求校验、OpenSpec 状态和严格校验：`implement` 用于变更一致性，`precomplete` 用于交付就绪。所有结果区分 `detected`、`recorded` 和 `executed`，脚本不会自动运行业务测试。（D-05、D-07；A-05）

### 7. 完成入口默认 dry-run 并包裹内置归档

完成脚本先执行 `precomplete`、严格 OpenSpec 校验、归档目标冲突检查并生成动作预览。只有显式 `--write` 才调用插件内置 `archive --json --yes`；不提供 `--no-validate` 或 `--skip-specs` 透传。内置运行时会在写入主规格前构建并验证全部结果，成功移动变更后脚本才原子写入需求状态。（D-06、D-07；A-06）

相比继续手工同步和 `mv`，该方案复用内置运行时的规范合并与写前验证，同时用插件前置门禁消除 `--yes` 对未完成任务的上游绕过语义。

## Risks / Trade-offs

- [Git 忽略会排除用户希望分析的本地文件] → 报告具体排除原因；需要纳入时由用户显式调整项目忽略规则或提供安全副本。
- [大型仓库重新计算指纹增加检查耗时] → 仅在 `deepAnalysis: true` 时计算，保持 20 MiB 上限和稳定优先级。
- [旧需求没有关联变更范围] → 继续按旧规则检查并给迁移警告，不阻断历史交付审计。
- [运行时归档跨多个文件系统操作，不具备数据库事务] → 前置完成全部可预测校验并预查目标冲突；任何失败不更新需求为“已验收”，报告残余状态供恢复。
- [当前工作区没有 Git 索引基线] → fixture 使用临时 Git 仓库覆盖 Git 分支，本仓库结果保留降级警告。

## Migration Plan

1. 升级模板和读取器，使旧 Wayfinder 字段缺失时仍可解析。
2. 发布扫描器与检查器，新字段只在显式深度刷新后写入。
3. 发布新版需求模板和校验阶段；旧需求继续使用 `complete` 审计，新需求使用 `precomplete` 完成。
4. 更新技能，要求行为修订先改需求，并统一通过完成脚本归档。
5. 使用 Vue 3 + Vite fixture 验证初始化、重复执行、深度刷新、普通升级、检查和完成阻断。

回滚时可恢复上一版插件；新版写入的额外机器字段位于受管区块，旧版读取器会忽略未知字段。
