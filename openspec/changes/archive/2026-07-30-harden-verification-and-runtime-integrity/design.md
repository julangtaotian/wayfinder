## Context

见 `proposal.md` 的 Why。当前根脚本只有分散的 test、validate 和版本检查；GitHub Actions 复制其中两项。框架识别逻辑已经存在，但主 fixture 固定为 Vue 3 + Vite。内置 OpenSpec 是完整生产安装目录，包含嵌套依赖和可能缺少 `.bin` 链接的开发缓存副本，因此完整性算法必须跨源仓库与缓存保持稳定。（D-02、D-03、D-04、D-05；A-02、A-03、A-04、A-05）

## Goals / Non-Goals

**Goals:**

- 用一个 Node.js 标准库编排器形成短路、可定位、只读的完整验证。
- 用数据驱动的临时 fixture 扩展现有手写端到端测试，不引入生成器或测试依赖。
- 以每个生产包为粒度计算稳定树摘要，并让清单可在源插件和安装缓存中复核。
- 保留插件现有安全边界并完成 0.11.0 发布验证。（D-02、D-04、D-05、D-06；A-02、A-04、A-05、A-06）

**Non-Goals:**

- 不运行 fixture 的真实构建或包安装。
- 不提供加密签名、远程证明或漏洞扫描。
- 不实现 Monorepo workspace 编排。

## Decisions

### 1. 使用 Node.js 编排器而非 shell 命令链

新增根级验证脚本，以参数数组启动每个阶段并继承输出；失败时立即退出并显示稳定阶段名称。这样避免不同 shell 的引号和短路差异，也便于测试失败传播。备选方案是在 `package.json` 中使用 `&&`，但其错误定位和跨平台语义较弱。（D-02；A-02）

### 2. OpenSpec 严格校验覆盖活动变更与主规格

编排器调用插件内置 CLI 的 `validate --all --strict --no-interactive`，让活动变更和归档后的主规格使用同一严格门禁。不使用全局命令，也不让 verify 写入或归档变更。备选方案只校验主规格，但会遗漏尚未归档的无效 delta；只校验活动变更则无法保护已经归档的主规格。（D-02、D-06；A-02、A-06）

### 3. fixture 使用矩阵描述和最小真实文件

测试用矩阵声明框架依赖、构建依赖、锁文件和期望命令，复用现有初始化、升级和检查函数。每个 fixture 只创建识别和工作流需要的文件，不安装依赖。完整生命周期至少在每类框架/构建组合上执行，包管理器命令在矩阵内交叉覆盖。（D-04；A-04）

### 4. 完整性清单按生产包树计算摘要

生成器发现根 `@fission-ai/openspec` 和 `node_modules` 中每个实际包目录。每个包摘要按相对路径稳定排序，组合文件类型、相对路径和内容摘要；排除所有嵌套 `node_modules`，让每个依赖独立成行，并忽略可由安装器重建的 `.bin`。清单记录 schema、运行时版本和入口，每个包记录相对目录、名称、版本、声明许可证、文件数和树 SHA-256。（D-05；A-05）

树摘要比逐文件清单更小，同时仍能检测包内文件增加、删除和修改。备选方案是只哈希 `package.json` 与许可证，无法发现可执行代码漂移；逐文件清单则会制造数千行发布噪声。

### 5. 默认检查，显式写入

完整性脚本无参数或 `--check` 时只比较磁盘计算结果与受管 JSON；`--write` 才以原子替换方式更新清单。验证编排器永远使用检查模式。清单不含时间戳和绝对路径，确保跨目录逐字一致。（D-05；A-05）

### 6. 以 0.11.0 发布并更新缓存标识

根包和插件 manifest 升到 0.11.0，manifest 使用新的开发 cachebuster，marketplace 同步展示版本。技能行为不因实现细节新增公开入口；README 只补充统一验证和运行时清单用法。（D-06；A-06）

## Risks / Trade-offs

- [包树哈希增加验证耗时] → 运行时规模有限，按流式文件摘要和稳定枚举实现，并通过测试记录门禁耗时。
- [符号链接在源仓库和缓存中不同] → `.bin` 统一排除；其他符号链接以链接目标文本参与摘要，不跟随到包外。
- [许可证字段可能是对象或缺失] → 规范化字符串/对象为稳定 JSON，缺失值明确记录为 `UNKNOWN`，不联网猜测。
- [框架版本范围解析不完整] → 沿用当前“提取首个数字”的兼容语义，并增加常见 semver 范围回归；不在本轮引入 semver 依赖。
- [CI 与 engines 小版本漂移] → setup-node 固定 `20.19.0`，由结构测试断言与根 engines 一致。

## Migration Plan

1. 保留根提交 `c60e188` 作为完整回退点，在独立分支创建需求和 OpenSpec 变更。（D-01；A-01）
2. 先实现验证编排器和 CI，再扩展 fixture；每一步运行现有测试，避免一次改变多个故障面。（D-02、D-03、D-04；A-02、A-03、A-04）
3. 实现完整性生成器，显式生成受管清单后校验确定性和漂移检测。（D-05；A-05）
4. 更新版本和文档，完成全量、严格及官方验证，随后归档 OpenSpec 变更并重新验证主规格。（D-06；A-06）
5. 如需回滚，恢复到 `c60e188` 或撤销本分支实现提交；运行时内容和清单必须作为一个整体回滚。
