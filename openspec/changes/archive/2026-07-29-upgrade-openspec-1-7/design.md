## Context

插件把 OpenSpec 作为随包发布的固定运行时，而不是项目或机器级依赖。现有 1.6.0 包装器、需求校验器、完成检查器、模板和内部参考共同定义了规划到归档的受控链路。OpenSpec 1.7.0 同时改变了状态、操作输入、路径和 Store 语义，因此需要跨模块升级；单独替换 npm 包无法保证完成门禁仍然成立。

本次设计受以下约束：

- 仅调用插件内置运行时，不探测或调用全局 OpenSpec。
- 默认预览、显式写入，不覆盖非受管业务内容。
- 需求文档是业务事实源；OpenSpec context/guidance 是补充输入。
- 正常完成入口不能传递跳过校验、跳过规格或确认未完成任务的选项。
- 仓库当前没有可用 Git 基线，运行时替换必须先在独立临时目录组装和验证。

## Goals / Non-Goals

**Goals:**

- 将固定运行时安全升级为官方 `@fission-ai/openspec@1.7.0` 生产依赖闭包。
- 让检查、实施和归档显式理解 1.7.0 的状态、路径、动态输入、名称与 Store 来源。
- 保留插件现有需求治理、硬门禁和受管升级语义。
- 为普通变更、合法无规格变更、日期名称和嵌套规格提供回归证据。

**Non-Goals:**

- 不调用全局安装、`openspec update` 或运行时自更新。
- 不为业务项目生成 OpenSpec 上游自带的 Codex Skill。
- 不自动迁移历史变更名、规格目录和需求事实。
- 不扩展新的前端框架专项分析。

## Decisions

### 1. 从官方 npm 包构建独立候选运行时

在临时目录精确安装 `@fission-ai/openspec@1.7.0`，启用 `--omit=dev`、`--ignore-scripts`、`--no-audit` 和 `--no-fund`，再把包入口、资源文件、许可证与生产依赖闭包组装成候选目录。候选目录必须先通过版本、入口、依赖和严格校验，才替换现有目录；原 1.6.0 目录在最终验证前保留为可恢复备份。（D-01、D-02；A-01、A-09）

未选择在当前运行时目录执行 npm 安装，因为这会在核验完成前改变可用版本，也可能把开发依赖或生命周期脚本带入发布物。

### 2. 包装器强制关闭版本检查

包装器向每次内置运行时调用注入 `OPENSPEC_NO_UPDATE_CHECK=1`，调用者不能把它恢复为开启。版本来源继续读取内置 `package.json` 并与固定常量一致，不搜索 PATH。（D-01；A-01）

未调用 `openspec update`，因为插件运行时属于发布物而不是用户机器上的可变工具。

### 3. 完成度由状态模型而不是命令退出码决定

完成检查解析 `status --json`，要求 `isComplete === true`，并逐个验证 artifact 状态。只接受 `done`；只有 `.openspec.yaml` 明确声明 `skip_specs: true` 时，`specs` artifact 才允许为 `skipped`。`ready`、`blocked`、缺失、未知状态、非 specs 的 skipped 或不一致元数据全部在归档预览前阻断。（D-03、D-04；A-02、A-03）

命令成功仅代表 OpenSpec 能读取变更，不能代表规划已完成，因此不再把退出码当作完成证据。

### 4. 动态输入是可见补充，不是授权来源

实施继续读取 `instructions apply --json`；完成预览新增读取 `instructions archive --json`。返回的 context、operationGuidance、warnings 和实际路径纳入结构化结果与证据，但需求状态、验收、任务、严格校验、根目录和写入开关仍由插件门禁决定。（D-05；A-05）

项目模板为 apply/archive 提供插件兼容 guidance，内部参考说明冲突优先级。动态文本不解释为命令参数，也不能触发额外写入。

### 5. 使用运行时返回的具体路径并兼容名称归一规则

路径发现优先使用 `artifactPaths.<id>.existingOutputPaths` 和指令返回的具体文件，不从通配符输出路径推导真实规格。归档目标若变更名已有完整 `YYYY-MM-DD-` 前缀则原样使用，否则只添加一次当天日期。（D-06、D-07；A-04、A-07）

需求关联校验先按目录 basename 完整匹配；仅当目录位于 archive 且名称确实带系统日期前缀时，再尝试剥离一次日期的兼容候选。数字前缀不做转换。

### 6. 机器默认 Store 必须显式选择

包装层检查 OpenSpec JSON 的 `root.source`。本地项目命令若解析到 `global_default`，在任何写入前报错；`nearest` 项目根继续作为默认。未来显式 Store 入口必须携带用户选择并单独验证，不通过动态 guidance 隐式改变。（D-08；A-06）

未自动接受 1.7.0 的机器默认 Store，因为同名变更可能位于项目外，违背项目路径和事实源边界。

### 7. 上游参考采用三方语义合并

以 1.7.0 上游参考为新基线，吸收 context、operationGuidance、skipped 与嵌套路径说明；同时保留插件对需求关联、确认不可绕过、内置运行时和显式完成脚本的更严格规则。项目升级仍只替换 `frontend-ai-workflow:start/end` 之间的受管区块。（D-09；A-08）

未直接覆盖参考文件，因为上游默认流程允许的手工归档或通用选择语义可能绕过插件治理。

## Risks / Trade-offs

- [生产依赖闭包遗漏资源文件] → 从 npm 安装结果组装完整包内容和依赖闭包，并用真实 CLI、严格校验和归档场景验证。
- [把合法 skipped 扩大为通用绕过] → 仅接受 specs artifact，且要求变更元数据与需求 D-03 同时成立，完成入口不新增参数。
- [动态 guidance 与项目规则冲突] → 仅作为结构化补充返回，并在技能参考中声明需求和硬门禁优先。
- [日期前缀兼容回退误匹配] → 完整名称优先；只对 archive 目录的完整日期前缀增加一个回退候选。
- [嵌套规格被通配符或扁平路径漏掉] → 使用运行时 JSON 的 existingOutputPaths，并增加嵌套归档测试。
- [仓库无 Git 基线导致替换难以回滚] → 在临时目录保留 1.6.0 备份，全部验证成功后才清理。

## Migration Plan

1. 建立需求、提案、设计、规格与任务，并在旧运行时上完成规划校验。
2. 在临时目录构建 1.7.0 生产候选，核验版本、入口、许可证和依赖闭包。
3. 备份 1.6.0 运行时，替换候选并先运行版本与当前仓库严格校验；失败立即恢复备份。
4. 更新包装器、门禁、需求关联和版本元数据，运行聚焦回归。
5. 三方合并模板、技能参考、第三方声明和 README，执行全量测试与官方验证器。
6. 在 Vue 3 + Vite fixture 验证初始化、重复执行、升级和检查，再验证缓存重装后的插件版本与运行时。
7. 更新需求验证记录、勾选任务，执行完成预览和显式归档。

回滚时恢复保留的 1.6.0 运行时目录及 0.9.0 版本元数据；不迁移或删除业务项目中的历史 OpenSpec 数据。
