## Context

当前仓库把运行代码、五平台发布源、一次性视觉验收工程和完整历史需求放在同一工作树。AGENTS 已限制 AI 默认读取大目录，但默认 CI 仍下载全部 LFS，完成流程仍把已验收需求留在根目录，统一验证也没有体积预算。参见 `proposal.md`；行为边界以本变更六份 delta spec 为准。

本变更影响 CI、路径、临时目录、子进程、环境变量和机器可读诊断，标记为“跨平台高风险”。受影响平台为仓库真实矩阵声明的 Linux x64/ARM64、Windows x64、macOS Intel/ARM64；聚焦回归、本地统一验证和远端矩阵分别记录，不能相互替代。（D-13；A-08）

## Goals / Non-Goals

**Goals:**

- 在保留精简 AI UI 规范的前提下移除蓝湖一次性验收重资产和原型测试。
- 让历史需求在完成生命周期内自动分层，而不是靠定期人工搬运。
- 用只读预算门禁阻止 outputs、完整活跃需求和超大日常文件重新累积。
- 让开发者和每个 CI 矩阵任务只获取所需平台的 LFS 资产，同时保持真实冒烟与打包。
- 拆分超大模块并提供聚焦入口，但不改变插件公开行为。

**Non-Goals:**

- 不重写 Git 历史、不删除远端 LFS 当前对象、不引入新的制品服务。
- 不把历史蓝湖验证结果迁入插件运行时，也不改变业务项目 UI Review 的能力。
- 不在本地伪造远端五平台成功；未运行的矩阵保持待执行。

## Decisions

### 1. 蓝湖资产采用“保留最终合同、退役验证过程”

保留 `outputs/lanhu-ai-ui-spec/` 的纯 Markdown 和必要本地资产，删除 `outputs/lanhu-design-spec/`、其中的验证工程/图片/生成工具，以及直接依赖它们的 `ai-ui-review.test.mjs` 和 2000 行蓝湖重建测试。新增小型 `lanhu-ai-spec.test.mjs` 只验证最终合同的索引、场景和相对引用。

主规格通过 delta 移除双目录同步、双组件库项目和历史截图门禁。历史 requirements 与 OpenSpec archive 不批量重写业务事实，只通过年度需求归档和索引保持可定位。

替代方案是把完整目录迁入插件或另一个未选定远端；前者会把无关资产带入每个插件包，后者缺少用户选择和可验证发布目标，因此不采用。

### 2. 已验收需求使用“完整归档正文 + 根存根 + 稳定索引”

新增需求目录服务，使用项目路径安全函数规范化目标。完整正文写入 `requirements/archive/<year>/<原文件名>`；根路径写入短 Markdown 存根，包含标题、已验收状态、归档相对路径和关联变更。`requirements/index.json` 按 ID 排序，保存状态、stubPath、archivePath、changes 与正文 SHA-256，不写绝对路径和时间戳。

既有 31 份已验收需求由一次性迁移入口处理：默认预览，显式 `--write` 才移动。未来 `finalize-change` 在 OpenSpec 归档与证据改写后调用同一服务，并从归档正文执行 complete 审计。恢复逻辑同时识别根完整正文、根存根和唯一归档正文，任何多个候选都失败关闭。

只移动全文会破坏旧根路径；只保留全文又无法降低默认读取成本。轻量存根同时保留路径兼容和渐进读取边界。

### 3. 历史审计默认只读根入口，完整历史显式启用

`preview-requirement-upgrade` 和健康检查默认只读取根活跃全文与存根元数据。`verification-evidence` 增加显式历史开关后才读取索引指向的归档正文，结果仍通过现有 summary/code 分页输出。存根与索引不一致返回稳定诊断，不自动修复。

### 4. 体积预算基于 Git 跟踪集合而不是工作树总大小

审计通过无 shell 的 Git 子进程读取 NUL 分隔 tracked paths，并用同一 POSIX 归一化函数比较路径。首版预算固定为：

- `outputs/lanhu-design-spec/` 为禁止回归路径；
- `outputs/` 受跟踪文件不超过 200 个、总大小不超过 10MiB；
- 根目录完整活跃需求不超过 5 份，已验收根文件必须是存根；
- `tests/*.test.mjs` 单文件不超过 1000 行；日常 `plugins/frontend-ai-workflow/scripts/*.mjs` 单文件不超过 800 行；
- runtime、OpenSpec 归档、年度需求正文和持久 UI Review 证据不进入日常单文件预算，但仍受读取路由和专属合同管理。

预算定义放在仓库治理脚本的显式常量中，JSON 输出提供 schema、预算和诊断。统一验证在自动测试之后、结构校验之前执行 `footprint` 阶段。审计永不自动写回当前值；需要调整预算时必须修改需求与规格。

### 5. 大文件以职责边界拆分，入口保持兼容

`workflow.test.mjs` 的夹具帮助器迁入 `tests/helpers/workflow-fixture.mjs`，用例按项目识别/接入、深度上下文、需求治理和 OpenSpec 生命周期拆成多个根级 `workflow-*.test.mjs`，继续被现有 `tests/*.test.mjs` 发现。

`verification-evidence.mjs` 拆出历史审计、证据 manifest/语义和 CLI 编排模块；原文件继续重导出现有公共函数并保留入口。`real-project-validation.mjs` 拆出矩阵配置、工作区准备、执行/报告模块，原 CLI 和稳定字段不变。

### 6. 聚焦测试入口使用显式文件组并防止零发现

新增一个标准库测试配置入口，维护 `repository`、`workflow`、`platform` 三个稳定文件组，以当前 Node 启动 `--test`，执行前确认每组非空且文件存在。根 package 暴露 `test:repository`、`test:workflow`、`test:platform`；全量 `test` 和 `verify` 继续自动发现全部根级测试。

### 7. Git LFS 使用现有远端按平台拉取

CI checkout 关闭自动全量 LFS，随后根据 `matrix.platform` 执行 include 限定的 `git lfs pull`，只获取 `platform-assets/<platform>/**`。运行时检查必须识别 Git LFS v1 指针头、目标缺失和错误平台，返回稳定 code/target；其他平台保留指针不影响当前平台的完整性与包构建。

README 提供轻量克隆流程：跳过 smudge、选择当前平台、拉取目标目录，再运行平台聚焦验证。当前已有完整克隆不会由脚本擅自删除 LFS 缓存；迁移完成后可由用户显式执行可恢复的 `git lfs prune`。

### 8. 版本和未来治理同步进入受管规则

根 package、插件 manifest、README、受管模板和缓存刷新版本同步到 0.18.0。AGENTS 增加“预算例外需正式变更、需求完成自动归档、禁止通过定期批量清理替代生命周期治理”的规则。`validate-structure` 和统一验证确认这些合同存在。

## Risks / Trade-offs

- [删除蓝湖重资产导致历史链接不再直接打开] → 根需求年度归档保留历史文字事实；Git 历史可恢复原文件；活动主规格明确退役边界。
- [需求迁移中途失败造成正文、存根和索引不一致] → 使用安全路径、独占暂存与原子写入，返回实际目标和幂等恢复参数，多候选失败关闭。
- [CI LFS include 在某个平台语法差异] → 使用 Git LFS 自身命令、无 shell 业务脚本回归和真实五平台矩阵；外部未通过前不标记发布完成。
- [文件行数预算诱导机械拆分] → 预算只覆盖日常源码/根测试，拆分必须以职责和公开接口为边界；预算调整仍需正式规划。
- [根存根降低默认历史审计覆盖] → 显式历史开关和索引提供按需完整审计；summary 保留历史条目计数但不展开正文。
- [当前克隆磁盘不会立刻减少 1.2GB LFS 缓存] → 本轮优化后续克隆与 CI；当前缓存只提供用户显式回收说明，不自动执行破坏性清理。

## Migration Plan

1. 先实现并验证需求归档服务、存根/索引格式和恢复回归，再预览迁移既有 31 份需求。
2. 实现蓝湖精简规范测试并确认通过后，删除重资产和直接依赖测试，更新主规格 delta。
3. 实现体积审计和聚焦入口，再拆分超大模块直至预算门禁通过。
4. 修改 CI LFS 流程和平台指针诊断，运行当前平台聚焦、完整性、冒烟与打包。
5. 显式执行既有需求迁移，核对根存根、年度正文、索引与 Git diff；运行全量本地验证和官方 validators。
6. 更新版本与文档。提交后运行真实五平台 CI；失败时记录平台、步骤、稳定 code、根因和新增回归。

回滚时先恢复需求根正文与蓝湖目录的 Git 版本，再撤销完成流程、体积门禁和 CI LFS include；不得删除用户 Git LFS 缓存或重写历史。
