## Context

参见 `proposal.md` 的动机。三个目标文件都是稳定入口，同时包含可独立测试的解析、校验或恢复实现。外部脚本和测试直接从原路径导入函数，因此拆分必须采用“入口重导出 + 内部单向依赖”，不能要求调用方迁移。

当前相关共享链包含路径规范化、原子写入、临时日志、无 shell 子进程、需求/测试方案语义绑定和归档恢复。跨平台高风险命中路径、临时目录、子进程、环境变量和机器可读诊断，受影响平台为现有 CI 的 macOS ARM64/x64、Linux ARM64/x64、Windows x64。

需求依据：D-01～D-08；本设计重点落实 D-02 的行为兼容、D-03 的职责边界、D-04 的文件规模、D-05 的依赖边界以及 D-07/D-08 的跨平台分层验证。

## Goals / Non-Goals

**Goals:**

- 三个稳定入口分别降到 600 行以内，新增模块低于 800 行。
- 原导入路径、导出名称、CLI 参数、退出码、JSON 字段和稳定诊断保持兼容。
- 内部依赖保持单向，公共入口不被内部模块反向导入。
- 让后续局部修改优先只读取一个职责模块和对应专用测试。

**Non-Goals:**

- 不修改任何主规格或可观察行为。
- 不修改 CI、Git LFS、平台运行时存储和检查器仓库类型识别。
- 不增加第三方依赖，不改变证据 schema 或归档文件格式。

## Decisions

### 1. 稳定入口采用重导出兼容层

原三个文件继续承载 CLI 和面向调用方的公开 API。被移动的公开函数由入口显式重导出，内部模块只导入更底层的安全、语义和文件工具，不反向导入入口。

这样现有 `import ... from './finalize-change.mjs'` 等调用无需迁移，也能用模块图静态避免循环。替代方案是直接修改所有调用方导入新路径，但会扩大兼容面并让插件外部消费者失去稳定入口，因此不采用。

### 2. 完成流程按“归档准备与恢复”拆分

新增 `finalize-change-archive.mjs`，承载证据引用改写、测试方案改写、归档目标安全解析、恢复上下文、部分失败结果和恢复执行。`finalize-change.mjs` 保留 `finalizeChange` 正常完成总编排、CLI 解析与入口判断，并从新模块重导出既有公开改写函数。

归档后审计作为注入服务保留明确边界，恢复模块通过参数接收原子写入、需求归档和审计服务，避免硬编码测试替身或形成入口反向依赖。现有 `finalize-change-references.mjs` 继续只负责年度需求引用迁移，不与恢复编排合并。

### 3. 需求校验按“文档解析”和“交付关联”拆分

新增 `requirement-decision-parser.mjs`，承载 Markdown 表格、决策、验收、状态矩阵、验证记录和证据映射解析；新增 `requirement-delivery-validation.mjs`，承载所选变更范围、任务引用、Git 基线、测试文件策略、证据路径和完成状态校验。

`validate-requirement-decisions.mjs` 保留阶段参数解析、各模块结果汇总、最终结构和 CLI。解析模块返回结构化结果并通过数组收集 errors/warnings，不读取项目目录；交付模块才接触 Git、变更目录和持久证据。替代方案是只抽一个大 helper，虽然能降低入口行数，但会继续把纯解析与文件系统副作用混在一起，因此不采用。

### 4. 验证证据按“执行捕获”和“持久清单校验”拆分

新增 `verification-evidence-validation.mjs`，承载证据文件描述符、schema v1/v2 分类、local-command/external-ci/ui-review 清单校验和验证记录审计。`verification-evidence.mjs` 保留命令规范化、无 shell 执行、日志捕获、语义执行前后校验、清单写入和 CLI，并重导出既有校验 API。

新校验模块继续复用 `verification-evidence-foundation.mjs`、语义绑定和 UI Review 状态校验，不复制摘要、路径或指纹算法。这样执行路径与完成阶段的只读审计边界保持清晰。

### 5. 通过结构合同限制后续回长

在现有 `repository-footprint.test.mjs` 或目标功能测试中增加三个稳定入口不超过 600 行的断言；仓库现有 800 行门禁继续覆盖全部新模块。600 行是本需求的入口职责目标，不替换或放宽全仓预算。

### 6. 回归分层与跨平台定位

- 聚焦层：复用 `workflow-requirements`、`workflow-openspec`、`workflow-trust-boundary`、`verification-evidence-integrity`，验证公开重导出、恢复幂等、错误字段、Windows/POSIX 路径和子进程退出码。
- 全量层：运行体积门禁、`npm test`、结构校验、统一验证和官方 validators，证明共享链没有遗漏。
- 外部层：提交后仅以同一 SHA 的五平台矩阵为通过证据；本地路径样本不替代真实 runner。

## Risks / Trade-offs

- [移动函数时遗漏闭包常量或默认服务] → 先按函数依赖簇移动，再由原入口显式导入/重导出；聚焦测试覆盖默认与注入服务。
- [拆分后出现循环依赖] → 内部模块禁止导入三个公共入口；入口只向下依赖，公共重导出不用于内部调用。
- [错误对象或 JSON 字段轻微漂移] → 断言稳定 `code`、`status`、`target`、计数和退出码，同时保留必要中文语义断言。
- [Windows 路径只在本机偶然通过] → 继续使用 `path.win32` 样本与双侧规范化测试，并要求真实 Windows CI。
- [为追求行数产生过碎文件] → 每个新模块围绕一个稳定职责，目标是 2～3 个内部模块而不是逐函数拆分。

## Migration Plan

1. 先增加入口行数与重导出结构回归，确认现有测试基线通过。
2. 拆分完成归档模块并运行完成/恢复聚焦测试。
3. 拆分需求解析和交付校验模块并运行需求聚焦测试。
4. 拆分证据清单校验模块并运行证据/信任边界聚焦测试。
5. 运行体积门禁、全量测试、结构、统一验证和官方 validators。
6. 使用 WebStorm 提交并推送，等待精确提交的五平台 CI。

回滚时只需恢复三个入口和删除新增内部模块；不涉及数据迁移、schema 变化或外部服务。
