## Context

本变更建立在现有真实项目验证的安全能力之上：仓库已经有项目根校验、Git 基线摘要、无硬链接克隆、有界工作区、环境隔离、日志脱敏、资源预算和清理结果，但现有生命周期明确拒绝脏源工作树，也不运行代理任务。三个第一轮候选中有两个包含用户未提交内容，因此新基准必须只克隆 HEAD，同时证明运行前后的分支、提交和状态摘要完全一致，不能复用“源必须干净”的判断。

运行代理使用当前 Codex CLI 的非交互 `exec --json` 与 `exec resume --json` 能力。插件组需要真实加载已安装的 frontend-ai-workflow 技能，对照组必须处于没有受管工作流文件的提交基线。需求生成、执行和验收会跨多个长进程，因此证据协议、恢复状态和隐藏验收隔离需要先于业务运行落地。动机见 `proposal.md`，外部行为合同见 `specs/synthetic-developer-effectiveness-benchmark/spec.md`。

跨平台高风险命中路径、临时目录、子进程、环境变量和机器可读诊断；真实 CI 平台为 darwin-arm64、darwin-x64、linux-x64、linux-arm64、win32-x64。

本设计完整承接 D-01、D-02、D-03、D-04、D-05、D-06、D-07、D-08、D-09、D-10、D-11、D-12；技术取舍不得改变这些需求事实。

## Goals / Non-Goals

**Goals:**

- 用一个默认只预览、显式写入的入口完成项目固定、用例生成、冻结预检、配对执行、隐藏验收、返工、指标汇总和清理。
- 让所有核心计算和状态迁移可使用注入执行器进行确定性测试，普通仓库验证绝不消耗 Codex 额度或访问业务项目。
- 使第一轮本机运行可恢复、可审计，且业务项目已有未提交内容始终留在原地、从未复制、前后摘要不变。
- 用独立评估副本隔离隐藏验收和参考实现，避免执行代理在返工时读取答案。
- 产出机器 JSON、工作簿导入 CSV 和人工复核摘要，保留合成数据与真实开发者指标的边界。

**Non-Goals:**

- 不把 Codex JSONL 的自然语言内容当作唯一事实；路线、进程、验收和 Git 状态都需要独立证据。
- 不追求通用的人类问题理解或完全自动化的误阻断语义判断。
- 不把首次工作流初始化计入单任务耗时，也不比较模型、推理强度或不同验收器。
- 不让真实代理运行进入 `npm test`、`npm run validate` 或默认 CI。

## Decisions

### 1. 使用两层职责、四个限长模块，而不是扩张真实项目矩阵

基础层由 `developer-effectiveness-benchmark-foundation.mjs`、`developer-effectiveness-benchmark-metrics.mjs` 和 `developer-effectiveness-benchmark-process.mjs` 分别承担路径与 Git 隔离、指标与 schema、无 shell 子进程协议；编排层由 `developer-effectiveness-benchmark.mjs` 承担文件生命周期、Codex/ Git/验收调用和阶段推进。四个文件都服从仓库日常脚本 800 行预算，测试只导入纯函数和 runner 的可注入入口。

选择独立能力而不是给 `real-project-validation.mjs` 增加大量阶段，因为现有真实矩阵的合同是“源工作树必须干净且不运行代理”，而本基准需要“允许但排除已有未提交内容、执行长任务并恢复”。两者共享底层安全思路，但不应让普通真实矩阵验证意外获得代理执行或额度消耗。

### 2. 配置路径只存在于进程内，持久证据只保存别名

CLI 接收三个 `--project <id>=<path>` 参数以及 `--run-id`、`--model`、`--reasoning`、`--timeout-minutes`。解析后立刻得到 canonical path，但写入清单时仅保留项目 ID、项目名称、分支、提交、是否存在未提交内容和状态 SHA-256。所有日志在持久化前同时替换 POSIX 与 Windows 表达的业务路径。

输出固定为 `outputs/developer-effectiveness-benchmark/<run-id>/`；运行 ID 仅允许字母、数字、点、下划线和短横线。路径比较双方都经过同一个目标平台规范化函数，Windows 样本显式使用 `path.win32`。输出根、工作区、评估副本和清理目标逐层验证，拒绝根目录、用户主目录、越界路径和符号链接。

替代方案是把本机路径写入矩阵 JSON，但这会产生不可提交的绝对路径、泄漏业务目录并增加误用风险，因此不采用。

### 3. 接受已有未提交内容，但用双摘要证明零影响

源基线包括独立 Git 根、分支、HEAD、`git status --porcelain=v1 --untracked-files=all` 的 SHA-256 和 dirty 布尔值。隔离副本使用 `git clone --no-hardlinks --no-checkout` 后显式 checkout 记录的提交，只包含 Git 对象中的内容。每个阶段结束及整轮结束重新采集源摘要，任何字段变化都标记 `source_baseline_drifted` 并停止新运行。

这与把源目录复制到工作区相比，可以确定排除用户未提交文件；与要求用户先清理工作区相比，不会干扰现有开发工作。

### 4. 用“种子失败、参考通过”冻结可执行用例

需求作者在一次性 author 工作区中按固定复杂度矩阵生成两个候选：P1 为小型和大型，P2 为中型和大型，P3 为小型和中型。每个候选包含：

- `public-requirement.md`：执行代理可读的目标和公开验收边界；
- `seed.patch`：从源 HEAD 构造相同初始状态的受控变化；
- `evaluator.patch` 与 `acceptance.json`：仅评估副本可见的隐藏测试和允许命令；
- `reference.patch`：只用于证明任务存在至少一个通过实现，不向执行代理释放；
- `clarifications.json`：有限问题模式与预先冻结答案；
- `case.json`：项目、复杂度、任务类型、允许路径、返工上限和全部内容 SHA-256。

冻结预检在全新副本中证明“HEAD + seed + evaluator”失败且“HEAD + seed + reference + evaluator”通过。两次命令必须离线可运行；否则候选不进入执行。冻结后只读打开或在每次使用前复算 SHA-256，禁止边跑边改验收。

选择参考实现预检而不是仅让作者声明“可实现”，因为后者无法区分坏需求、坏测试和代理失败。参考实现只证明存在解，不进入效果统计。

### 5. 隐藏验收始终运行在独立评估副本

插件组和对照组工作区只包含 HEAD、seed 和各自代理改动。每次交付后，控制器提取相对 HEAD 的二进制安全 Git diff，并在新的 evaluation 工作区依次应用 seed、代理差异和 evaluator；验收器只在该副本执行。原会话收到经过脱敏、去路径、限长的失败摘要，不会看到 evaluator 或 reference 文件。

直接把隐藏测试复制进代理工作区实现更简单，但返工会话可以读取测试和答案，导致一次验收后的比较失真，因此不采用。

### 6. 用稳定最终响应 schema 驱动澄清、交付和阻断状态机

每次 `codex exec` 或 `codex exec resume` 都传入同一个 final-response JSON schema，要求状态只能是 `delivered`、`needs_clarification` 或 `blocked`，并提供摘要、问题或阻断类别。控制器同时读取 JSONL 中的 session ID、命令事件和最终消息：

- `needs_clarification`：仅当问题命中冻结预案时恢复原 session，计数加一；否则以 `unplanned_clarification` 阻断；
- `delivered`：记录首次交付时间，提取差异并运行隐藏验收；失败且未超过上限时用同一 session 返工；
- `blocked`：记录阻断并执行冻结可用性检查，只有确定性反证时确认误阻断，其余进入 `review-required`；
- 进程启动失败、非零退出、超时和信号中断独立于模型最终状态记录。
- 额度、服务或本地进程不可用属于可恢复的基础设施中断，不写成开发失败样本；恢复时从该组重新执行。到达任务时间上限的真实代理超时仍作为受测行为保留。

首次交付时长从公开需求首次发送到第一次 `delivered`；总周期到最终通过、明确阻断或达到上限。返工次数等于隐藏验收失败后实际恢复的次数，不用 Git commit 数推断。

### 7. 插件准备与任务计时分离，路线使用多证据判定

每个项目先构建一次 plugin-prepared 基线：调用当前插件的初始化逻辑并验证重复执行，准备耗时单列但不进入任务指标。每个插件组运行从该基线创建副本，再应用同一 seed；对照组直接从源 HEAD 创建副本并应用 seed。任务源码起点相同，唯一预期环境差异是插件管理文件和指导内容。

插件提示要求根据已安装插件准入规则处理需求；路线证据综合 JSONL 中读取的技能路径、最终结构字段和产物：完整通道需要匹配需求与 OpenSpec 产物，快速通道需要匹配技能读取事件且不得产生受管产物。对照组提示只包含公开需求和“直接实现并验证”，其工作区若出现新的工作流管理产物则样本无效。

只相信代理自报路线会高估合规；只看产物又无法证明快速通道，因此采用多证据并把证据不足标为无效。

### 8. 子进程入口显式、无 shell，并支持测试注入

生产执行器接受显式 Codex 可执行文件或 JavaScript CLI 入口。JavaScript 入口始终由当前 `process.execPath` 启动；其他入口必须是实际可执行文件，Windows `.cmd`/`.bat` 被拒绝，不为兼容默认开启 shell。所有参数使用数组传递，工作区含空格和非 ASCII 的情况由聚焦测试覆盖。

子进程环境只增加本轮 `TMPDIR`、`TMP`、`TEMP`、缓存和 Git ceiling，保留认证所需环境但不覆盖 `HOME`、`CODEX_HOME` 等系统关键变量。结构化事件边读边解析并有总字节上限；超时先发送温和终止，短暂等待后按真实退出状态强制终止，不能把“已发送信号”误判为“已经退出”，清理失败单独记录。

测试通过 operations 注入假的作者、Codex、Git、验收和时钟执行器，不启动真实代理。真实运行只能由显式 `--write` 加 `--execute-agents` 开启，避免预览或普通测试误耗额度。

当前 Codex CLI 的 `--approve-for-me` 已隐含 workspace-write，写模式不得再同时传 `--sandbox`；只读作者仍显式使用 `--sandbox read-only`。`--smoke-case` 将范围下推到作者和插件准备阶段，只生成目标项目的两条候选并执行其中一条；完整模式继续严格冻结三个项目的六条用例。

### 9. 使用不可变阶段清单和原子证据支持恢复

顶层 `run.json` 记录 schema、冻结配置摘要、阶段状态和 artifact 描述；每个用例与运行使用独立状态文件。写入先落入同目录唯一临时文件，再原子 rename。已完成阶段的输入摘要匹配时跳过，不匹配时以 `resume_input_mismatch` 停止；已完成证据不原地重写。

阶段为 `previewed → authored → frozen → prepared → executing → evaluated → summarized → cleaned`。一次运行失败只关闭该运行；源摘要漂移、冻结内容漂移、无法可靠脱敏的高置信度敏感输出或输出边界失效会关闭整轮后续执行。代码检索中常见的令牌、密码字段赋值只替换值并记录脱敏状态，避免把字段名误判成真实凭据。

### 10. 指标分为运行、配对和汇总三层

`run-metrics.json` 保留原始 ISO 时间、毫秒值、次数、布尔结果、null、状态、路线、diffstat 和证据引用；`pair-metrics.json` 只在两组都有效时计算同用例差异；`summary.json` 按项目、复杂度和执行组聚合。除法分母为零时结果为 null。

`workbook-import.csv` 使用稳定列顺序，能够映射现有工作簿的任务记录页；模拟记录以 `SYN-` 任务 ID 和 `synthetic=true` 标记。摘要只有六个有效配对时才允许 `conclusionStatus=descriptive-comparison`，否则固定为 `insufficient-pairs`。即使配对完整，文字也只能描述本轮模拟任务，不能外推真实开发者收益。

### 11. 第一轮运行与仓库验证分开

聚焦测试覆盖所有状态与平台差异；`npm test`、`npm run validate`、官方 validators 和 Vue 3 + Vite fixture 只验证代码与插件结构，不运行真实作者或执行代理。第一轮三个项目、六个用例、十二次执行作为单独的 V-04 本机证据，需要显式命令、当前账号额度和人工复核。

真实五平台 CI 只运行确定性测试。没有同一提交的矩阵结果时，V-05 保持待执行，本机业务试点不能替代发布级跨平台证据。

## Risks / Trade-offs

- [作者与执行代理可能来自同类模型，存在任务风格偏置] → 固定任务、使用独立隐藏验收、保存模型配置，并把结论限制为合成基准。
- [插件组包含额外指导文件而工作区字节不完全相同] → 源码 HEAD、seed、模型和验收保持相同，初始化成本单列；报告明确环境差异就是实验处理变量。
- [Codex JSONL 事件版本变化] → 只依赖最小稳定字段并保存 CLI 版本；未知事件忽略，缺少 session 或最终结构时样本无效而非猜测。
- [真实项目命令需要网络或未安装依赖] → 作者只能选择离线可重放验收；预检失败就替换候选，不自动安装或访问生产系统。
- [长任务消耗时间和额度] → 先跑聚焦测试和单用例 smoke，再执行六配对；设置单轮预算、超时、返工和澄清上限，已完成证据可恢复。
- [日志或补丁包含业务敏感内容] → 只保留必要摘要，路径和凭据先脱敏；原始工作区按轮清理，输出不自动上传或提交。
- [源工作区在实验期间被开发者修改] → 每个阶段复核分支、HEAD 和状态摘要，一旦漂移立即停止后续运行并保留已完成证据。
- [误阻断语义无法完全自动化] → 只有冻结可用性检查提供确定性反证时确认，其余统一进入人工复核队列。

## Migration Plan

1. 新增 foundation、runner、schema 和聚焦测试，但保持入口默认只预览。
2. 将确定性测试加入 workflow 测试分组，完成本地统一验证、官方 validators 和 Vue 3 + Vite 生命周期。
3. 对一个生成用例执行作者与单组 smoke，确认事件协议、隐藏验收隔离、额度和清理边界。
4. 显式运行三个项目的六用例十二次配对试点，人工复核用例质量和误阻断候选，再导入指标工作簿。
5. 保留真实五平台 CI 为发布证据；未完成时不归档为跨平台交付通过。

回滚时移除新增命令入口、模块与测试；只删除明确的 `outputs/developer-effectiveness-benchmark/<run-id>/` 子目录。业务项目不需要回滚。已生成的本地合成证据可选择保留用于审计，不能被后续运行静默覆盖。
