## Context

参见 `proposal.md` 的 Why。当前 `verification-semantics.mjs` 只生成一种快照，既包含稳定的 D/A/R/TC 语义，也包含 V-* 的“执行内容或环境”。后者会在测试成功后由正常流程补写，因此形成自引用过期。`verification-evidence-validation.mjs` 又总是使用当前默认算法复算，没有按清单中的绑定版本分派。

约束：证据 schema、公开 CLI 和历史 JSON 不做破坏性迁移；只使用 Node.js 标准库；机器诊断保持跨平台稳定；真实命令、定位、日志和工作区新鲜度门禁不能放松。

设计依据：D-01～D-06；对应 A-01～A-04。

## Goals / Non-Goals

**Goals:**

- 让 v2 绑定表达“验证了什么”，而不是重复表达“运行后如何记录结果”。
- 让生成、执行中复核和后续校验使用同一明确版本。
- 让旧 v1 清单继续按旧算法验证，未知版本显式失败。
- 用真实生命周期顺序证明第一次 complete 通过，同时保留真正语义变化负例。

**Non-Goals:**

- 不让证据入口自动编辑 Markdown。
- 不修改机器证据 schema 版本、工作区指纹排除规则或归档流程。
- 不自动迁移历史清单，不新增公共命令或依赖。

## Decisions

### 1. 语义快照使用显式版本白名单

在语义模块中定义当前版本 v2 和兼容版本 v1。构造快照时由版本选择字段集合：v1 完整保留原 `verification.execution`；v2 的 verification 只保留 ID 与类型，其余 D/A/R/TC 稳定语义不变。

选择白名单而不是事后删除字段，因为新增解析字段不会意外进入哈希。没有选择直接从所有版本删除执行说明，因为那会让现有 v1 清单全部失效。

### 2. 生成器默认 v2，校验器按记录版本复算

新证据和执行前后一致性检查使用默认 v2。校验持久清单时先验证 `semanticBinding.version` 是否在支持集合，再把该版本传给复算函数。这样新路径稳定，旧路径保持严格原义，未知版本不能静默降级。

选择嵌套绑定版本而不是提升整个证据 schema，是因为改变的是语义摘要算法，不是命令、日志或证据清单结构；单独版本能缩小迁移面。

### 3. 完成事实继续由 Markdown 门禁检查，不进入 v2 哈希

V-* 的结果、日期、证据路径，TC 状态、结果与证据，以及验收复选状态仍由 `validate-test-plan` 和需求完成校验直接检查。它们不需要再被语义哈希绑定。实际命令由清单 argv 和已绑定的 TC 聚焦命令双重描述，运行说明只是人类可读补充。

### 4. 公开指南明确正常顺序和诊断边界

指南明确：预览、显式执行、只更新完成事实、一次 complete。v2 允许运行说明补写，但不得借此修改 D/A/R/TC 稳定语义；已知 code 直接按合同处理，只有字段缺失或未知故障才读取实现。

### 5. 回归按真实失败链组织

在证据专用测试中生成 v2 清单，再模拟本轮复验的 Markdown 更新并调用 complete 校验，断言一次通过；随后逐项修改真实语义并断言过期。另构造 v1 清单证明原算法兼容，构造未知版本证明失败关闭。工作流测试只锁定公开顺序和禁止常规源码回读的文字合同。

## Risks / Trade-offs

- [v2 排除执行说明可能隐藏命令变化] → TC 聚焦命令仍在绑定中，清单还记录实际 argv；回归同时修改两处时必须判旧或暴露不一致。
- [版本分派被伪造] → 只接受显式支持版本，并用对应版本完整复算哈希，不接受自报摘要。
- [历史 v1 行为难以长期维护] → 保留小型确定性 v1 fixture，版本函数集中在单一语义模块。
- [模型仍可能先失败再读源码] → 公开指南给出一次闭环顺序和已知诊断处理，行为复验作为后续发布证据；代码回归只证明确定性能力。
- [跨平台诊断漂移] → 断言稳定 code、version、target 和状态，不使用绝对路径或完整中文文案作为唯一条件。

## Migration Plan

1. 发布时生成器与校验器同时更新，新清单默认写语义绑定 v2。
2. 已有 v1 清单保持原文件，校验时自动走 v1 复算。
3. 未知版本失败关闭并提示重新生成，不做批量写入。
4. 回滚整个插件版本可恢复旧行为；不得只回滚生成器或校验器一侧。
