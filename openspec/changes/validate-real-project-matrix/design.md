## Context

参见 `proposal.md` 的动机。本仓库现有检查、初始化、升级、测试上下文、证据门禁和 Node Test Runner 回归已经可用；六个目标项目均在 2026-08-24 复核为干净，但它们位于插件仓库之外，包含 npm/Yarn、Vitest/Jest、Vite/Webpack、uni-app 与原生微信等不同历史形态。验证必须同时满足两项约束：取得真实运行证据，并保证原项目源码、锁文件、依赖缓存和 Git 元数据不被验证过程改变。

本变更命中路径、临时目录、子进程、包管理器入口和机器可读诊断，属于跨平台高风险。业务项目只在本机 macOS ARM64 运行；仓库五平台 CI 只证明插件共享代码，不替代业务项目运行。

需求依据：D-01～D-14；验收范围：A-01～A-10。以下技术决策不得扩大该范围。

## Goals / Non-Goals

**Goals:**

- 用固定提交和稳定项目 ID 形成可重复的六项目矩阵。
- 将只读事实核对、可能写入的生命周期、项目测试、人工判断和插件回归分层。
- 通过有界隔离、前后 Git 快照和清理记录证明原工作区未被改变。
- 让失败、阻断、有限支持和产品缺陷可定位，避免“命令存在即通过”或“一个项目通过即完整兼容”。
- 输出可供下一轮缺陷修复和运营支持矩阵直接使用的报告。

**Non-Goals:**

- 不在本变更修复任何插件产品缺陷，不修改六个业务项目。
- 不联网安装依赖，不访问后端、真实账号、远程设计服务或业务数据。
- 不把六项目扩展成 pnpm、React + Vite、真实 Monorepo、多应用或全平台认证。
- 不通过运行全量 coverage、所有构建或开发服务器来制造验证数量。

## Decisions

### 1. 使用固定矩阵清单，不做目录批量自动挑选

矩阵以 P1～P6 的稳定 ID、规范化路径、分支、精确提交、项目角色和期望边界为输入。每轮开始重新读取 Git 和项目事实，并把实际值与清单比较；提交或工作区漂移只阻断该项目的写入型阶段。

备选方案是每次扫描三个父目录并自动选择“最像”的项目。这样会因目录新增、依赖变化或 AI 判断改变样本，导致两次结果不可比较，因此不采用。

### 2. 原工作区只读，隔离副本从本地 Git 对象创建

只读识别直接针对原工作区，以保证依赖、配置和测试目录事实真实。任何可能写入的阶段都在 `outputs/real-project-validation/<run-id>/workspaces/<project-id>/` 执行；副本从本地仓库精确提交建立独立 Git 数据，不访问远程，也不使用会修改源仓库 worktree 注册信息的 `git worktree`。

生命周期验证只需要受跟踪源码，不复制原项目的未跟踪文件、`.env` 或依赖目录。原生测试需要已有依赖时，先计算磁盘预算并将 `node_modules` 复制到对应隔离副本；符号链接落点越界、依赖缺失或空间不足一律阻断，不降级到原工作区运行，也不执行安装。

备选方案是在原工作区运行并用 `git status` 善后。测试缓存和被忽略文件可能不被 Git 状态发现，无法证明零污染，因此不采用。使用 `git worktree` 虽然节省空间，但会修改源仓库 Git 元数据，也不采用。

### 3. 每个项目按相同阶段状态机执行，但测试深度由真实证据决定

阶段固定为：baseline → inspection → lifecycle → native-test → boundary-review → cleanup。P1～P6 都执行 baseline、inspection 和 lifecycle；native-test 仅在已有命令、运行器、目标文件和可安全隔离依赖时执行。

- P1：Vue 3 + Vite + Vitest，验证首版认证闭环。
- P2：Vue 2 + Webpack + Jest，验证大型非 Vitest 项目与最窄可用入口。
- P3：React + Webpack + Yarn/Jest，验证 Yarn 命令、老版本工具链与零测试/目标定位边界。
- P4：Vue 2 + Vite/Webpack 混合链，验证 preset 不掩盖混合事实，并运行已有最窄测试。
- P5：uni-app + Yarn + 嵌套 package，验证根 package 边界和缺测试命令阻断。
- P6：原生微信小程序，验证轻量识别与缺自动测试/开发者工具认证阻断。

备选方案是为所有项目统一执行 `test`、build 和 coverage。它会扩大历史失败、时间和副作用，也违背相称验证原则，因此不采用。

### 4. 机器状态和人类判断分开保存

自动阶段只产生稳定项目 ID、stage、status、code、argv、exitCode、计数和受控附件描述；原始绝对路径只用于本机执行，不作为唯一断言。人类报告补充框架混合、结论措辞、缺口和缺陷影响，但不能覆盖机器失败。

状态语义固定：`passed` 表示该单元的已声明断言已真实满足；`limited` 表示存在事实或运行证据但不足以认证更大范围；`blocked` 表示因安全、命令、依赖、目标或环境缺失未执行/未闭合；`defect` 表示实际插件行为违反规格或项目事实。正确阻断可以证明守卫有效，但被阻断能力本身仍未通过。

### 5. 子进程和缓存使用显式、可审计边界

验证命令保存 argv 数组并禁用默认 shell。插件自己的 JavaScript CLI 通过当前 `process.execPath` 启动；包管理器只执行项目已声明的脚本，不解析或补造脚本。在 Windows 共享回归中不直接启动 `.cmd` 包装器；POSIX 与 Windows 路径样本均先规范化再比较。

本轮设置的临时目录和 npm/Yarn 缓存都指向当前 run 的有界目录，不覆盖 `HOME` 等系统关键变量。子进程分别保留启动失败、非零退出、零测试发现、产品断言失败和超时；清理失败作为第二错误报告。

### 6. 证据按项目、阶段和验证 ID 双重索引

`outputs/real-project-validation/<run-id>/` 保存 baseline、inspection、lifecycle、test-runs、boundaries、plugin-validation 和 report；OpenSpec 的 V-02/V-03/V-04/V-06 机器证据引用对应持久附件的相对路径、大小和 SHA-256，V-01/V-05/V-07/V-08 保留人工环境与结论。

日志默认只保存必要摘要；发现疑似密钥、Cookie、环境变量值、业务响应或未跟踪正文时不持久化原文，并将对应单元阻断给人工复核。旧 run 不参与新鲜度判断，也不得被新 run 清理。

### 7. 验证与修复使用两个变更闭环

本变更允许新增验证专用回归、执行资料和支持结论，但不更改被验证的产品判断逻辑。若矩阵发现缺陷，先在本轮报告中固定项目提交、输入、预期、实际、稳定错误字段和影响，再为每个可独立交付的根因建立新的受管变更。修复后使用同一项目、提交、阶段和断言复验，不改换样本来关闭问题。

## Risks / Trade-offs

- [风险] P1～P4 的依赖目录复制可能消耗大量磁盘和时间。→ 运行前记录逐项目大小与可用空间，逐项目准备并及时清理；空间不足时明确阻断，不安装或复用原目录写入。
- [风险] 老项目依赖包含绝对符号链接、本机原生模块或只在特定 Node 版本可运行。→ 记录 Node/平台、检查链接边界，把不安全依赖和 ABI 问题分类为环境阻塞，不改锁文件或降级依赖。
- [风险] 历史测试本身失败。→ 保留实际退出码和最窄命令结果，区分插件缺陷、项目断言失败、历史无关失败与环境阻塞。
- [风险] 本机运行成功被误写为跨平台。→ 报告固定证据层级；业务项目标注 macOS ARM64，插件代码变更仍要求精确提交五平台 CI。
- [风险] 输出日志泄露业务信息。→ 只收集命令与稳定摘要，敏感形态触发阻断，附件入库前记录相对路径、大小和哈希。
- [权衡] 不使用远程依赖安装会使部分真实测试无法运行。→ 这是有意的安全边界；`blocked` 比污染项目或偷偷联网更可信。

## Migration Plan

1. 先落地矩阵与测试计划，在任何命令执行前重新复核六项目基线和磁盘预算。
2. 依次完成只读识别、隔离生命周期、P1～P4 原生测试、P5/P6 阻断与边界复核，每层单独保存证据。
3. 执行插件聚焦与统一验证；若只产生规划和证据，不提升五平台发布结论；若新增验证代码，则提交后复核精确 SHA 五平台 CI。
4. 汇总支持矩阵、缺陷清单和未覆盖范围；缺陷进入独立变更后再按相同基线复验。
5. 回滚仅删除本轮明确创建的隔离子目录和未提交验证代码/资料；原业务项目无需回滚，持久报告按仓库历史保留。
