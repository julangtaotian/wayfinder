## Context

参见 [proposal.md](./proposal.md) 的动机。本变更同时影响初始化/升级、Wayfinder 迁移、UI Review、验证证据和完成归档，是跨模块安全变更；现有代码已有多套“项目相对路径”检查，但对项目内符号链接的处理不一致，部分写入点还直接调用文件系统。当前机器证据 schema v1 已记录工作区指纹、日志和附件摘要，但验证端没有复算全部持久产物，也没有独立绑定 `requirements` 与 `openspec` 中的当前验收语义。

仓库只允许 Node.js 标准库，必须保留默认 dry-run、显式写入、受管内容保护和历史只读兼容。变更命中路径、临时目录、子进程、结构化诊断与 CI 证据，按跨平台高风险处理；本地聚焦、本地统一验证和真实五平台矩阵是三层独立事实。

本设计覆盖 D-01、D-02、D-03、D-04、D-05、D-06、D-07、D-08、D-09、D-10、D-11、D-12，并落实 A-01、A-02、A-03、A-04、A-05、A-06、A-07；后续任务不得缩减或扩展该映射。

## Goals / Non-Goals

**Goals:**

- 用一个共享合同约束所有目标项目 mutation，在普通目录、项目根别名、内部符号链接和路径变化下产生一致结果。
- 让 schema v2 证据分别证明“实现/测试工作区未变”“当前验收语义未变”“持久证据未变”，避免一个过宽或过窄的摘要承担全部职责。
- 让 UI Review、external-ci 和顶层完成状态使用明确的信任等级，任何非可信子状态都不能被折叠为通过。
- 保留现有公共入口与历史读取路径，使调用方可以逐步迁移且无需批量改写归档内容。

**Non-Goals:**

- 不解决拥有仓库写权限的恶意作者同时伪造源码、需求和完整历史的问题；本变更不是签名或远程证明系统。
- 不为 GitHub/GitLab、Figma/蓝湖新增联网读取器，也不改变动态项目识别、Monorepo 编排或测试 runner 支持范围。
- 不重写 OpenSpec 运行时；只在调用内置运行时前后保护插件可确定的目标项目 mutation 表面。

## Decisions

### 1. 建立共享的无符号链接 mutation 边界

新增一个仅依赖 Node.js 标准库的项目路径安全模块，负责：解析项目根入口为唯一真实目录；规范化项目相对路径；使用 `lstat` 从真实根逐段检查每个既有节点；拒绝根以下任何符号链接、越界、空段、父级穿越和跨平台绝对路径；为尚不存在的普通目标返回最近安全祖先与规范化目标。UI Review 现有路径函数保留导出兼容，但改为委托共享模块，避免调用方接口变化。

选择“内部符号链接一律拒绝”，而不是只拒绝最终真实路径越界。后者允许预览与写入之间的落点语义发生变化，也难以在不同入口保持一致；严格拒绝会牺牲少量有意使用项目内链接的便利，但只作用于插件受管 mutation 目标，不限制业务构建和依赖读取。

所有 mutation 都执行两层检查：规划阶段生成动作前检查一次，紧邻创建/覆盖/移动/删除前再检查一次。共享写入辅助负责安全建目录、独占临时文件、同目录原子替换和失败清理；删除辅助只接受已经再次确认的普通文件。初始化、升级、迁移、证据、UI Review 与 finalize 调用点逐个迁移，不改变其原有受管内容决策。

Node.js 没有跨平台统一的 `openat`/`O_NOFOLLOW` 目录句柄链，因此无法完全消除恶意并发替换的 TOCTOU 窗口。这里采用紧邻操作复核、独占临时文件、原子替换和操作后边界确认，将风险限制在本地协作工具的合理威胁模型内；不通过扩大权限或跟随链接来“兼容”竞态。

### 2. 对内置 OpenSpec mutation 做表面预检，不分叉运行时

finalize 在调用内置 OpenSpec archive 前，预检 `requirements`、所选活动变更、archive 根、涉及的 delta/main spec 目标及其既有祖先；运行时返回后，再对实际归档目标做相同检查，才允许需求与测试方案原子改写。若引擎内部失败，保留其原始错误和现有部分恢复合同。

选择调用边界预检而不是修改内置 OpenSpec。分叉运行时会扩大升级和兼容成本，也偏离本变更范围；插件已经能从 status/instructions 获得具体路径，足以在自身授权 mutation 前建立失败关闭边界。

### 3. schema v2 使用三个相互独立的完整性层

新清单继续保存排除生命周期目录的实现/测试工作区指纹，并新增：

- `semanticBinding`：保存算法、最新需求修订、关联 D/A/V/TC ID 集合和规范化语义摘要；
- `logs` 与 `artifacts` 文件描述符：统一保存项目相对路径、字节数和 SHA-256；
- kind 专属合同：local-command 保存真实命令与定位，ui-review 保存运行身份和关键产物，external-ci 保存外部引用但不自带可信提升能力。

语义摘要从结构化解析结果构造稳定对象：当前 V-* 的类型与可观察执行说明、验收映射关联的 A-* 断言、这些 A-* 关联的已确认 D-* 取值、对应 TC-* 的前置/操作/可观察断言/定位和关联关系，以及最新 R-* ID。执行日期、结果、证据路径、勾选状态和用例运行结果不进入对象。序列化按键排序、ID 排序后计算 SHA-256。

选择结构化选择性摘要而不是整份 Markdown 哈希。整文哈希会在写回验证结果、证据路径和验收勾选时立即让证据自我失效；继续只用工作区指纹又无法发现验收语义变化。解析缺失、重复或关联歧义时 v2 生成与严格验证都失败关闭，不猜测关系。

### 4. 文件描述符由同一验证器生成和复算

抽取统一文件描述符与校验逻辑，生成时和完成时都使用相同的安全路径解析、普通文件检查、字节数和 SHA-256 算法。严格验证按清单逐项复算，返回首个或全部可定位诊断；任何必需文件缺失、经链接、大小变化或摘要变化都会使当前 evidenceId 失败。完成阶段不重跑命令。

日志继续写入有界 `outputs/verification-evidence/<change>/<V-ID>/`，证据清单继续位于活动变更 `evidence/`。写入清单前再次验证日志和附件描述符，防止“记录的摘要”和实际持久文件来自不同状态。

### 5. UI Review v2 复用运行状态合同，不接受只存在的 JSON

UI Review 清单验证先通过安全路径读取状态，再使用现有状态校验规则解析 schema；随后比对 runId、scenarioId、scenarioFingerprint、actualCapture、状态文件项目相对身份和 `status === passed`。关键产物集合从通过状态的必需产物合同确定，并与清单中的文件描述符双向匹配；状态声明但清单缺失、清单多报、产物变化都失败。

选择复用状态合同而不是复制一套宽松 JSON 字段判断。这样 UI Review 状态升级仍由其能力负责，机器证据只负责绑定和完整性，不会出现两个互相矛盾的“通过”定义。

### 6. 使用显式信任格而不是把 `ok` 当成 passed

校验结果区分“结构可读”和“可满足严格门禁”。本地命令与合格 UI Review 可分别形成 `local-captured`、`ui-review-state` 的可信 passed；没有可信远程读取回执的 external-ci 固定为 `external-recorded`，其本地 `remotelyVerified` 字段不参与提升。历史 schema v1 可在非严格只读审计中返回 `legacy` warning，但活动 `verification_evidence: required` 只接受 v2 可信 passed。

`validateVerificationEvidenceRecords`、需求校验、test-plan complete、check-change 和 finalize 共享同一聚合规则：只有所有必需项 `status=passed` 且 trust 属于允许集合时，顶层才是 passed。warning/recorded/inconclusive/blocked/failed/stale/unknown 保持原语义，并透传 code、target、trust、evidenceId。这样 `ok: true` 只表示结果被成功解析，不能再充当完成事实。

### 7. 以专用跨入口测试文件锁定边界

新增 `tests/workflow-trust-boundary.test.mjs`，使用仓库现有 Node Test Runner、隔离 fixture、普通文件哨兵和可用平台上的真实符号链接覆盖 mutation 与证据。Windows 路径语义使用确定性输入覆盖，真实文件系统差异仍由五平台矩阵证明。测试只断言稳定 code/status/target/trust/evidenceId；平台路径和中文文案作为辅助。

聚焦测试先锁定新增行为，再运行 `npm test`、`npm run validate`、`npm run verify` 与官方 validators。最终提交的 Linux x64/ARM64、Windows x64、macOS Intel/ARM64 矩阵由人工复核运行链接，因为本变更明确禁止没有可信远程读取器的本地清单自动宣称远程通过。

## Risks / Trade-offs

- [已有项目有意把插件受管文件放在内部符号链接上，升级后会被拒绝] → 诊断定位具体 target，保留零写入并要求用户改用普通目录；不静默跟随链接。
- [路径辅助迁移遗漏某个直接文件系统写入点] → 先建立 mutation 清单与专用反向测试，再逐入口迁移；仓库搜索检查保留为任务和验证项。
- [需求或测试方案解析过严导致证据无法生成] → 只消费现有模板的稳定表格/字段，歧义返回具体 ID；不退回整文哈希或跳过绑定。
- [v2 使活动中的旧 v1 证据立即阻断] → 保留 v1 只读诊断和明确迁移提示；不改写历史，活动变更通过原受控入口重新取证。
- [external-recorded 不再自动通过会暂时降低 CI 自动闭环程度] → 这是预期的失败关闭行为；当前用人工 V-* 记录真实矩阵，远程可信读取另立变更。
- [紧邻复核仍不能抵御恶意并发 TOCTOU] → 在文档中明确威胁边界，使用独占临时文件和原子操作缩小窗口；不夸大为强对抗沙箱。

## Migration Plan

1. 先落共享路径安全模块和专用回归，将现有 UI Review 安全解析委托给它，但保持原导出与普通路径行为。
2. 按 bootstrap/update、Wayfinder migration、verification/UI Review、finalize 顺序迁移 mutation；每组迁移后运行对应聚焦用例，出现兼容回归可只回退该调用点。
3. 增加 schema v2 生成、语义绑定和文件描述符复算；保留显式 v1 只读分支，不批量转换历史 JSON。
4. 收紧 UI Review、external-ci 与聚合状态，完成 plan/implement/complete 结构校验和错误字段回归。
5. 运行本地分层验证并提交最终改动；只有最终提交五平台矩阵全部成功后，人工完成 V-05 与交付结论。

回滚时优先按调用点撤销共享 mutation 接入或 v2 聚合入口，不删除 v2/v1 历史证据，不覆盖业务项目内容。若正式归档在引擎成功后失败，继续使用现有部分恢复入口，以实际归档目录为事实源完成幂等修复。
