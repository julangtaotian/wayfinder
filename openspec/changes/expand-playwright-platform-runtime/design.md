## Context

参见 `proposal.md`。当前共享 Playwright 1.62.1 运行时与平台资产已经分离，`playwright-runtime.mjs` 负责平台选择和完整性，`build-playwright-platform.mjs` 通过 Playwright 的主机平台覆盖下载发布资产。现有实现把两平台数组、下载映射和结构校验文件列表分别硬编码，扩展时容易漏改；同时只有 Linux x64 CI 提供非本机真实启动证据。

约束来自 REQ-2026-020 D-08、D-10、D-13：目标项目零安装、运行阶段零下载、平台资产独立、固定 Playwright 版本、许可和摘要必须校验，且支持结论必须来自对应原生环境。

## Goals / Non-Goals

**Goals:**

- 用一个稳定的平台描述表驱动支持列表与构建主机映射，避免多处平台集合漂移。
- 新增 `darwin-x64`、`linux-arm64`、`win32-x64` 独立运行包，同时保持现有两平台元数据兼容。
- 让结构校验、完整性生成、专用测试和 CI 从同一五平台集合得出结论。
- 在五个平台的原生 GitHub Runner 上执行相同的真实 Chromium 冒烟。

**Non-Goals:**

- 不支持 Windows ARM64、Linux ARM32、其他浏览器或运行时按需下载。
- 不修改 UI Review 配置、状态、适配器、比较器或自动修复合同。
- 不把多个平台浏览器合并为一个可互相回退的通用目录。

## Decisions

### Linux ARM64 授权文件补齐

Playwright 的 Linux ARM64 Chromium headless shell 压缩包不包含授权文本。构建器必须从仓库内同版本的 Linux x64 运行包复制通用 `LICENSE.headless_shell` 到 Linux ARM64 独立目录，再执行完整性校验；缺少来源文件时构建失败并回滚，不允许发布缺少授权文件的平台包。

### 1. 以 Node 平台键作为唯一公共标识

公共索引继续使用 `${process.platform}-${process.arch}`，本轮固定为五个键：`darwin-arm64`、`darwin-x64`、`linux-x64`、`linux-arm64`、`win32-x64`。构建脚本在内部把它们分别映射到 Playwright 1.62.1 的 `mac15-arm64`、`mac15`、`ubuntu24.04-x64`、`ubuntu24.04-arm64`、`win64`。

选择该方案是因为运行时无需理解 Playwright 私有主机命名，也不会把 Windows 的 Node 标识误写成 `win64`。备选方案是在元数据中直接公开 Playwright 主机名，但会让运行时合同依赖上游内部命名。

### 2. 平台元数据与完整性清单继续逐包落盘

每个平台保留 `platforms/<key>.json`、`platform-assets/<key>/.local-browsers/` 和 `integrity/<key>.json` 三部分。新增元数据明确记录 Chromium headless shell 与 FFmpeg 的平台原生相对路径；完整性生成遍历全部五个平台，不把某个平台文件计入共享清单。

选择逐包清单是为了延续缺包、混装和摘要变化的失败关闭语义。备选方案是单一总清单，虽然文件更少，但无法清晰归因平台污染，也不利于后续拆分发布。

### 3. 构建命令保持预览优先并禁止覆盖

`build-playwright-platform.mjs --platform <key>` 继续只输出计划；只有 `--write` 才下载到临时目录，成功后原子移动并重建完整性清单。平台描述表提供主机覆盖值，现有最终目录仍禁止覆盖，失败只清理当前临时目录。

选择延续现有维护入口可保持发布过程可审查。备选方案是 CI 每次动态下载浏览器，但这违反运行阶段零下载和发布物自包含要求。

### 4. CI 使用五项原生 Runner 矩阵

验证矩阵使用 `macos-15`、`macos-15-intel`、`ubuntu-24.04`、`ubuntu-24.04-arm`、`windows-2025`，分别设置期望平台键。每项检出 Git LFS 资产、安装固定 Node 20.19.0，并运行统一验证；平台测试必须断言当前键受支持且 `smoke.skipped === false`。

选择原生 Runner 是因为交叉下载只能证明资产存在，不能证明操作系统装载器、权限和动态库满足真实启动。备选方案是在单一 Mac 上只做完整性检查，不能满足五平台支持证据。

### 5. 专用平台测试由集合驱动

继续复用 `tests/ui-review-platform-runtime.test.mjs`。fixture 为五个平台生成最小独立资产，断言共享清单不包含平台文件、每个平台只能引用自身目录、所有清单都能验证，并保留缺包、混装、摘要变化和未支持平台测试；真实浏览器测试只启动当前原生平台包。

### 6. Windows 原生验证保持文本、路径和测试进程可移植

仓库文本统一以 LF 检出，Playwright 的 LFS 平台资产继续显式使用 `-text`，避免 Windows 自动转换内置运行时文本后触发完整性误报。传给 Git pathspec 和诊断信息的仓库相对路径统一使用正斜杠；需要模拟 FFmpeg 的测试通过 Node 可执行文件加脚本参数启动，不依赖 Windows 不支持的 shebang 执行语义。

这些调整只修正原生验证基础设施，不改变 UI Review 的配置、运行结果或平台支持范围。继续保留字节级完整性校验，不在运行时对已检出的文件进行换行归一化，以免掩盖真实篡改。跨平台测试在比较 OpenSpec 返回的原生路径前统一路径分隔符，但不改写运行时实际输出。

### 7. Windows 运行副作用与规范路径采用精确兼容

Windows Chromium 首次启动会在浏览器可执行文件旁生成 `debug.log`。完整性遍历只排除 `win32-x64` 元数据所指可执行文件同目录下的这一条固定路径；其他日志、缓存或新增文件继续按未登记文件阻塞，避免把宽泛忽略规则变成完整性漏洞。

OpenSpec 1.8 会把规划根规范化为文件系统真实路径。完成门禁比较项目根时同步使用原生真实路径，并仅在 Windows 上折叠大小写，兼容盘符大小写、短路径别名和规范化结果差异；`global_default` 与真实跨目录结果仍然阻塞。

## Risks / Trade-offs

- [三个新增浏览器包显著增加 Git LFS、检出和插件缓存体积] → 保持平台目录独立和 LFS 跟踪，不在普通 Git 对象中存储二进制；CI 只运行一次统一验证任务/平台，避免额外重复矩阵。
- [Linux ARM64 GitHub Runner 仍处于公开预览，可能出现容量或镜像波动] → 固定 `ubuntu-24.04-arm` 并把基础设施故障与产品测试失败分开报告，不以跳过替代证据。
- [Windows 路径分隔符与 `.exe` 命名不同] → 元数据统一使用 POSIX 相对路径，运行时现有安全路径函数负责转换；新增 Windows fixture 和原生冒烟共同验证。
- [Windows Chromium 启动后产生诊断日志] → 只按元数据计算并排除可执行文件旁的固定 `debug.log`，专用测试同时证明任意其他新增文件仍被阻止。
- [交叉下载成功但平台资产目录结构发生上游变化] → 构建后立即按元数据检查浏览器、FFmpeg 和许可路径，再生成清单；路径变化会阻塞而不是发布不完整包。
- [五平台全量完整性遍历耗时增加] → 保留共享与平台分片清单；后续若需要拆分发布，可在不改变运行时平台键的前提下按包分发。

## Migration Plan

1. 先扩展平台描述、测试和结构校验，使缺少新增资产时验证明确失败。
2. 用预览确认三个新增平台的下载目标，再通过受控构建命令生成资产、元数据和五平台完整性清单。
3. 本机验证全部清单与当前 `darwin-arm64` 真实启动，随后提交 LFS 指针。
4. 启用五平台 GitHub Actions 矩阵，收集每个平台 `platformKey`、`skipped=false` 与截图字节数证据。
5. 五个平台全部通过后更新 V-17、关闭 A-10/A-12，并提升插件缓存版本验证安装副本。

回滚时整体移除三个新增平台的元数据、资产和清单，并恢复两平台列表与 CI；不得保留宣称支持但缺少资产的索引项。
