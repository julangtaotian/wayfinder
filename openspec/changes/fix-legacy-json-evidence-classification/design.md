## Context

见 `proposal.md`。当前解析链先抽取验证记录中的全部持久路径，再把所有 `.json` 文件送入机器证据清单校验；该分类没有区分普通资料与 V-* 机器证据。诊断生成时又无条件把解析失败标为 `failed`，使未启用严格合同的历史记录也被完成门禁阻断。

实现必须保持 Node.js 标准库约束、现有证据 schema、稳定机器字段和路径安全规则。（D-04）跨平台影响链命中路径规范化与结构化诊断，适用 Linux x64/ARM64、Windows x64、macOS Intel/ARM64。（D-05）

## Goals / Non-Goals

**Goals:**

- 在路径已规范化后稳定识别显式机器证据候选。
- 让历史无效候选保持可见警告，同时维持新合同失败关闭。
- 保留普通 JSON 的存在性、越界和符号链接安全检查。

**Non-Goals:**

- 不推断普通 JSON 的内容语义，也不迁移或改写历史记录。
- 不改变证据 schema、生成命令、归档流程或外部 CI 信任模型。
- 不新增依赖、后台服务或远程查询。

## Decisions

### 1. 用规范化相对路径识别机器证据候选

候选条件为文件名匹配 `V-<数字>.json`，或路径任一目录段为 `evidence`。路径比较统一把分隔符规范化为 `/`，文件名匹配不区分大小写，从而覆盖 POSIX 与 Windows 表达。（D-01、D-05）

选择路径约定而不是尝试解析每个 JSON，是因为机器证据已有固定生成位置与 V-* 命名，内容探测会继续误读普通配置，并增加不必要的文件读取。普通 JSON 仍保留在持久路径校验结果中。

### 2. 诊断严重级别由合同开关决定

机器候选解析失败时，`verification_evidence: required` 为真则保持 `failed`，否则返回 `warning`。稳定的 `code`、`target`、`evidenceId` 不变，便于既有消费者定位问题。（D-02、D-05）

不选择完全忽略历史无效候选，因为这会隐藏已经显式采用 V-* 或 `evidence/` 约定的损坏资料；warning 同时满足可见性与历史可读性。

### 3. 新合同缺失证据判断保持独立

严格合同仍按自动 V-* 查找同 ID 有效机器证据。只引用普通 JSON 时，候选集合为空并返回 `machine_evidence_missing`，不会被普通持久资料抵消。（D-03）

## Risks / Trade-offs

- [历史机器文件使用非标准命名且不在 `evidence/`] → 继续按普通资料处理并保留历史兼容警告；新合同只能接受受管生成位置和 V-* 命名。
- [Windows 分隔符导致目录段漏判] → 在分类前统一分隔符，并复用现有跨平台路径回归。
- [warning 被调用方误升级] → 聚焦断言校验器最终 `ok`、诊断 `status` 和稳定 `code`，不只断言中文文案。
- [修复意外放宽新合同] → 同一测试同时覆盖普通 JSON 缺失机器证据仍返回 `machine_evidence_missing`。

## Migration Plan

1. 先补充 TC-03 回归，稳定复现历史普通 JSON 误判。
2. 修改候选分类与诊断严重级别，运行聚焦和仓库统一验证。
3. 用官方 validators 校验 Skill/Plugin，更新插件 cachebuster 并重装本地插件。
4. 写入 V-01、V-02 本地机器证据；当前修复形成提交后取得 V-03 五平台原生矩阵，再完成变更。

回滚时恢复分类逻辑和对应测试即可；不删除或改写已有证据文件。
