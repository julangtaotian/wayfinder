# synthetic-developer-effectiveness-benchmark Specification

## Purpose
为真实前端项目提供安全、可重复且可审计的合成配对基准，在不修改业务仓库的前提下比较插件组与对照组的交付过程，并诚实区分模拟结果、无效样本和真实开发者效果。

## Requirements

### Requirement: 基准必须先固定安全且可重复的项目基线

系统 MUST 默认只预览，并在任何写入或代理执行前校验项目路径、独立 Git 根、分支、40 位提交、工作树状态摘要、运行 ID、模型配置、时间预算、任务规模与输出边界。业务项目已有未提交内容 MUST 被排除在隔离副本之外，且运行前后的分支、提交和状态摘要 MUST 完全一致。持久证据 MUST 使用项目别名和提交标识，不得包含业务项目的开发机绝对路径（D-01～D-03、D-10、A-01、A-05）。

#### Scenario: 合法配置只产生无写入预览
- **WHEN** 用户传入三个可读取项目及完整运行参数，但没有显式写入选项
- **THEN** 系统返回三个项目别名、分支、提交、六个需求、十二次运行和输出相对位置，且不创建工作区、不调用代理、不改变源仓库或既有输出

#### Scenario: 危险或运行期漂移基线失败关闭
- **WHEN** 项目指向文件系统根、用户主目录、非独立 Git 根、非预期提交，或分支、提交、已有工作树状态摘要在运行期间发生变化
- **THEN** 系统以稳定 `code`、`target`、`status` 和真实退出状态阻止受影响阶段，不用人类消息或平台路径作为唯一定位

#### Scenario: 已有未提交内容被排除但保持不变
- **WHEN** 项目开始运行前已有用户未提交内容，但分支、HEAD 和状态摘要能够读取
- **THEN** 系统仅从已提交 HEAD 创建隔离副本，记录未提交内容已排除，并在运行结束后证明源项目状态摘要没有变化

### Requirement: 模拟需求必须在执行前生成、校验并冻结

系统 MUST 为每个项目生成两个不依赖真实账号或生产接口的模拟需求，总计六个用例并覆盖小型、中型和大型复杂度。每个用例 MUST 在任一执行组启动前冻结公开需求、受控初始补丁、允许命令、澄清答案、隐藏验收器与内容摘要；执行代理只能读取公开需求和按需释放的澄清答案（D-01、D-02、D-06、D-11、A-02）。

#### Scenario: 六个用例通过冻结预检
- **WHEN** 需求生成阶段得到每个项目两个候选，并且所有候选的初始补丁、公开需求、允许命令和隐藏验收器均可在隔离副本执行
- **THEN** 系统写入带稳定任务 ID、项目 ID、复杂度、文件摘要和 SHA-256 的冻结清单，并在任何配对运行前停止修改这些内容

#### Scenario: 不可验收候选不能进入运行
- **WHEN** 候选依赖真实登录、生产写入、远程权限、不受控网络、越界命令、重复任务 ID、空验收器或无法重放的初始补丁
- **THEN** 系统替换候选或以稳定阻断状态停止整轮执行，不得通过放宽验收或向代理泄露隐藏实现继续运行

### Requirement: 配对运行必须隔离插件组和对照组

系统 MUST 为同一用例建立两个从相同提交和初始补丁派生的独立工作区，并使用相同模型、推理强度、时间预算、公开需求、澄清预案与验收器。插件组 MUST 记录真实工作流路线，对照组 MUST 不调用 frontend-ai-workflow 技能或产生工作流管理产物（D-03～D-05、A-03）。

#### Scenario: 插件组完成工作流准备后开始计时
- **WHEN** 插件组工作区尚未完成项目工作流初始化
- **THEN** 系统先在可复用基线上完成初始化并单独记录准备时长，任务的首次交付与总周期计时从模拟需求正式交给执行代理时开始

#### Scenario: 两组按冻结参数独立执行
- **WHEN** 同一用例的插件组与对照组开始运行
- **THEN** 两组只能访问自己的工作区和公开输入，运行清单记录相同基线与预算、实际启动顺序和不同执行模式，且任一组不能读取另一组的提示、日志、差异或结果

#### Scenario: 执行路线与产物不符时样本无效
- **WHEN** 插件组没有可验证的快速或完整路线记录，或对照组产生需求、OpenSpec 等插件工作流产物或调用证据
- **THEN** 系统把该次运行标记为无效并记录稳定原因，不得仍计入效果比较

### Requirement: 执行器必须支持首次交付、澄清和返工循环

系统 MUST 通过非 shell、可注入、可超时和可恢复的执行器保存结构化阶段事件。代理首次提交可验收结果后，独立验收器 MUST 运行；验收失败时只把必要失败反馈返回原会话并计为一次返工，代理提出材料中未回答的问题时只按冻结澄清预案响应并计数（D-07、A-04、A-07）。

#### Scenario: 首次验收通过
- **WHEN** 执行代理第一次结束实现且隐藏验收器全部通过
- **THEN** 系统记录一次验收通过、零返工、真实首次交付时长和总周期，并保留验收命令、退出状态、结果摘要与差异统计

#### Scenario: 验收失败后原会话返工
- **WHEN** 第一次或后续验收失败且没有超过冻结返工上限
- **THEN** 系统向同一会话提供经过脱敏的失败反馈，返工次数增加一，再次运行相同隐藏验收器并保留每一轮结果

#### Scenario: 代理请求必要澄清
- **WHEN** 代理明确请求公开需求未回答、但冻结澄清预案已定义的问题
- **THEN** 系统只释放对应答案并继续同一会话，澄清次数增加一；未命中预案的问题不得由编排器临时发明业务规则

#### Scenario: 超时、启动失败或中断
- **WHEN** 子进程无法启动、超过时间预算、返回非零状态或收到终止信号
- **THEN** 系统分别记录启动错误、真实退出码、超时或中断，终止当前子进程，保留已完成证据，并进入有界清理流程

### Requirement: 指标必须保留未知语义和可审计来源

系统 MUST 为每次运行记录首次交付时长、总周期、澄清次数、返工次数、阻断次数、误阻断候选、一次验收结果、最终状态、改动文件与行数、命令退出状态、执行路线和证据描述。无法可靠提取或确实未发生的字段 MUST 为带原因的 `null`，不得用零值或 Git 提交时间推断；首次交付前即阻断的运行在阻断和最终状态证据完整时 MUST 保留为有效失败结果，不能因首次交付为 null 而排除（D-07、D-08、A-04）。

#### Scenario: 完整运行形成有效样本
- **WHEN** 运行具有冻结基线、合法路线、开始时间、最终时间、全部适用计数、独立验收或证据完整的阻断结果和完整证据摘要
- **THEN** 系统标记该运行有效，并允许它进入同用例配对比较；已交付运行必须有首次交付时间，首次交付前阻断则以带原因的 null 保存该字段

#### Scenario: 不完整运行保持无效
- **WHEN** 任一必填指标、路线证据、验收结果或持久证据缺失
- **THEN** 系统将缺失字段保留为 `null`，列出数据质量原因并排除该运行及对应不完整配对，不得补零或推断成功

#### Scenario: 误阻断只有确定性反证时自动成立
- **WHEN** 代理报告阻断，且冻结预检或同一未改变环境中的确定性检查证明所需文件、命令或资源当时可用
- **THEN** 系统标记 `false-blocker-confirmed`；只有语义判断或证据冲突时标记 `review-required`，不自动算入确认误阻断率

### Requirement: 证据持久化与清理必须限制在本轮输出根

系统 MUST 把冻结清单、结构化事件、脱敏日志、验收摘要、差异统计、指标和清理结果限制在 `outputs/developer-effectiveness-benchmark/<run-id>/`。成功、阶段失败和进程异常均 MUST 清理本轮工作区；清理失败 MUST 保留原始运行结果并单独报告（D-10～D-12、A-05、A-07）。

#### Scenario: 持久输出经过脱敏和限长
- **WHEN** 代理、Git 或验收命令输出包含业务绝对路径、令牌、Cookie、密码、私钥或超过大小上限
- **THEN** 系统替换业务路径别名、拒绝持久化敏感原文并截断非敏感超长内容，同时记录稳定脱敏或截断状态

#### Scenario: 清理只作用于有界工作区
- **WHEN** 一轮运行成功、失败、超时或中断后开始清理
- **THEN** 系统只删除本轮工作区下已验证的非符号链接目录；越界、根目录、用户主目录或符号链接目标必须失败关闭

#### Scenario: 恢复运行不覆盖既有证据
- **WHEN** 使用同一运行 ID 重启已部分完成的基准
- **THEN** 系统校验冻结清单和既有证据摘要，只继续允许恢复的未完成阶段；内容冲突或已完成输出重写请求必须阻断

### Requirement: 汇总必须明确合成属性与结论门槛

系统 MUST 按项目、复杂度和执行组汇总有效样本、一次验收通过率、平均首次交付时长、平均总周期、平均澄清、平均返工和确认误阻断率，并生成稳定 JSON 与工作簿导入数据。所有输出 MUST 显著标记为合成基准并列出限制（D-02、D-09、A-06）。

#### Scenario: 六个配对样本完整时生成相对比较
- **WHEN** 六个用例的插件组和对照组均为有效样本
- **THEN** 系统报告十二次运行和六个有效配对的分组指标、逐用例差异与限制，但不把结果描述为真实开发者或团队生产收益

#### Scenario: 有效配对不足时不形成优劣结论
- **WHEN** 至少一个用例缺少任一执行组的有效样本
- **THEN** 系统展示已采集状态、无效原因和现有描述性指标，并明确 `conclusionStatus=insufficient-pairs`

### Requirement: 跨平台验证必须与本机试点分层

系统 MUST 对路径、临时目录、环境变量、子进程、结构化诊断、超时、中断和清理提供确定性平台回归，并分别记录聚焦测试、本地统一验证和真实五平台 CI 证据（D-12、A-07）。

#### Scenario: Windows 与 POSIX 路径得到一致机器结果
- **WHEN** 回归输入 Git 风格 Windows 路径、Node 风格 Windows 路径、POSIX 路径、尾部分隔符、空格和非 ASCII 目录
- **THEN** 系统对比较双方使用相同目标平台路径语义，生成一致别名和稳定机器字段，不直接启动 Windows `.cmd` 包装器

#### Scenario: 没有真实矩阵证据时只报告本地结果
- **WHEN** 聚焦回归和本地统一验证通过但同一提交的五平台 CI 尚未完成
- **THEN** 系统只声明本地层级通过，并把外部矩阵保持待执行，不得宣称跨平台发布验证完成
