## 背景与目标

插件已经完成核心流程、信任边界与动态依赖事实等阶段，但仓库 fixture 和插件自身测试不能独立证明它在真实历史项目中不会漏识别、误执行或夸大结论。本需求以用户指定目录中筛选出的六个真实前端项目建立验证矩阵，覆盖 Vue 3/Vue 2/React、Vite/Webpack/混合工具链、npm/Yarn、Vitest/Jest、uni-app 与原生微信小程序。

本轮目标不是继续扩展框架名单，也不是在验证过程中直接修复业务项目，而是形成可重复、可审计的证据：插件识别的每项事实都能回溯到项目文件；允许自动执行的链路真实运行；缺少命令、配置或认证证据时明确阻断；最终结论只覆盖已经取得的证据。

## 范围

### 包含

- 固定六项目的路径、分支、提交号、干净状态、框架、构建工具、包管理器、测试命令与运行器事实。
- 对六项目执行插件只读识别，并逐字段核对根 package、配置和测试文件证据。
- 在隔离副本中验证初始化预览、显式写入、重复执行、升级、检查、自定义内容保护与未受管文件冲突。
- 按 D-08 执行 P1～P4 的项目原生测试链，并验证 P5/P6 的正确阻断与人工边界。
- 检查 P4 混合工具链是否被单一 preset 过度概括，以及 P5 嵌套 package 是否被错误宣传为 Monorepo 支持。
- 形成逐项目、逐能力、逐证据的矩阵和总览结论，区分通过、有限、阻断和缺陷。
- 运行插件聚焦回归、本地统一验证、官方 validators；仅在插件代码发生变化时要求最终提交五平台 CI。
- 修复 P3 测试启动器误报，并把 Windows 多来源路径的双侧规范化要求写入仓库规则、插件规则模板、共享清单和确定性回归。

### 不包含

- 修改六个业务项目的源码、配置、package manifest、锁文件、测试或 Git 历史。
- 在业务项目或隔离副本中联网安装、更新依赖，或自动修复发现的问题。
- 访问后端、生产环境、真实账号、敏感数据或内部远程服务。
- 认证远程 Figma/蓝湖同步、浏览器视觉还原、微信开发者工具完整发布链或业务接口正确性。
- 宣称 pnpm、React + Vite、真实 workspace/Monorepo、多前端应用编排和所有非 Vitest 运行器已经完整认证。
- 漏洞库、许可证、依赖最新版本、安全审计或传递依赖兼容结论。
- 修改 P3 或其他六个业务项目的测试、脚本、依赖或 Git 历史；本轮只修复插件自身识别逻辑。

## 当前行为

- 插件仓库已有 fixture、专用回归、本地统一验证和五平台 CI 证据，但真实历史项目尚未形成统一、可复验的项目级矩阵。
- 项目识别能够动态采集根 package 直接依赖并输出有限兼容画像，但还没有逐个对照这六个真实项目验证误报、漏报和结论措辞。
- Vue 3 + Vite + Vitest 是当前认证链；Jest、混合工具链、uni-app 和原生微信项目只有有限或阻断边界，不能从脚本存在推断真实成功。
- Monorepo/多应用、远程设计同步和外部 CI/PR 状态回写仍未被这六项目覆盖。
- P3 的 `scripts/test.js` 当前被文件名规则误计为测试文件；Validate #43 还暴露了 Git 与 Node 路径分隔符不同却直接严格比较的问题，说明仅覆盖单个反斜杠样本不足以保护真实 Windows 路径来源。

## 期望行为

### 场景：六项目只读识别与事实核对

- 前置条件：六项目位于 D-01 的精确提交且原工作区干净。
- 当：执行项目检查、依赖画像和测试上下文检查。
- 则：每个机器结论都能由根 package、配置、测试文件或 Git 状态证明，并记录稳定字段与证据来源。
- 并且：未知或冲突信号保持有限/冲突，不因目录名或固定名单生成完整技术栈结论。
- 异常或边界：任一工作区不再干净或提交漂移时，该项目写入型验证立即阻断并要求重新确认基线。

### 场景：隔离副本中的工作流生命周期

- 前置条件：隔离副本从精确提交创建，原工作区保持只读，磁盘与依赖条件满足。
- 当：依次执行初始化预览、显式写入、重复写入、升级预览/写入和工作流检查。
- 则：预览零写入；写入只创建或更新受管内容；重复执行幂等；升级保留标记外自定义内容；未受管冲突被拒绝覆盖。
- 并且：成功与失败均记录变更文件清单和清理结果，原项目 Git 状态与提交号前后完全一致。
- 异常或边界：依赖无法在不联网、不污染原项目的条件下运行时，结果为 `blocked`，不得降级到原工作区偷偷执行。

### 场景：不同测试链的真实执行与阻断

- 前置条件：项目测试命令、运行器与目标测试文件均来自真实项目证据。
- 当：在隔离副本中按 P1～P6 的矩阵执行最窄可用命令。
- 则：P1 记录完整 Vitest 闭环；P2/P3/P4 分别记录实际 Jest/Vitest 发现数、退出码和失败分类；P5/P6 因命令或运行器证据不足保持阻断。
- 并且：退出 0 但零测试、没有目标定位、启动失败和产品断言失败分别分类，不合并为“测试失败”或“通过”。
- 异常或边界：大型全量命令若超出聚焦验证需求，先执行已存在的专用/最窄命令；只有共享链影响或无聚焦入口时才执行全量并记录理由。

### 场景：形成不越界的支持结论

- 前置条件：各项目验证记录包含提交、环境、命令、状态、证据和剩余风险。
- 当：汇总项目矩阵并评估插件当前支持范围。
- 则：结论明确哪些能力已通过、哪些只是有限支持、哪些正确阻断、哪些是插件缺陷。
- 并且：未覆盖的 pnpm、React + Vite、真实 Monorepo、多应用、远程设计同步和全平台项目运行继续列为缺口。
- 异常或边界：没有实际运行或缺少机器证据的项目不得使用“已认证”“完整支持”或“没有兼容性问题”。

### 场景：区分测试启动器与测试用例

- 前置条件：项目测试命令通过 `node scripts/test.js` 启动 Jest，`scripts/test.js` 位于普通脚本目录且没有 `*.test.*`、`*.spec.*` 或测试目录证据。
- 当：插件只读检查测试命令、运行器、测试目录和测试文件。
- 则：测试命令与 Jest 运行器仍被识别，`scripts/test.js` 不进入 `testFiles`、`handwrittenTests` 或 Git 跟踪测试清单。
- 并且：真实的 `*.test.*`、`*.spec.*` 以及已识别测试目录中的合法 `test.*` 不受影响。

### 场景：比较 Windows 与外部工具返回路径

- 前置条件：Git 或其他子进程在 Windows 返回 `D:/workspace`，调用方通过平台路径 API 得到 `D:\\workspace`，或在非 Windows 主机验证 Windows 样本。
- 当：路径参与相等、集合、前缀、去重或机器证据判断。
- 则：实际值和期望值通过同一规范化函数后再比较，不直接比较原始字符串，也不根据 `process.platform` 推断外部输出格式。
- 并且：确定性回归同时覆盖 POSIX、Windows、正斜杠、反斜杠和外平台解析，最终发布证据仍要求同一提交五平台真实成功。

## 接口与数据

- 接口文档链接：本需求关联 OpenSpec delta spec 与 `test-plan.md`。
- 请求方法与路径：本地 CLI argv；输入为六项目绝对路径、精确提交和有界输出目录，不调用 HTTP 接口。

## 兼容性与风险

- 受影响页面、公共组件、路由、权限或接口：不修改业务页面、公共组件、路由、接口或权限；当前阶段影响测试上下文识别、规则模板、跨平台路径约束、验证资产与最终支持结论。
- 历史数据与兼容策略：原项目始终只读；验证副本固定提交并独立清理；已存在 outputs 资产不整体删除。
- 上线与回滚注意事项：P3 修复只修改插件识别逻辑与规则资产；出现回归时回滚插件提交即可，业务项目无需回滚。本矩阵只清理本轮隔离副本并保留报告。
- 跨平台高风险：是；命中 CI、路径、临时目录、子进程、包管理器入口和机器可读诊断。多来源路径必须双侧使用同一规范化函数；外平台样本使用 `path.win32`/`path.posix`；Windows 不直接启动 `.cmd` 包装器；结构化断言不依赖完整中文文案、绝对路径或换行。
- 受影响平台：真实项目本轮只在 macOS ARM64 执行；插件若产生代码变更，则额外验证 Linux x64/ARM64、Windows x64、macOS Intel/ARM64 的同一提交 CI。
- 剩余风险：真实项目依赖可能无法离线复制或安全复用；历史测试可能有与插件无关的失败；六项目不能代表全部框架、包管理器、运行器、浏览器或业务环境。

- 独立测试方案：需要；触发条件：需要跨六项目、D/A/V、生命周期和不同测试链追踪；活动变更与目标：`openspec/changes/validate-real-project-matrix/test-plan.md`；需求修订基线：R-01。
