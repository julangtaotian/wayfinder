# REQ-2026-025：前端测试用例工作流

## 基本信息

- 状态：待验证
- 提出人：用户
- 负责人：Codex
- 目标版本：0.15.0
- 关联页面或模块：公共 Skills、需求与变更规划、测试上下文识别、测试方案校验、完成门禁、README 与插件发布
- 关联变更：`add-frontend-test-workflow`

## 背景与目标

当前工作流已经要求需求记录交互状态矩阵和测试文件策略，也要求 `$frontend-change` 在实施期间补充必要测试，但“测试用例形成”仍依赖单次 AI 实施判断。使用者不能在写业务代码前独立审查具体测试用例，也没有稳定的 `TC-*` 产物来追踪业务决策、验收、测试代码与验证证据之间的关系。

本需求新增统一的 `$frontend-test` 公共能力，在复用现有需求台账、OpenSpec 变更和 `D-* / A-* / V-*` 生命周期的前提下，提供“只读分析、测试方案形成、测试代码实现、聚焦验证和证据同步”闭环。首版不建设第二套管理生命周期，不安装测试依赖，不自动修改业务源码，并以 Vue 3 + Vite + Vitest fixture 证明最小完整能力。

## 范围

### 包含

- 新增 `$frontend-test` 公共 Skill，并以用户自然语言自动路由只读分析、测试方案、测试实现和验证意图。
- 新增测试用例规则与 `test-plan.md` 模板，定义 `TC-*`、需求修订基线、测试定位、执行命令、状态和证据合同。
- 新增测试上下文只读检查，识别项目规则、测试命令、测试目录、配置、手写专用测试、生成测试基线和 Git 基线。
- 新增测试方案三阶段校验器，提供稳定 JSON 字段、中文诊断、危险路径拒绝、事实引用校验、过期检查和完成门禁。
- 更新需求模板、需求编写规则和 `$frontend-change`，让行为变更的规划、实施与完成能够引用并校验测试方案。
- 更新项目健康检查与完成入口，使已声明测试方案的非法、过期或未完成状态保持可见并阻止错误完成。
- 在 Vue 3 + Vite + Vitest fixture 上验证新建专用测试、聚焦执行、零测试发现、重复执行和失败分类边界。
- 更新 README、插件 manifest、公开 Skill 清单、结构校验和版本元数据。

### 不包含

- 自动安装、升级或配置 Vitest、Jest、Cypress、Playwright 等业务项目依赖。
- 在 `$frontend-test` 中修改业务源码、自动修复产品缺陷或降低已确认断言。
- 新建独立测试用例管理后台、远程服务、账号连接或业务项目常驻运行时。
- 自动覆盖率目标、覆盖率看板、Mutation Testing、性能压测、安全扫描或无障碍专项平台。
- 为所有前端框架维护固定测试代码模板，或把插件内置 UI Review Playwright 变成业务项目测试依赖。
- 自动改写全部历史测试、默认修改 `.generated.spec.*`、默认执行全量测试或把未执行结果标记为通过。
- 为无活动变更的存量功能持久化测试方案或直接写入回归测试；首版只提供只读缺口审计。
- 修改两个既有活动变更的业务范围或 Playwright 平台发布行为。

## 当前行为

- 需求模板只有状态矩阵、测试文件策略和“自动测试”摘要，没有结构化 `TC-*` 测试方案。
- `$frontend-change` 会在实施期间选择和补充测试，但没有可独立调用的测试设计与验证入口。
- 需求校验器可以检查 D/A/V、状态矩阵、测试文件路径和 Git 基线，但不会校验具体用例、需求修订基线、测试定位和执行结果。
- 公共 Skill 列表没有测试能力，项目检查不会报告测试方案状态。
- UI Review 已能形成视觉证据，但不负责生成业务项目原生自动测试。

## 期望行为

### 场景：只读分析测试覆盖

- 前置条件：用户指定需求、活动变更或受影响模块，项目可能存在或缺少测试设施。
- 当：用户要求分析、盘点或检查测试覆盖，未要求写入。
- 则：工作流读取需求事实、源码、测试、配置、命令和 Git 基线，形成测试上下文与覆盖缺口。
- 并且：不创建测试方案、测试文件、依赖或验证记录。
- 异常或边界：没有活动变更时保持只读，不把当前实现推断成已确认产品行为。

### 场景：形成可审查测试方案

- 前置条件：需求状态为已确认或实施中，活动变更已经声明适用 D-* 与 A-* 范围。
- 当：用户要求生成或持久化测试用例。
- 则：在该变更内形成 `test-plan.md`，每条 `TC-*` 可追溯到已确认事实、验收、规格和状态覆盖。
- 并且：plan 阶段校验通过后才允许描述为可实施。
- 异常或边界：未确认决策、缺失来源、危险路径、重复 ID 或未知引用使方案保持阻断。

### 场景：实现项目原生测试

- 前置条件：测试方案 implement 校验通过，用户明确要求实现，项目存在可用测试设施。
- 当：工作流按用例目标新增或扩展测试。
- 则：只修改同功能手写专用测试或新建职责清晰的专用测试文件，复用项目已有工具与风格。
- 并且：每条自动用例记录稳定测试定位，重复执行不重复添加用例或文件。
- 异常或边界：缺少测试设施、目标文件冲突、生成测试误用或需要业务源码修复时停止并报告。

### 场景：聚焦验证并同步证据

- 前置条件：自动测试用例已经实现，测试方案记录可用聚焦命令。
- 当：用户要求验证或复验。
- 则：只执行相称的聚焦测试，记录真实退出结果并分类失败原因。
- 并且：只有实际成功的用例才能关联通过的 V-*，视觉与人工用例引用对应持久证据。
- 异常或边界：零测试发现、环境阻塞、历史无关失败或产品缺陷不能被改写成通过。

### 场景：需求修订使旧方案失效

- 前置条件：测试方案记录需求修订基线，需求新增了更晚的 R-* 记录。
- 当：再次规划、实现或完成变更。
- 则：确定性校验报告测试方案已过期，要求重新核对受影响用例。
- 并且：未更新方案前不得继续实现或完成。
- 异常或边界：不自动改写历史用例或假定所有用例仍然有效。

## 页面与交互

- 入口与操作路径：用户通过 `$frontend-test` 或自然语言请求分析、形成用例、实现测试、验证和复验；`$frontend-change` 在相关阶段消费同一测试方案。
- 字段、文案与默认值：公共名称为 `frontend-test`；用例使用 `TC-01` 起的稳定 ID；校验阶段使用稳定英文 `plan / implement / complete`；错误信息使用中文。
- 加载态、空态、错误态、禁用态：无图形界面；缺少测试设施为空态，未确认事实、非法方案、过期基线和测试失败为明确错误或阻断状态。
- 权限与角色差异：只读分析不写文件；持久化方案、测试实现和测试执行分别服从用户请求与现有仓库权限。
- 设计稿链接：不适用。

## 接口与数据

- 接口文档链接：仓库内 `test-plan.md` 模板、测试用例规则和命令帮助。
- 请求方法与路径：通过 Skill 调用插件内置 Node.js 标准库脚本；规划根必须来自当前项目，不能回退到未授权全局 Store。

## 兼容性与风险

- 受影响页面、公共组件、路由、权限或接口：不涉及业务页面；影响公共 Skill 清单、需求/变更规划、测试代码写入边界、项目检查和完成门禁。
- 历史数据与兼容策略：没有测试方案的历史需求与变更继续可读；只有当前变更显式声明测试方案时启用新门禁，不自动补写历史测试事实。
- 上线与回滚注意事项：新增能力必须随插件版本、结构校验和官方 validators 一起发布；失败时可以移除新 Skill 与关联门禁，不改变业务项目已有测试。
- 主要风险：测试方案可能与规格重复、跨 runner 发现语义不一致、AI 生成脆弱断言、完成门禁误伤历史变更；通过派生事实引用、项目原生模式、首版兼容声明和显式启用降低风险。

## 测试与验证

- 测试文件策略：新建；目标路径：`tests/frontend-test-workflow.test.mjs`；基线证据：当前路径不存在且未被 Git 跟踪；选择理由：测试用例工作流包含独立的上下文、方案合同、校验阶段、写入边界和 fixture 闭环，应使用职责清晰的专用测试，不继续扩充综合工作流测试。
