# 测试用例工作流规则

测试方案是活动变更的技术派生产物，需求台账仍是业务事实源。测试用例只能展开已确认或项目默认的 D-* 与 A-*，不得通过断言补充产品规则。

## 阶段与写入边界

- “分析、盘点、检查覆盖”默认只读；没有活动变更时只能返回缺口，不创建方案或测试文件。
- “形成、生成测试用例”在活动变更内创建或更新 `test-plan.md`，并把 `.openspec.yaml` 的 `test_plan` 设为 `required`；不得覆盖其他元数据。
- “实现测试”必须由用户明确请求，并先通过 implement 校验；只修改测试代码，不修改业务源码或安装业务依赖。
- “验证、复验”执行方案记录的项目原生命令；只有真实发现计划用例且退出成功才可记录通过。

## 测试方案合同

- 方案必须位于所选活动变更根目录，文件名固定为 `test-plan.md`。
- 基本信息必须记录状态、仓库相对需求路径、完整变更名、最新 R-* 基线和默认聚焦命令。
- 状态只使用“草稿、就绪、已实现、已验证”。
- 每条用例使用唯一 `TC-01` 格式标题，并完整填写模板字段；字段不适用时写明“不适用”，不能留空。
- 每条用例必须关联所选变更范围内可执行的 D-*、A-* 和 V-*，并写明规格场景与六类状态矩阵中的适用状态。
- 自动用例必须包含安全的项目相对测试路径、稳定测试定位和聚焦命令；测试定位优先在新测试标题中保留 `[TC-01]`。
- 视觉用例把目标测试、测试定位和聚焦命令写为“不适用”，并在证据中引用现有 UI Review 场景、视口和持久文件。
- 人工用例必须在前置、操作、断言和证据中记录设备或环境、检查项和持久证据位置。

## 三阶段校验

- plan：检查文件合同、事实来源、变更范围、路径安全和生成测试保护；允许用例尚未实现、结果为“未执行”、证据为“待执行”。
- implement：额外要求方案状态至少为“就绪”、需求状态可实施、R-* 基线最新；自动用例必须有 detected 测试命令、目标测试和聚焦命令。
- complete：要求方案状态为“已验证”，自动用例状态和结果分类均为“通过”，人工或视觉用例为“人工通过”，目标测试、V-* 与可识别持久证据存在。
- 晚于方案基线的任何 R-* 都使整个方案过期；首版不猜测某项修订是否只影响部分用例。

## 测试文件与依赖

- 复用测试模式不等于复用文件。先找同功能手写专用测试，没有时再在真实测试目录创建专用文件。
- `.generated.spec.*` 只作为基线参考，除非项目规则明确授权并在需求与方案同时记录来源和理由。
- 只使用项目已经声明的 runner、配置、fixture、mock 和断言习惯；不得调用安装命令或把插件运行时注入业务测试。
- 缺少测试设施时保留人工用例或阻断自动实现，不能虚构命令、目录或“通过”结果。

## 结果与交接

- 结果分类只使用“未执行、通过、产品实现缺陷、测试设计错误、测试代码错误、需求歧义、环境阻塞、历史无关失败”。
- 零测试发现属于测试设施或测试代码阻断，不是通过。
- 产品实现缺陷交回 `$frontend-change`；测试入口不得顺手修改业务源码或降低已确认断言。
- 全量验证仍遵守影响面规则，聚焦结果、全量结果和历史无关失败分别报告。
