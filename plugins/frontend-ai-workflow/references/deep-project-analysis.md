# AI 深度项目扫描规则

本规则用于用户明确要求深度扫描、全量项目地图或高可信项目上下文时。默认初始化不执行本流程。

## 前置与范围

1. 阅读目标仓库适用的 `AGENTS.md`，执行 `git status --short`，保留所有已有改动。
2. 使用插件的只读范围清单命令获取纳入范围、排除目录、文件限制和稳定文件列表：

   ```bash
   node <plugin-root>/scripts/collect-project-scope.mjs --target <repository-root>
   ```

3. 范围清单只定义要处理的材料，不代表业务架构。不得根据目录名、文件名、依赖名或框架惯例直接得出项目结论。
4. 范围收集必须在读取前排除真实 `.env`、凭据、密钥和 Git 忽略项；环境模板可以纳入，但不得把任何疑似密钥值写入报告或 Wayfinder。
5. 不安装依赖、不启动服务、不执行构建或测试，除非用户在本次任务中明确要求验证。

## 覆盖阶段

1. 将范围清单中的每个纳入文件分批读取；不得只读取少量“代表文件”。
2. 对每个文件记录一个状态：`已阅读并归类`、`超限`、`不可读取`、`读取后内容变化` 或 `用户明确排除`。逐文件账本在本次扫描报告中保留；长期上下文只记录总量、覆盖边界和未完成原因，避免为扫描过程新增文档或堆积冗长清单。
3. 建立初始项目地图，至少列出入口、构建与运行配置、路由、页面、组件、状态、请求与服务、鉴权与权限、测试、样式和文档。
4. 如果任一纳入文件尚未处理，最终报告必须列出该文件与原因，不得声称已完成完整项目分析。

## 验证证据边界

1. 将范围结果的 `validationEvidence` 作为能力事实：安全枚举、文本读取和内容哈希已执行，不代表语法解析、平台编译、Lint 或测试已执行。
2. 没有真实执行具体解析器、平台工具、Lint 或测试命令时，不得写“没有解析错误”“编译通过”“Lint 通过”或“测试通过”。只有命令实际成功后才能按该命令的范围报告结果。
3. `observations` 只是不阻断的静态观察。`wxml-attribute-spacing` 表示对应路径和行号需要平台工具复核，不等于已经确认的 WXML 语法错误或编译失败。
4. 观察数组为空只表示没有命中当前启发式模式，不表示源码已经通过完整语法或平台编译验证。

## 深读阶段

在初始地图完成后，围绕跨文件链路阅读完整上下文并交叉核对：

- 路由文件与对应页面；
- 服务模块、请求层和环境配置；
- 用户信息、权限逻辑与路由守卫；
- 构建 base、路由 base 与部署相关配置；
- 测试脚本、测试资产及关键行为覆盖；
- 公共组件、全局样式和状态管理的影响范围。

发现以下任一类源码、配置或公开依赖证据时，再补充对应扩展维度；没有证据时保持不写，不能按框架惯例猜测：

- 国际化资源、语言路由、格式化和回退策略；
- Service Worker、PWA 清单、缓存和离线降级；
- 设计 Token、Storybook、可访问性规则和组件演示；
- 错误追踪、埋点、性能观测、实验或 Feature Flag；
- 跨端入口、条件编译、平台生命周期和目标发布配置。

动态导入、运行时拼接、环境变量实际值、后端协议和仓库外业务约定不能仅凭源码确认，必须记为待确认项。

## 结论合同

深度分析必须写入既有 `wayfinder/frontend.md` 的受管分析区块，且包含：

1. 扫描范围与覆盖报告（总量、排除原因、未覆盖原因、验证证据边界、静态观察和覆盖边界）；
2. 本次范围指纹、扫描时间、Git 提交与工作区脏状态；
3. 项目地图；
4. 已确认事实，每项提供来源文件，必要时提供行号；
5. 推断，说明依据与边界；
6. 待确认项，说明不能确认的原因；
7. 高风险区域与验证建议。

## 项目地图完成状态

`deepAnalysis: true` 仅表示范围清单、范围指纹和安全读取边界已经建立。项目地图通过 `meta` 区块中的以下字段单独表示完成度：

- `analysisStatus: pending`：已取得范围快照，尚未开始项目地图；`analysisCoveredFiles` 必须是 0。
- `analysisStatus: partial`：只读完部分纳入文件；覆盖数必须大于 0 且小于 `scopeIncludedFiles`，删除待生成占位内容，并在项目地图中写清未覆盖文件和原因。
- `analysisStatus: complete`：每个纳入文件均已阅读和归类，`analysisCoveredFiles` 必须等于 `scopeIncludedFiles`，`analysisUpdatedAt` 必须为 ISO 时间。

写入 `complete` 时，删除分析区块中的待生成占位标记，并至少保留“项目运行与交付边界”“功能与依赖链路”“数据、状态与安全边界”“验证基线与高风险区域”“事实、推断与待确认项”五个维度。标题可以根据项目语义调整，但每个维度前必须分别保留且只保留一个稳定标记：

```text
<!-- frontend-ai-workflow:analysis-dimension:run-delivery -->
<!-- frontend-ai-workflow:analysis-dimension:functional-dependencies -->
<!-- frontend-ai-workflow:analysis-dimension:data-state-security -->
<!-- frontend-ai-workflow:analysis-dimension:verification-risks -->
<!-- frontend-ai-workflow:analysis-dimension:facts-inferences-questions -->
```

标记必须位于 `frontend-ai-workflow:analysis:start/end` 区块内，区块外的同名标记不构成完成证据。按证据启用的国际化、PWA、设计系统、观测和跨端维度不属于小项目的必填项。每个稳定结论仍须附来源；维度标记只保证信息结构齐全，不替代证据。

深度刷新会先将状态重置为 `pending`，以免旧项目地图在新范围快照下被误认为有效。刷新后只有重新完成阅读、交叉核对和状态更新，才可再次标记为 `complete`。

任何没有来源证据的内容不得写入“已确认事实”。跨文件链路至少引用首尾关键文件。存在未覆盖、超限或不可读取项目时，必须说明结果的覆盖边界。

同时替换 `AGENTS.md` 的 `frontend-ai-workflow:deep-guardrails:start/end` 区块。该区块只保留 4–8 条项目专属、可执行的硬约束：优先提炼已确认的请求边界、鉴权/会话或安全状态、路由/构建边界、以及测试基线；每条附关键源码路径。没有源码证据的推断和待确认项只能留在 Wayfinder，不得写成 AGENTS 约束。

## 写入与复核

1. 先执行 `bootstrap-project.mjs --deep` 展示范围摘要和既有工作流文件的计划；未确认前不写入文件。
2. 用户确认后执行 `bootstrap-project.mjs --deep --write` 创建或刷新受管范围区块；深度模式不得新增项目分析文档。
3. 仅在用户已确认写入后，替换 `wayfinder/frontend.md` 的 `analysis` 受管区块及 `AGENTS.md` 的 `deep-guardrails` 区块；保留 `meta`、`scope` 区块、AGENTS 外层受管区块的其他通用规则和所有标记之外的维护者内容。
4. 若 Wayfinder 缺少有效的 `meta`、`scope` 与 `analysis` 成对标记，停止并报告冲突，不得覆盖或插入标记。
5. 写入后执行工作流健康检查，并汇报覆盖数量、未覆盖原因、证据边界和写入文件。
6. 普通工作流升级只保留既有范围快照，不代表分析已经刷新；健康检查提示指纹过期时，必须重新预览并由用户确认深度刷新。
