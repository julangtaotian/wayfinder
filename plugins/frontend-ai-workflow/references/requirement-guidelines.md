# 需求文档规则

需求文档的目标是让产品、开发、测试和 AI 对同一行为达成一致，而不是提前写实现代码。

## 必须包含

- 背景与可观察目标。
- 明确的包含范围和不包含范围。
- 当前行为与期望行为。
- 主要场景、失败场景和边界场景。
- 页面入口、字段、默认值、加载态、空态、错误态和权限差异。
- 接口路径、方法、字段、状态码和空值语义；未知内容必须标记待确认。
- 兼容性、风险、测试计划和可勾选验收标准。

## 编写原则

- 区分用户已经确认的需求、基于项目现状的暂定方案和仍待确认的问题。
- 不把推测写成已确认事实。
- 使用可验证的“前置条件、当、则、并且”描述交互。
- 对安全性要求给出具体边界，例如长度、允许字符、敏感信息存储和服务端校验。
- 受管变更创建后，需求文档保留为入口，详细实现依据以变更规划资料为准。

## 平台画像的条件化分析

- 先读取 AGENTS 或 Wayfinder 中的 `targetPlatformKind`、框架、来源和证据；画像是需求分析输入，不是框架运行或发布能力证明。
- 同时读取 `platformCommandStatus`、目标、证据和候选摘要；`detected` 只证明非空脚本名存在，不能写成已构建、已验证或已发布。
- `native-mini-program`：只在需求相关时核对小程序生命周期、页面与导航、授权与隐私、存储、网络域名、分包和开发工具验证边界；没有用户或源码依据的细节保持待确认。
- `cross-platform`：先确认本次需求影响的真实发布目标及差异，再核对框架生命周期、条件编译、路由、权限、存储、网络和构建命令；不得因框架依赖推断微信、支付宝或 H5 已经可用。
- `conflict`：明确列出多框架证据并确认本次影响范围，不能自行选择框架或生成跨框架实施任务。
- `unknown`：不主动增加小程序专项需求；只有用户描述或受影响源码提供新的平台事实时，才把对应边界加入决策台账。
- 已确认目标存在多个平台命令候选时，验证计划列出实际选用依据，不由画像自动选择；只有命令真实执行成功后才能更新对应 V-* 为通过。
- 已识别平台框架但平台命令缺失时，把所需人工开发工具或外部 CI 环境写入验证计划和剩余风险，不得根据框架习惯虚构脚本、安装工具或扩大自动执行权限。

## 决策事实源

- 在正文之前先完成“决策台账”：每项使用唯一 `D-01`、`D-02` 等 ID，并完整填写决策项、状态、取值和来源。
- “已确认”只能来自用户明确说明、已确认需求或可追溯的正式业务规则；“项目默认”只能来自项目规则或源码证据，且必须写明路径或规则来源。
- 关闭语义、权限、接口、持久化、输入规则、兼容范围、敏感数据处理和用户可见文案等空白，必须标为“待确认”或带来源的“暂定”；不得把 AI 推测写成已确认事实。
- “暂定”和“待确认”只能说明风险或待确认问题，不能进入实现任务、规格承诺或验收标准；用户确认后才更新其状态。
- 拆分文档使用 `D-*` 引用需求事实。不得重新发明、改写或静默补充业务决策；技术实现选择与业务决策冲突时，以决策台账为准并先修订需求。

## 需求修订与变更范围

- 新需求建立受管变更后，在“关联变更范围”中为每个变更显式填写变更名、适用 D-* 和适用 A-*；一个需求拆分多个变更时不得让单个变更静默承担全部范围。
- 范围、用户可见行为、接口、权限、安全、数据或兼容决策变化时，先更新需求决策台账、验收标准、证据映射和状态矩阵，再修订规划资料。
- 每次行为修订增加唯一 `R-*` 记录，列出受影响 D-*、A-*、V-* 和任务；旧证据不能证明新行为时，将对应 V-* 恢复为“计划”并重新打开相关任务。
- 仅技术实现选择且不改变任何业务决策时，可以只修订设计与任务，但必须记录其需求依据。
- 只有决策台账中的“已确认”或“项目默认”行同时明确写出“本变更不改变可观察行为”和 `skip_specs: true` 时，规划才可省略 delta specs；缺少该授权、存在任何行为影响或已经产生 delta specs 时不得使用。
- 关联变更按完整目录名优先匹配，包括数字或日期前缀。只有校验系统生成的 archive 目录时，才允许在完整名称未命中后剥离一次 `YYYY-MM-DD-` 归档前缀。
- 新需求按“草稿 → 已确认 → 实施中 → 待验证 → 已验收”迁移；规划要求已确认，实施要求已确认或实施中，完成前检查要求待验证，归档成功后才更新为已验收。

## 验收—证据映射

- 每条验收标准使用唯一 `A-01`、`A-02` 等 ID，并在“验收—证据映射”中一一对应。
- 新需求状态只能使用“草稿、已确认、实施中、待验证、已验收”；只有完成全部交付验证后才可更新为“已验收”。
- 映射必须填写关联 `D-*`、`V-*`、验证方式（自动、人工或自动+人工）、证据位置和可观察断言结果。
- 字段错误文案、关闭提示、重置、权限和安全边界等可见行为，断言必须验证实际输出；“未进入成功流程”不能替代对要求文案或状态的验证。
- 每条 `V-*` 验证记录都填写验证类型、实际命令或人工环境、执行日期、结果和证据位置；计划阶段可记录“计划”，完成阶段必须为“通过”。
- V-* 使用可识别的仓库内相对路径时，完成前必须确认文件存在且没有越出项目范围；仅写“终端摘要”时只能视为文档记录，不能描述为已核验的持久文件。
- 视觉、设备或浏览器兼容项可以使用人工验证，但必须在 `V-*` 中写明视口或设备、检查项及截图或录屏路径；不能因无法自动化而没有证据。
- 编写完成后运行插件内置需求决策校验器；结构、引用、映射或证据校验失败时，先修订需求。因真实未决事项产生的状态失败应保留为草稿并明确向用户追问，不能伪造为已确认；在所有状态校验通过前，不进入变更规划或实施。

## 交互状态矩阵

- 新需求使用“初始（已有数据）、用户操作、刷新、空态、错误态、卸载”六行状态矩阵；每行选择“覆盖”或“不适用”，不允许静默遗漏。
- 涉及首屏数据渲染时，评估初始已有数据、空态和错误态；涉及筛选、表单、按钮或其他显式操作时，评估用户操作和刷新；涉及订阅、计时器、可取消请求、路由切换或组件销毁时，评估卸载。
- 标记“覆盖”的状态必须填写触发或前置条件、可观察期望、验证方式和关联 `A-*` 验收；覆盖仅指有对应断言或人工检查，不以“主流程未报错”替代。
- 标记“不适用”的状态必须说明具体原因；“本次未测试”不是不适用理由。无法确定时保留待确认问题，不得凭空排除状态。
- 旧需求缺少矩阵时保持可读；补充需求、修订规划或实施新交互时，应先补齐矩阵再决定测试场景。

## 测试文件策略

- 当用户要求独立形成、实现或持续复验多条测试用例，或变更需要跨 `D-* / A-* / V-*` 追踪时，在需求中把“独立测试方案”标为“需要”；创建活动变更后，方案固定写入该变更的 `test-plan.md`，并声明 `test_plan: required`。普通单点验证可继续只使用本节与验证记录，不强制补建方案。
- 测试方案是需求的技术派生，不是新的业务事实源。每条 `TC-*` 只能引用所选变更范围内已确认或项目默认的决策、验收和规格；无法确认的前置、操作或断言必须先进入需求修订，不能直接写进 TC。
- 方案记录当前最新 `R-*` 作为基线；需求出现更晚修订后，原方案整体过期，重新核对受影响用例并更新基线前不得实施或完成。
- 先读取受影响模块的测试目录，区分手写专用测试、通用测试基线和自动生成测试；复用既有测试模式不等于直接复用测试文件。
- 文件名包含 `.generated.spec.` 的测试属于通用生成测试基线：可用于理解已有覆盖、stub、mock 和断言风格，默认不承载新功能的专用交互场景。
- 存在覆盖同一功能的手写专用测试时，在该文件追加场景；不存在时，页面交互、表单状态或关键业务流程应在项目真实测试目录中创建名称表达功能职责的专用测试文件。
- 自动测试必须写明“新建 / 复用”、目标文件路径、Git 基线证据和选择理由；“复用”仅适用于已有手写专用测试。若项目自定义规则明确允许修改生成测试，必须同时记录规则来源和例外理由。
- Git 基线可用时，复用目标必须已受版本控制；若无法取得 Git 基线，明确记录无法确认，不得把它写成已有测试的证据。
- 测试目录无法判定或场景无法自动化时，不得猜测目标文件；写明待确认事项或人工验证方式。

## 验证范围策略

- 先根据受影响文件和调用链选择验证范围：局部页面、组件、表单或独立业务交互默认运行专用测试与必要构建，不默认执行全量测试或 coverage。
- 请求层、鉴权、路由、构建、共享组件或共享状态受影响时，或没有可用聚焦测试时，才升级为相称的全量测试或 coverage。
- 用户明确要求全量验证，或需求记录了发布级理由时，可以执行全量测试或 coverage；必须写明触发原因、命令和与本次需求无关的既有失败或网络噪声。
- 最终交付只是报告时机，不是执行全量测试或 coverage 的理由。项目提供的默认测试命令若实际运行全量 coverage，也不得因命令可用而自动执行。
- 自动测试计划必须写明“聚焦 / 全量”、执行命令和选择理由；若验证范围无法判断，先标记待确认，不得将 coverage 作为兜底。
